# 평가 체계 개편 진행 현황 (2026-10-13 기준)

설계안 원본: [평가체계_설계안_v1.1.html](평가체계_설계안_v1.1.html) (2026-10-12 확정). 이 문서는 설계안 각 단계가 코드에 어디까지 반영됐는지와 남은 일을 순서대로 적는다. 단계가 끝날 때마다 이 문서와 `변경내역/` 을 같이 갱신한다.

작업 원칙(사용자 결정): 코드 평가는 항상 PASS/FAIL만 낸다(미검사 없음) · 의미 평가는 기준 6 → 세부 기준 25 → 점검 항목 39로 판정하고 판정에 "모른다/판단 불가"는 없다 · 인용 검증 실패는 재확인 최대 3회 뒤 FAIL(확인 불가로 구분) · 답변의 출처 링크 유무는 판정에 쓰지 않는다 · 정답지는 없다 · 점검표를 따로 생성하지 않고 판정 시점에 질문의 요소를 펼친다 · 기존 방식(legacy)은 설정으로 되돌릴 수 있게 남긴다 · API 비용은 계산하지 않는다 · AIONA 특화 검사는 보류(건드리지 않음) · 변경마다 pull → commit → push(main).

## 3. 앞으로 할 것 (순서)

1. **3단계 마무리** — 위 테스트 3종, 검토, legacy 바이트 불변 스냅샷 확인.
2. **3b webapp 실시간 반영** — `comparison_service` 가 `semantic_context{answer_tools, collected_at}` 전달(API 수집 답변 = 도구 없음, AIONA = 불명), SSE 행에 재확인 횟수·확인 불가, `version_registry.evaluation_profile` 에 `fields.pipeline`(없으면 legacy)·items_version·quote_policy·recheck_policy, `execution.dispatch`, `criteria_registry.registry()['semantic_items']`(v2), 결과 화면 `semanticEvidence` 의 subs/items 블록, `version-comparison.js knownProfile` 의 pipeline 누락 → legacy 정규화.

## 4. 정할 것 (열린 질문)

- J2-5.b(글이 목적을 수행하는가)는 설계 표에 예시가 없어 구현에서 한 쌍을 새로 썼다 — 확인 필요.
- J3-2·J3-5·J5-1·J5-2.a 의 적용 규칙 단어 목록은 설계 예시 질문 16개로만 고정했다. '뜻·의미' 규칙이 번역 질문도 J5-1 로 넣는다. 사람 판정 일치율(30문항 × 4모델) 뒤 보정.
- J5 참(TRUE) 판정도 관측된 출처 URL 을 요구한다(기억만으로 판정 금지). 검색이 꺼진 설정에서는 J5-1 을 보내지 않는다.
- J6-3.b 적용 시점: 롱 컨텍스트 세트 초안은 "같은 결과물 2회 이상 편집 뒤"로 통일했으나 J6-2/J6-4 초안은 2번째 편집부터, J6-3 초안은 3번째부터 적용 — 사람 검토 때 한쪽으로 맞춘다.
- G-2(줄 수·문장 수 범위 정의)는 공식 정의 변경 승인 대상이라 미결. G-3(이전 턴 형식 지시의 코드 승계)은 채택했으나 구현 단계 미정.
- 외부 답변이 있어도 API 3개 수집을 필수로 둘지, 외부만으로도 실행을 허용할지.
- 정밀 모드는 보류.
