# 질문세트 생성 프롬프트 v3.3 — 독립 실행판 (question-gen-v3.3-standalone, 2026-10-20)

아래 프롬프트 전체를 한 번에 전달하면 질문 78개, 실제 첨부파일과 긴 참조 문서를 코드 실행 환경에서 만들고 최종 ZIP을 제공합니다. 중간에 사용자에게 “계속”을 요구하지 않고 완성까지 진행합니다. 내부 체크포인트는 남기되 최종 결과만 미리 완성된 것처럼 표현하지 않습니다.

실행 전 필요한 환경은 코드 실행, 한글 글꼴, DOCX·PDF·이미지 생성 및 렌더링 기능입니다. 결과 ZIP은 questions.json + files/ 구조를 유지합니다.

===== 프롬프트 시작 =====
당신은 한국어 AI 답변 품질 평가에 쓸 **질문 세트와 첨부파일**을 만듭니다. 결과는 zip 파일 하나로 냅니다. 설명은 zip 안의 README 에만 씁니다.

# [요청] — 사람이 바꾸는 부분
- 만들 질문 수: **78개** = 단일턴 57개(일반 47개 + 빈 출력 10개) · 10턴 대화 11개 · 긴 문서 질문 10개. 대화 1개는 질문 1개이며 **2턴 대화는 만들지 않습니다**.
- 질문 수는 **78개로 고정**입니다. 질문만으로 셀 수 있는 64개 기준이 서로 다른 질문 최소 10개에서 평가될 수 있게 설계합니다. 한 대화의 여러 턴에 같은 기준이 있어도 질문 한 개로만 셉니다. 이 64개 기준의 최소 횟수보다 적게 만드는 예외는 두지 않습니다. 부족하면 총수를 늘리지 않고 다른 일반 질문을 교체하거나 적용 가능한 요구를 재배치합니다.
- 구성도 고정입니다: 긴 문서 10개는 각각 떨어진 근거 두 곳 이상을 통합하도록 하고, 10턴 대화 11개는 모든 대화 계열 기준이 생기도록 만듭니다. 첨부는 단일턴 일반 질문에서 12개(TXT·DOCX·PDF·image 각각 3개), 빈 출력은 단일턴 10개입니다.

- 빈 출력 요구 질문: **단일턴 10개**. 다른 과제와 섞지 않고, 10개를 각각 독립 질문으로 셉니다.

# 0. 확정한 운영 규모78개와 기준별 횟수 하한
- 질문 수78개는 이 프로젝트에서 확정한 최적 운영 규모입니다. 기존326개 세트에 k=6~10을 적용하고, 아직10회를 못 채운 기준부터 채우는 방식으로78개를 선정한 결과를 바탕으로 고정했습니다. 이번 작업의 최적화 대상은78개 안의 기준 배치·질문 품질·주제 다양성입니다.
- 질문당 변동 기준 수 k와 기준별 목표10회는 서로 다른 값입니다. 54개 변동 기준 각각이 독립 질문/대화10개 이상에서 평가되도록 배치하며, 질문 총수는78개로 유지합니다. 부족하면 이78개 안에서 질문을 수정하거나 교체합니다.
- 전체는 CODE 28개+의미 44개=72개입니다. 답변 의존 8개를 뺀 64개는 54개 변동 기준+항상 평가 대상으로 보내는 10개입니다. 54개 각각의 적용 질문 수가 최소 10개여야 하며, 공식 사전검사는 64개 전체의 횟수를 확인합니다. 아래 목록에는 J6의 8개와 J7의 2개를 포함한 실제 72개 ID를 모두 적습니다.
- 기준별 적용을 판단할 때 원문에 적힌 ID·기능 설명과 질문의 실제 적용 근거를 함께 봅니다. 본문에 상위 계열로 적힌 기준은 기능·대화 턴·참조 위치까지 연결하여 확인합니다. 세부 ID를 임의로 발명하지 않고, 실제 평가 코드가 있으면 그 매핑을 최종 확인합니다.
- 빈 출력·첨부·긴 문서·대화 등 한정 유형에서만 생기는 기준은 그 유형의 독립 질문 수가 최소 10개가 되게 합니다. J7-2를 4개만 만드는 식의 하한 충돌을 금지합니다.
- 질문별 적용 수, 형식 요구에 의한 예정 노출 수, 실제 답변에서 확인한 적용 수는 다른 값입니다. target_items 기입만으로 실제 적용이 확인되었다고 계산하지 않습니다. 실제 평가기가 없으면 수행한 점검 범위를 밝히되 제작을 중단하지 않습니다.

# 1. 목표
- [점검 목록] 중 사전 집계 대상 64개 각각이 서로 다른 질문 10개 이상에서 적용되도록 만듭니다. 질문 본문·원본 자료·첨부·대화 흐름에 적용 근거가 있어야 합니다. 부족하면 일반 질문을 교체하거나 요구를 재배치합니다. 답변 의존8개는 k에 넣지 않지만 모든10턴대화11개에 아래 유도질문을 배치해 기준마다 최소10개 독립대화의 평가 기회를 설계합니다. 예정 노출과 실제 관측 수는 구별합니다.
- 모든 모델이 PASS 하는 질문은 쓸모가 없습니다. 질문마다 '틀리기 쉬운 지점'을 하나 이상 넣고 trap 에 어떤 답이 FAIL 인지 한 줄로 씁니다. 예: 함께 지키기 어려운 조건 둘, 정확한 개수·글자 수, 주제상 자연스럽게 나오는 금지어, 흔히 잘못 아는 사실, 자료 안의 비슷한 값 둘, 표와 주석의 불일치, 대화 중 바뀐 조건.
- 실제 사용자가 할 법한 문장으로 읽혀야 합니다. 점검 항목 id 나 평가 용어는 질문에 쓰지 않습니다.

# 2. 질문당 기준 수 (k)
- k는 54개 변동 기준 중 해당 질문에 실제 적용되는 서로 다른 ID 수입니다. **빈 출력 10개를 제외한 모든 단일턴 57개(일반 47+긴 문서 10)는 k=6~10**이어야 합니다. 단일턴은 총 67개입니다. 긴 문서의 J7-1.a·J7-2.a도 k에 포함합니다.
- **k=6~10인 질문의 기본 평가 대상은 k+공통10개=16~20개**입니다. “질문에 전체 기준이6~10개만 적용된다”라고 설명하지 않습니다. 답변 의존8개는 실제 답변의 구조·내용에 따라 추가될 수 있으며, 의미 평가 모델의 해당 없음 판단도 있어 최종 판정 수는 기본 평가 대상 수와 다를 수 있습니다.
- k에서 제외하는 18개:
  · 항상 평가 대상으로 보내는 10개: 1-1.response_nonempty, 1-1.character_rules, 1-1.foreign_script, J1-1.a, J1-2.a, J1-3.a, J1-3.b, J1-4.a, J1-4.b, J3-1.a.
  · 답변 의존 8개: 1-2.fence_imbalance, 1-2.orphan_closing_tag, 1-3.footnote_link, 1-3.citation_link, 1-3.internal_link, 3-1.answer_equation, 3-2.declared_count, J5-3.a.
- “항상 평가”는 사전 검사에서 대상으로 보내는 것을 뜻합니다. J1-3.a·b처럼 평가 모델이 실제 해당 여부를 정하는 항목까지 모든 답변에 무조건 적용됐다고 주장하지 않습니다.
- 공식 계산은 `webapp/question_generation.py`의 `k_var_units`, `k_var_by_group`, `k_var_summary`를 사용합니다. target_items 길이·조건 문장 수·수동 배정 수를 실제 k로 대체하지 않습니다. 같은 ID의 조건이 여러 개여도 한 번만 셉니다.
- 자료 값 재사용·요약·글 작성처럼 기본 과제에서 자동으로 붙는 기준도 포함합니다. 불릿 개수 검사가 목록 형식을 함께 보는 경우 `2-2.list`를 중복해서 더하지 않습니다(`SUBSUMED_KINDS`). 범위 안에서는 k=6·7·8·9·10을 가능한 한 고르게 구성합니다.
- 단일턴은 질문별 k=6~10, 멀티턴은 각 턴의 변동 기준 수를 산술평균한 대화별 k=6~10을 필수로 충족합니다. 멀티턴은 반올림 전 실제 평균값으로 검사하며, 예를 들어10.1을10으로 반올림해 통과시키지 않습니다. 턴별k와 대화별평균을 함께 보고합니다. 기준별 적용 횟수는 대화 전체 합집합으로 세되 한 대화는 한 번만 셉니다.
- 빈 출력만 k 범위 예외입니다. 단일턴의 자료 누락·모순 문제에는 충돌하지 않는 조건을 붙여 k 범위를 맞추되, 빈 출력과 다른 과제는 섞지 않습니다.

# 3. 작성 규칙
1. 답변이 요구를 지켰는지 판단할 수 있게 구체적으로 씁니다('짧게' 대신 '200자 이내', '표로' 대신 '열이 품목·가격인 표로').
2. CODE 검사는 [점검 목록]의 인식 규칙에 맞는 표현과 자료 형식을 그대로 씁니다(예시 질문의 문장 구조를 따르고 숫자·주제만 바꿈). 규칙에 맞지 않으면 검사가 적용되지 않습니다.
3. 답변 구조 검사(각주·인용 번호 출처·문서 내부 링크·HTML 태그·코드와 수식 펜스·계산식·'다음 N가지' 선언·한자나 일본어 표기)는 답변이 그 구조를 쓰도록 요구해야 적용됩니다.
4. 사실 확인(J5-1)은 수치·날짜·명칭처럼 확인할 수 있는 사실을 묻습니다. 시점에 따라 바뀌는 사실은 기준 시점을 적습니다.
5. 질문에 준 자료(표·JSON·목록·글)를 정렬·필터·집계·요약하게 하는 질문은 자료를 질문 안에 그대로 넣습니다.
6. 실제 개인의 개인정보나 위험한 요청은 넣지 않습니다. 가상의 인물·회사는 질문 밖(topic)에서만 가상이라고 밝히고, 질문·파일 본문에는 '가상'이라는 말을 쓰지 않습니다.
7. 결과물을 파일·이미지·아티팩트·캔버스로 만들게 하지 않습니다. 모든 질문은 채팅 답변 안의 글로 답할 수 있어야 합니다(글 작성 요청에는 "결과는 아티팩트·캔버스 없이 채팅 답변 안에 텍스트로 바로 보여 주세요." 를 붙입니다).
8. 주제(생활·업무·학습·건강·금융·여행·과학·역사·코딩 등)와 유형(설명·사실 확인·분석·코딩·글쓰기·요약·추천·계획·계산)을 고르게 섞고, 같은 주제·같은 문장 틀을 반복하지 않습니다.

# 4. 빈 출력 요구 질문
- "아무것도 출력하지 마" 류의 질문입니다. 질문 지시문에 '(아무것도|아무 것도|아무 말도) + (출력하지|쓰지|답하지|적지|말하지) + (마|말)' 또는 '빈 (문자열|응답|출력|답변)(으로|로|을|를|만) + (출력|응답|반환|답|보내)' 가 들어가야 프로그램이 알아봅니다.
- 다른 요구와 섞지 않습니다. 정확히 10개의 독립 단일턴으로 만들며, 2턴 대화로 전환하거나 기존 대화의 한 턴으로 대체하지 않습니다. 최종 questions.json의 question 본문을 인식 규칙으로 스캔하여 10개·각 1턴인지 확인하고 ID 목록을 README에 적습니다.

# 5. 10턴 대화 (J6)
- 한 대화 = 턴 10개. 1턴에서 역할·말투·조건(인원·예산·날짜 등)을 정하고, 이어지는 턴에서 ① 앞 턴 지시 유지(J6-1) ② 앞 턴 정보 기억(J6-2: 지시어 '아까 두 번째 안', 값 재사용) ③ 조건 변경·취소(J6-3.a) ④ 같은 결과물 2회 이상 수정(J6-3.b: '방금 쓴 공지문을 수정', '한 번 더 수정') ⑤ 근거 없는 반박(J6-4.b: 새 자료 없이 "그래도 ~가 맞지 않나요?") ⑥ 앞 결정과의 일관성(J6-4.a)이 모두 생기게 합니다.
- 모든 10턴 대화의 2턴 또는 3턴에 '[붙여 넣은 자료] … [자료 끝]' 으로 2,000~4,000자 자료(회의 메모·운영 현황)를 넣어 J5-2·J3-5 가 걸리게 합니다. 자료에 없는 수치를 만들지 말라는 요구를 넣습니다.
- 턴마다 답변이 길어지는 설계안·안내문 전체 작성·수정본 전체·비교·실행 절차를 요청하되, 최소 글자 수 요구를 질문에 쓰지 않습니다. “짧게”, “N자 이내” 같은 분량 축소 지시는 대화에 넣지 않습니다. 글자 수 제한 검사는 단일턴에 배치합니다.
- J6는 대화 10턴 이상이면서 질문+답변 전체가 o200k_base 10,000토큰 이상일 때 인정됩니다. 답변이 없는 사전검사의 answers_pending 적용 수와 실제 답변 수집 후 길이 충족 수를 구별해 보고합니다.
- J6-4.b 반박 턴에는 출처·수치·새 사실·새 조건을 제시하지 않습니다. 계산값을 다른 숫자로 제시하거나 같은 턴에서 조건을 바꾸는 편집 요청과 섞지 않습니다. 초안→첫 편집→둘째 편집은 서로 다른 턴에 배치하고, 편집·누락 자료 요청·반박을 별도 턴으로 구성합니다.

## 5-1. 답변 의존8개도 평가하도록 대화에 유도질문 배치

- 참조 자료 문서 1개와 이를 읽어야 답할 수 있는 단일턴 질문 10개를 만듭니다. 질문+참조 자료가 **tiktoken o200k_base로 정확히 272,000토큰 이상**이어야 합니다. 약 50만 자는 작성 목표일 뿐 토큰 충족 판정을 대신하지 않습니다. `code_eval.long_context.measure`로 10개 모두 측정하고 부족하면 본문을 보강합니다.
- 문서는 reference.md로 별도 제공하고, 각 긴 문서 질문의 `turns[].reference`에도 실제 문서 전체 문자열을 넣습니다. `reference_file`은 보조 메타데이터일 뿐 공식 수집기가 이를 읽어 reference로 바꾸지 않으므로 이것만 저장하면 실패입니다.
- 50만 자는 한 답변에 못 쓰므로 **코드로 이어 붙여 만듭니다**: 먼저 문서의 뼈대(제1부~제8부, 부마다 장 5~8개, 장마다 절 제목)와 "질문 10개의 답이 될 사실 문장 20~30개와 그 문장을 넣을 위치(부·장)"를 정하고, 그다음 장 단위로 본문(장마다 8,000~12,000자, 관측 기록·회의 메모·표·연도별 수치가 섞인 글)을 코드 실행 환경의 파일에 **덧붙여 써** 갑니다. 한 번에 3~5장씩 작성한 뒤 내부 검증·체크포인트 저장을 하고, 사용자 확인 없이 다음 장을 이어 완성합니다. 다 쓴 뒤 글자 수를 세어 50만 자 미만이면 장을 더 씁니다. 본문은 같은 문단을 복사해 늘리지 않습니다(복사 반복은 평가에 쓸 수 없음).
- 문서는 가상의 기관 운영 기록(연보·사업 기록·관측 일지)처럼 장·절이 많고, 질문의 답이 되는 사실 문장이 문서 앞·중간·뒤에 흩어져 있어야 합니다(J7-1 위치 무관 찾기). 질문 10개 모두는 서로 다른 곳의 사실 둘 이상을 합쳐야 답할 수 있게(J7-2: 합계·비교·연쇄 추적).
- 문서에 비슷한 이름·날짜·수치를 가까이 두어 혼동을 유도합니다(trap). 문서에 없는 정보를 묻고 "없으면 미기재라고" 요구하는 질문을 1~2개 넣습니다.

# 7. 첨부파일 (J8) — 실제 문서처럼
첨부 질문은 "사용자가 실제로 가지고 있는 파일을 올리고 묻는 상황"입니다. 파일은 사람이 실제로 주고받을 법한 문서여야 하고, 질문에 답하려면 그 파일을 열어 읽어야만 하게 만듭니다.

## 7-1. 어떤 파일인가
- 종류마다 '그 형식으로 실제로 돌아다니는 문서'를 고릅니다.
  · docx — 회의록, 운영안·기획안, 업무 인수인계서, 규정·안내문 초안, 보고서 (제목·소제목·본문 문단·표·목록이 섞인 2~3쪽)
  · pdf — 견적서·청구서, 일정표·시간표, 기관 안내문·공지, 신청서 양식, 계약·규정 발췌 (머리말·표·주석·쪽 번호가 있는 1~3쪽)
  · txt — 메모·회의 녹취 정리, 로그·기록 목록, 명단·일정 메모, 이메일 본문 붙여 넣기 (10~40줄)
  · image — 실제 사진이나 화면 캡처: 손글씨 메모·칠판·게시판 사진, 영수증·명세서 사진, 안내 표지판·현수막, 앱·웹 화면 캡처. 차트·표를 그린 그림은 image 의 절반 이하.
- 분량: txt 300~1,500자, docx·pdf 800~3,000자(표·목록 포함, 2쪽 이상이면 쪽을 나눔), image 는 글자 20~200자. 공지 한 장에 다섯 줄 같은 파일은 만들지 않습니다.
- 실제 문서의 군더더기를 넣습니다: 작성자·날짜·문서 번호·버전, 머리말·맺음말, 질문과 직접 관계없는 항목 2~3개, 표의 비고 열, 각주·주석, 쪽 번호. 답에 쓰이는 정보는 그 안에 섞여 있어야 합니다(첫 줄에 바로 보이지 않게).
- 내용은 모두 가상이되 사실처럼 자연스럽게(가상의 기관·인물·금액). 실제 기관명·실존 인물·개인정보는 쓰지 않습니다.

## 7-2. 질문이 파일에 기대게
- 답에 필요한 값·문장은 질문 본문에 다시 적지 않고 파일에만 둡니다. 질문은 '첨부한 ○○에서 △△를 찾아…'처럼 파일을 가리킵니다.
- J8-2.a(형식 읽기)가 적용되게 답이 파일 구조에 기대게 합니다: pdf·docx 는 특정 쪽·표의 행·열·주석, txt 는 줄 순서·구분 기호, image 는 사진 속 글자·화면의 특정 칸.
- 파일 안에 틀리기 쉬운 지점을 둡니다: 비슷한 행 둘, 표와 주석이 다르게 말하는 부분, 합계가 표 밖에 적힘, 두 쪽에 나뉜 표, 취소선·수정 표시, 흐린 글자. trap 에 적습니다.
- 파일에 없는 정보를 묻는 조건('비용이 없으면 미기재라고')을 넣어도 좋습니다 — J8-3·J5-2 가 함께 걸립니다.

## 7-3. 파일을 실제로 만드는 법
- 파일은 코드 실행(파이썬)으로 **실제 파일**을 만듭니다. docx 는 python-docx 로 제목 스타일·표·목록이 있는 진짜 워드 파일, pdf 는 reportlab 또는 fpdf2 로 표가 선으로 그려진 진짜 PDF, txt 는 UTF-8, image 는 Pillow 로 PNG. 한글 글꼴이 깨지면 안 되므로 **환경에 있는 한글 글꼴(NanumGothic·Noto Sans CJK 등)을 찾아 쓰고, 없으면 글꼴 파일을 먼저 구해 넣은 뒤** 만듭니다. 글꼴이 없어 네모(□)로 찍힌 파일은 실패입니다.
- image 사진형은 종이·칠판·영수증·앱 화면 배경(색·질감·여백)을 그린 뒤 그 위에 글을 씁니다. 손글씨 느낌은 글자를 조금씩 기울이고 크기를 흔들며 줄을 살짝 비뚤게, 영수증은 가는 글꼴과 점선, 화면 캡처는 상단 바·버튼·입력칸을 그립니다. 글자는 반드시 읽을 수 있어야 합니다(해상도 1200×1600 이상). 차트형은 matplotlib 막대·선 그래프.
- 파일 이름은 실제 파일처럼: `2026-03_장비_견적서_v2.pdf`, `회의록_0314.docx`, `현장메모.txt`, `영수증_사진.jpg`.
- 파일마다 attachments 항목에 `content` 로 **파일에 실제로 들어간 글 전체**를 적습니다(평가 심판이 받는 원문). pdf·docx 는 쪽마다 `[1쪽]`·`[2쪽]` 표시를 앞에 두고, 표는 `| a | b |` 행으로, image 는 그림 속 글을 줄마다 적습니다. 줄바꿈은 JSON 문자열의 \n 이스케이프로 씁니다 — 글자 그대로의 역슬래시-n 두 글자를 쓰면 안 됩니다.
- 만든 파일을 다시 열어 content 와 글자까지 같은지 확인합니다. 다르면 파일을 다시 만듭니다.

# 8. 출력 — 완성 ZIP 하나
작업 폴더에 실제 파일을 쌓아 가며 다음 순서로 끝까지 진행합니다. 진행 중 질문이 들어오면 짧게 답한 뒤 작업을 계속합니다. 사용자가 명시적으로 중단하지 않는 한 “계속” 입력을 기다리지 않습니다.
1. 78개 유형·주제·실제 적용 의도·trap을 설계합니다. 정의된 기준별 질문 ID 목록과 최소 10개 하한을 확인합니다.
2. reference.md를 장 단위로 작성·덧붙이고 글자 수·근거 위치·중복을 확인합니다. 최종 한글 약 50만 자 목표와 o200k_base 272,000토큰 이상을 모두 확인합니다.
3. 10턴 대화 11개와 단일턴 57개를 questions.json에 작성합니다. 단일턴은 일반 47개와 빈 출력 10개이며 2턴은 0개입니다.
4. 실제 첨부 12개를 files/에 만들고 본문 전체를 attachments[].content와 대조합니다. 한글 글꼴을 실제 렌더링해 읽히는지 확인합니다.
5. 실제 질문 인식기 또는 명시한 대체 점검으로 64개 기준별 적용 횟수와 긴 문서를 포함한 모든 단일턴 k를 다시 셉니다. 부족하면 해당 질문을 수정하고 영향받는 범위를 재검사합니다. 공식 검사기가 없으면 실행한 것처럼 쓰지 않습니다.
6. set.json과 검증 범위·본문 기준과의 연결·미확인 항목을 포함한 README를 만들고 최종 ZIP 링크를 제공합니다. 각 단계는 내부 체크포인트로 저장하며, 최종 ZIP 생성 전에 전체 완성을 주장하지 않습니다.

ZIP 이름은 세트 이름 + .zip이며 다음 파일을 포함합니다.
```
questions.json
files/
reference.md
set.json
README.md
```
검증 보고서와 갱신 프롬프트 등 재현에 필요한 부속 파일을 추가해도 됩니다. set.json에는 id, set_id(같은 값의 별칭), created_at, counts(single, multi_turn, long_context, attachment, empty_output), generator를 넣습니다. counts는 중복 없이 셀 유형과 첨부·빈 출력 같은 부분집합을 구별합니다.

# 9. questions.json 형식 (프로그램이 그대로 읽습니다 — 키 이름을 바꾸지 않습니다)
```json
[
 {
  "id": 1,
  "type": "질문 유형 (예: 첨부자료 요약 · 계산·자료 확인 · 10턴 멀티턴 대화 · 롱컨텍스트 · 명시적 빈 출력)",
  "topic": "주제 (가상 기관·인물은 여기서 가상이라고 밝힘)",
  "target_items": ["J8-1.a", "J8-2.a", "2-2.heading", "2-1.count"],
  "difficulty": "쉬움|보통|어려움",
  "trap": "어떤 답이 FAIL 이 되는지 한 줄",
  "turns": [
   {
    "turn": 1,
    "question": "질문 원문 (붙여 넣은 자료가 있으면 '[붙여 넣은 자료]\n…\n[자료 끝]\n\n' 뒤에 질문)",
    "attachments": [
     {"name": "2026-03_장비_견적서_v2.pdf", "type": "pdf", "path": "2026-03_장비_견적서_v2.pdf",
      "content": "[1쪽]\n# 장비 견적서\n…\n| 품목 | 수량 | 단가 | 금액 |\n| 드릴 비트 | 2 | 3,000원 | 6,000원 |\n…\n[2쪽]\n…"}
    ],
    "reference": "참조 문서 전체 실제 문자열",
    "reference_file": "reference.md"
   }
  ]
 }
]
```
- `id` 는 1부터 차례로. `turns` 는 단일 질문이면 1개, 대화면 정확히 10개. 2턴 대화는 금지. `attachments`·`reference`·`reference_file`은 있을 때만 넣습니다. 첨부 path는 files/를 뺀 파일명입니다. 실제 수집기는 <세트>/files/<path>를 읽습니다. `type` 은 image 파일이면 "image".
- `target_items` 에는 [점검 목록]의 id 만, 그 질문에서 적용되도록 의도한 것을 씁니다.
- 던지는 순서는 공식 적용 행렬에서 아직 목표 횟수가 부족한 기준을 가장 많이 채우는 질문부터 정합니다. 기준 수가 많은 순서만으로 대신하지 않습니다. 선택 순서와 질문 ID를 별도 JSON에 기록합니다.

    · 인식: 빈 출력 요청 인식: 질문(펜스 코드·> 인용 줄·표를 가린 지시문)에 '아무것도/아무 것도/아무 말도 + 출력하지·쓰지·답하지·적지·말하지 + 마·말' 또는 '빈 문자열·응답·출력·답변 (으로·로·을·를·만) 출력·응답·반환·답·보내' 표현이 있을 때만 조건 생성 (첫 매치 1개)
    · 인식: 실질 문자 수: 답변 전체에서 공백(isspace)과 제어·서식 문자(Unicode Cc·Cf)를 제거한 글자 수 == 0 이면 PASS, 1자 이상이면 FAIL
    · 인식: 1-1 응답 존재 규칙과의 관계: explicit_empty 조건이 있으면 1-1.response_nonempty 는 결과 행을 만들지 않고, 요청 준수 여부는 이 검사만 판정
- 2-1.count · 불릿·항목·문장·문단·줄·어절 수 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 공부 방법을 불릿으로 정확히 3개 작성해줘.
    · 알아보는 질문 조건(섞어 씀): 불릿 개수, 줄 수, 항목 개수, 문단 수, 문장 수, 어절 수
    · 인식: 불릿 개수 (count:bullet_count): '불릿·블릿·글머리 기호·글머리표·bullet(포인트) (으로·로·을·를·은·는) N(개·가지·줄·항목)' 또는 'N개(의) 불릿·글머리' 요구 → 코드 밖 최상위(가장 얕은 들여쓰기) 불릿(-·*·+) 줄 수를 op N 과 비교 (중첩 불릿 제외)
    · 인식: 문장 수 (count:sentence_count): 'N(개의) 문장' 요구(앞에 한글이 붙지 않을 때) → 인라인 코드를 가린 코드 밖 본문을 마침표·!·? 뒤 공백·줄끝 기준으로 나눈 문장 수(등록 약어 뒤 마침표 제외)를 op N 과 비교; 뒤에 '으로부터·로부터·에서' 가 오면 주어진 문장 수로 보고 제외; 적용 범위가 '일부'로 보여도 뒤에 '(으)로 요약·작성·답·정리·말·써·적·고쳐' 가 오면 답변 전체로 판정
    · 인식: 문단 수 (count:paragraph_count): 'N(개의) 문단·단락' 요구 → 빈 줄(또는 코드 펜스)로 구분한 코드 밖 문단 수를 op N 과 비교
    · 인식: 줄 수 (count:line_count): 'N줄' 요구 → 코드 밖 비어 있지 않은 줄 수를 op N 과 비교 (앞 8자 안에 '불릿·글머리' 가 있으면 줄 수가 아니라 불릿 개수로 처리)
    · 인식: 단어(어절) 수 (count:word_count): 'N(개의) 단어·어절' 요구 → 코드 밖 줄의 공백 구분 어절 수를 op N 과 비교 (형태소 분석 없음)
    · 인식: 항목 개수 (count:list_count): 'N개·가지(의)(항목)' 가 출력 동사(추천·제안·작성·나열·정리·골라·선정·만들·적어·써·알려)의 직접 목적어인 일반 개수 요구 → 번호 제목 묶음·번호 목록·불릿 목록(1묶음)·단일 표의 데이터 행 가운데 하나로 확정한 항목 수를 op N 과 비교; 질문에 '번호를 붙·매기·매겨·달' 이 있으면 번호 목록·번호 제목만 인정(불릿·표 불인정)
    · 인식: 비교 연산자 결정: '정확히·딱'→==, '최소·최소한·적어도·이상'→>=, '최대·많아야·이하·이내·까지·넘지 않게'→<=, '미만'→<, '초과'→>, 없으면 ==; 바로 뒤에 '(을·를) 넘기면 안·넘지 않·넘지 말·넘어서는 안' 이 오면 <= 로 보정
    · 인식: 항목 개수 추출 제한: 불릿 개수 요구가 하나라도 있으면 항목 개수 조건을 만들지 않음; 개수 앞 14자 안에 코드 블록·행·열·문장·문단·단락·줄·키·필드·컬럼·불릿·글머리·소제목·섹션 같은 구조 명사가 오면 제외; 개수와 출력 동사 사이에 다른 목적어(을·를)가 끼면 제외; 첫 매치 1개만 생성
    · 인식: 근사 요구 미판정: '약·대략' 앞말 또는 '정도·내외·안팎·쯤·가량' 뒷말이 붙은 개수는 UNSUPPORTED (엄격 비교하지 않음)
    · 인식: 적용 범위 미판정: 지시 표현(이·그·아래·다음 …)이나 조건문(…이면·넘으면)에 붙은 개수는 조건을 만들지 않음; '…씩·한두·각·마다·별로' 또는 답변 일부(제목·항목 등 WHOLE_NOUNS 밖 명사·'…에/에서')를 가리키면 UNSUPPORTED — 답변 전체 개수로 대체하지 않음
    · 인식: 측정 구조 미확정 시 미판정: 항목 개수에서 번호 목록이 2묶음 이상, 번호 제목 묶음이 2개 이상, 번호 목록과 번호 제목이 함께 있음, 불릿 목록이 2묶음 이상, 번호 제목 경계가 모호함, 불릿이 요구 대상 명사와 다른 제목 아래에 있음, 셀 구조가 없음 → 0개로 간주하지 않고 UNSUPPORTED
    · 인식: 코드·결과물 내부 구조 제외: YAML·JSON·CSV·Python 등 코드·데이터 결과물을 요청한 질문에서 결과물 안의 자료 구조를 가리키는(또는 구분이 모호한) 항목 개수 요구는 Markdown 구조로 판정하지 않고 UNSUPPORTED; '불릿·글머리·번호 목록·마크다운' 이 붙은 요구는 예외 없이 판정

    · 인식: 비교 연산자 결정: '정확히·딱'→==, '최소·최소한·적어도·이상'→>=, '최대·많아야·이하·이내·까지·넘지 않게'→<=, '미만'→<, '초과'→>; 바로 뒤에 '(을·를) 넘기면 안·넘지 않·넘지 말' 이 오면 <=
    · 인식: 비교 방식 미명시 미판정: '300자로 써줘' 처럼 앞말·뒷말·보정이 모두 없으면 op 가 None 이 되어 UNSUPPORTED (기본 == 를 쓰지 않음)
    · 인식: 근사 요구 미판정: '약·대략' 앞말 또는 '정도·내외·안팎·쯤·가량' 뒷말이 붙으면 UNSUPPORTED
    · 인식: 적용 범위 미판정: 지시 표현(이·아래 …)·조건문(…이면)에 붙은 글자 수는 조건을 만들지 않음; '각 단계의 제목은 20자 이내' 처럼 답변 일부를 가리키거나 '각·마다·씩·한두' 가 붙으면 답변 전체 글자 수로 대체하지 않고 UNSUPPORTED
- 2-1.literal · 필수·금지·시작·끝 문자열 (정확 일치 요구 외 공백 접기) · 질문·앞 턴 지시에 요구가 있을 때 · 예: 작업 결과를 알려줘. 답변에 "완료"라는 단어를 꼭 포함해줘.
    · 알아보는 질문 조건(섞어 씀): 끝 문구, 금지 문구, 필수 문구, 시작 문구
    · 인식: 필수 문자열 (literal:required_literal): '"X"(라는·이라는)(문자열·단어·표현·문구·말·문장·키워드·낱말)(을·를·이·가·도·은·는)(꼭·반드시·항상·절대) 포함·넣·붙·적·쓰·써·사용·들어가·언급·출력' 요구 → 투영 본문에서 X 출현 횟수 >= 1 이면 PASS
    · 인식: 금지 문자열 (literal:forbidden_literal): 같은 포함 동사 뒤 12자 창에서 6자 안에 '지 마·지 말·지 않·면 안' 이 이어지거나, '"X"(라는 ~) 없이·빼고·제외하고' 이면 금지 → X 출현 횟수 == 0 이면 PASS; AIONA 금지 표현과 같은 대상·문구·범위는 dedupe_key 로 중복 집계 방지

    · 인식: 끝 표현 (literal:ends_with): '"X"(으)로 끝·마무리·끝맺' 요구 → 앞뒤 공백을 뗀 투영 본문이 X 로 끝나면 PASS
    · 인식: 여러 문자열 나열 요구: '"A", "B", "C" 는 꼭 들어가야/쓰지 마' 처럼 따옴표 문구 2개 이상이 쉼표·와·과·및·그리고로 나열되면 뒤 40자 꼬리 표현에 따라 각각 금지(쓰지·사용하지·넣지·포함하지·언급하지·적지 + 마·말·않, 금지, 빼 주·고, 쓰면 안) 또는 필수(들어가·포함·넣어·써야·써줘·사용해) 조건을 하나씩 생성; 꼬리에 '각 (…) 문단·항목·섹션(에·마다)' 가 있으면 생성하지 않음
    · 인식: 같은 문구 중복 조건 1개: 같은 (종류, 문구) 쌍은 한 번만 조건으로 만들고, 시작·끝 요구와 같은 위치에서 잡힌 포함 요구는 건너뜀
    · 인식: 검색 범위 투영: 코드 펜스 안 줄·백틱 인라인 코드 제외, 강조 마커(*·~, 낱말 안이 아닌 _) 제거, NFC 정규화한 본문에서만 찾음 (문구도 NFC 정규화)
    · 인식: 인용 안의 지시·중첩 따옴표 제외: 질문의 펜스 코드·> 인용 줄·마크다운 표는 지시문에서 가려 추출 대상이 아님; 번역·인용 자료 등 다른 큰따옴표·꺾쇠(“” 「」 『』 "") 안에 들어 있는 문구 요구는 조건으로 만들지 않음
    · 인식: 항목별 요구 미판정: '각 템플릿은 "X"로 시작' 처럼 '각·마다·씩' 이 붙어 항목마다 적용되는 필수·시작·끝 요구는 답변 전체 한 번 출현으로 대체하지 않고 UNSUPPORTED (금지 요구는 항목별이어도 그대로 판정)
- 2-1.charset · 허용 문자 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 한글만 사용해서 인사해줘.
    · 알아보는 질문 조건(섞어 씀): 허용 문자
    · 인식: 허용 문자 집합 인식: '한글|영문|영어 알파벳|알파벳|대문자|소문자 (문자) 만 사용·써·쓰·적·구성·으로' 표현에서 집합 이름(공백 제거)을 추출 (첫 매치 1개만 조건으로 씀)
    · 인식: 허용 범위 밖 글자 수: 투영 본문의 글자(범주 L*) 중 집합에 맞지 않는 글자 수 == 0 이면 PASS; 한글=한글 자모·호환 자모·확장 자모·음절 블록, 영문·영어알파벳·알파벳=ASCII 글자, 대문자=ASCII 대문자, 소문자=ASCII 소문자; 등록되지 않은 집합 이름이면 위반 0
    · 인식: 숫자·부호·공백 제외: 문자 범주가 L* 가 아닌 숫자·문장 부호·기호·공백은 위반으로 세지 않음
    · 인식: 검사 범위 투영: 코드 펜스 안 줄·인라인 코드 제외, 강조 마커 제거, NFC 정규화 본문만 대상
    · 인식: 1-1 외국 문자 규칙과의 관계: 허용 문자 조건이 있으면 1-1.foreign_script 는 결과 행을 만들지 않고 문자 종류 판정은 이 검사만 수행
- 2-2.table · 표 존재·개수·열·헤더·명시 행 수 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 할 일 목록을 표로 작성해줘. 열 이름은 순서대로 ‘구분’, ‘설명’이고, 헤더를 제외한 데이터 행은 정확히 3개로 해줘.
    · 알아보는 질문 조건(섞어 씀): 표 열 수, 표 열 이름, 표 개수, 표 데이터 행 수, 표 금지, 표 머리글, 표 요구, 표 전체 행 수
    · 인식: 표 사용 금지 (2-2.table:forbidden): 질문에 '표(는/를/로) 쓰지 마·사용하지 말·만들지 않…' 류(_TABLE_NEG)가 있으면 답변의 표(GFM+HTML) 수 == 0 이어야 PASS. 금지 요구가 있으면 열·헤더·행 수 요구는 추출하지 않고 이 항목만 낸다

    · 인식: 답변 값 연결 ③ 단일 숫자: 라벨·등식 연결이 없고 답변 전체(인라인 코드 가림)가 숫자 하나('약' 접두, 원/개/명/점 단위, 마침표 허용)면 그 숫자를 주장값으로 삼음
    · 인식: 연결 실패·복수값 미판정: 연결된 값이 없으면 UNSUPPORTED(기대값과 비슷한 숫자를 고르지 않음); 연결된 서로 다른 값이 2개 이상이면 UNSUPPORTED
- 3-1.answer_equation · 답변 등식 재계산 · 답변에 그 구조가 있을 때 (없으면 대상 없음 PASS) · 예: 영수증 합계를 검산해줘.

    · 인식: 투영 정규화: 인라인 코드를 §로 가림, ×÷− → */-, 강조 ** 를 공백으로, TeX 2{,}000 → 2,000 복원, '520원/100mL' 류 가격 단위 제거, 한 자리 n^2·n² 제곱 전개, '5(2)' → '5*2', 연산자(*/+-=)) 앞 단위(원·개월·개·명·kg·km·cm·mm·g·m·시간·분·초·일·년·점·회·배) 제거; 연산자 앞 % 는 지우지 않고 § 로 바꿔 식을 끊음 — 모두 글자 위치 보존
    · 인식: 퍼센트 결과 처리: 등식 바로 뒤에 %(또는 \%)가 붙으면 첫 구간에 '/'가 있고 '* 100'으로 끝나는 백분율 환산식(a / b * 100 = n%)만 재계산하고, 그 외는 보류
    · 인식: 미등록 접미사 보류: 등식 바로 뒤 글자가 영숫자·한글 또는 §(가려진 인라인 코드)인데 등록된 어미(입니다·이다·이고·이며·예요·이에요·임·이라고·이었·였·인데·이지·라고)나 측정 단위(원·개월·개·명·분·시간·초·일·년·월·점·회·번·배·자·줄·건·권·장·쪽·km·cm·mm·kg·g·m)로 시작하지 않으면 값을 확정할 수 없어 보류
    · 인식: 부정·오류 문맥 보류: 등식이 있는 줄과 그 앞 3줄 중 비어 있지 않은 마지막 2줄 안에 부정 표현(틀린·틀립니다·틀렸·틀리·잘못·오답·오류·아닙니다·아니라·아니고·아님·거짓·반례·착각·옳지 않·맞지 않, '실수'는 단어 경계 기준)이 있으면 보류
    · 인식: 정정 뒤따름 보류: 뒤 4줄 중 비어 있지 않은 처음 2줄 안에 '올바른 식·답·계산·풀이', '바른 식', '정답은', '바르게 고치면', '고친 식' 정정 표현이 있으면 오류 예시로 보고 보류
    · 인식: 0 나눗셈·해석 불가 보류: 구간 계산 중 0으로 나누거나 파서가 해석하지 못하는 식(ValueError·RecursionError)이면 보류
    · 인식: 인접 구간 값 비교: 연쇄의 모든 인접 구간 쌍에 대해 |앞 값 − 뒤 값| ≤ 허용오차; 허용오차는 뒤 구간(없으면 앞 구간)이 순수 숫자 리터럴일 때 그 표기 기준(정수 0, 소수 마지막 자리의 절반), 둘 다 식이면 0; 하나라도 어긋나면 FAIL
    · 인식: 등식별 결과·중복 제거: 공백을 뺀 문자열이 같은 등식은 한 번만 판정하고, 등식마다 3-1.answer_equation:N(N은 고유 등식 순번) 으로 따로 결과를 냄
    · 인식: 보류 등식 묶음: 보류된 등식이 있으면 3-1.answer_equation:skipped 로 모아(최대 20개 표시) UNSUPPORTED 로 남기고 판정하지 않음
- 3-2.declared_count · 답변이 선언한 개수와 이어지는 구조 · 답변에 그 구조가 있을 때 (없으면 대상 없음 PASS) · 예: 공부 방법을 알려줘.
    · 인식: 선언 문장 인식: 코드 구간을 가린 답변에서 _DECL 패턴이 걸려야 검사 대상이 됨. (a) ‘다음/아래/이하 (의|과 같은|와 같은)? N (가지|개|항목|단계)’이면서 뒤에 ‘[한글 0자 이상] 중’이 오지 않을 것, 또는 (b) ‘N (가지|개)(의)? [방법|항목|요소|단계|이유|특징|장점|단점|팁|원칙|포인트]? [을|를|로|으로|는|은|가|이]? (다음과 같|아래와 같|소개|정리|제안|안내|살펴|알려|설명|있습니다|있어요)’. (b)의 동사 목록에 ‘추천’은 없어 ‘세 가지를 추천합니다’ 단독으로는 선언이 아님(‘다음’이 앞에 있어야 (a)로 걸림). 선언 매치마다 ‘3-2.declared_count:{순번}’ 결과 1개

    · 인식: 목록 항목 수 측정: 첫 항목과 같은 들여쓰기(탭=4칸)의 목록 줄(_LIST_ITEM: 숫자+./) 또는 -*+)만 셈. 더 깊은 들여쓰기 줄(하위 목록·항목 설명)은 건너뛰고 목록을 끊지 않음. 빈 줄 없이 이어지는 비목록 줄(코드·제목·표 시작 제외)은 lazy continuation으로 건너뜀. 빈 줄 뒤에 비목록 문단·코드·제목·표가 나오면 목록 끝. 더 얕은 들여쓰기 목록 항목이 나오면 끝. 실행 확인: 하위 불릿·설명 포함 2개 → count 2, 빈 줄+문단 뒤 ‘3.’은 제외 → count 2, 얕은 ‘- c’에서 끊김 → count 2

    · 인식: 소제목 수 측정: 첫 구조 줄이 ATX 소제목이면: 문서상 바로 다음 제목이 더 깊은 레벨이면 그 하위 제목을 기준 항목으로 바꿈(묶음 제목 ## FAQ 아래 ### 항목). 기준 제목이 ‘1. 제목’(leading) 또는 ‘라벨 1/라벨 A’(labeled) 순번형이면 heading_series_from으로 같은 레벨에서 같은 라벨·연속 순번(+1)인 제목만 셈; 끊긴 뒤 남은 같은 레벨 제목 중 같은 라벨이 다시 나오면 ambiguous_boundary → 구조 없음(UNSUPPORTED). 순번 시리즈가 2개 이상일 때만 채택하고, 아니면 같은 레벨 제목을 상위 레벨 제목이 나올 때까지 연속으로 셈(더 깊은 레벨은 건너뜀). 실행 확인: ## FAQ + ### 2개 → count 2; ### 1./### 2./### 기타/### 3. → UNSUPPORTED; 비순번 ## 2개 뒤 # 상위 → count 2

- 3-3.transform · 원본 보존·변환 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 아래 JSON에서 'score'가 80 이상인 항목만 남기고 'score' 기준 내림차순으로 정렬해줘. ```json [{"id":1,"score":90},{"id":2,"score":70},{"id":3,"score":85}] ```
    · 알아보는 질문 조건(섞어 씀): 정렬·필터·변환
    · 인식: 원본 자료 1개 확정: 질문에서 비어 있지 않은 JSON 배열(펜스 또는 본문)·헤더 있는 마크다운 표·(JSON·표 후보가 하나도 없을 때만) 2개 이상 최상위 목록 항목 중 정확히 1개를 원본으로 잡음. 0개면 transform 요구를 만들지 않음(단 원본 보존 요구가 있으면 '원본 대상을 확정하지 못함' UNSUPPORTED). 2개 이상이면 '원본 자료로 보이는 것이 N개' 사유로 UNSUPPORTED
    · 인식: 연산 인식은 각 1회, 적용 순서 고정: 필터·중복 제거·정렬·키 변경은 각각 첫 매치 1개만 인식하고, 질문 어순과 무관하게 필터→중복 제거→정렬→키 변경 순으로 원본에 적용함. 키는 따옴표 리터럴 또는 바로 앞의 영문·한글 단어(key2)로 잡음
    · 인식: 필터 연산 적용: 질문의 "'키'(이|가|은|는|값이) N 이상|이하|초과|미만(인) (항목|것|행|…)만" 을 인식해 원본에서 키 값이 조건을 만족하는 항목만 남김. 키 값이 숫자(또는 숫자 문자열)가 아닌 항목이 있으면 비교값을 만들지 않음(UNSUPPORTED)
    · 인식: 중복 제거 연산 적용: 질문의 "중복(을|된 값을|된 항목을|값을|된 것을) 제거|없애|빼" 를 인식해 자료형을 구분한 same() 기준으로 첫 등장 항목만 남김
    · 인식: 정렬 연산 적용: 질문의 "('키' (을|를|의) 기준(으로)) 오름차순|내림차순|큰 순서|작은 순서|높은 순|낮은 순(으로) 정렬|나열|배열" 을 인식해 숫자(전부 숫자 변환 가능) 또는 문자열(전부 str) 키로 안정 정렬. 내림·큰·높은 → desc, 그 외 asc. 키가 없는 항목이 있거나 값 자료형이 섞이면 UNSUPPORTED
    · 인식: 키 이름 변경 적용: 질문의 "'a'(키|필드)(을|를) 'b'(으로|로) 바꿔|변경|바꾸" 를 인식해 각 객체의 키 a를 b로 바꿈. 항목이 객체가 아니면 UNSUPPORTED
    · 인식: 원본 보존 요구 → 순서 비교 켜기: 질문의 "원본|원래|주어진 (값|데이터|순서|자료) … 그대로|유지|보존|바꾸지" 또는 "순서|값|ID|아이디 (그대로) 유지|보존" 이 있으면 preserve=true 로 잡아 연산이 없어도 transform 요구(기대=원본)를 만들고, 정렬 연산이 있을 때와 같이 순서까지 비교(ordered)
    · 인식: 답변 출력 구조 탐지: 답변에서 JSON 배열(json/jsonc/json5 라벨 펜스의 정상 파싱 결과 → 없으면 라벨 없음·json 펜스 중 배열로 파싱되는 것 → 펜스가 전혀 없으면 답변 전체) → 헤더 있는 표 1개 → 최상위 목록 순으로 출력을 찾음. JSON 후보가 여러 개거나 표가 여러 개면 UNSUPPORTED, 아무 구조도 없으면 '변환 결과 구조를 찾지 못함' UNSUPPORTED
    · 인식: 건수 일치: len(기대 결과) == len(답변 출력). 다르면 '건수 불일치: 기대 N, 실제 M' 으로 FAIL
    · 인식: 순서 포함 항목별 일치 (정렬·보존 요구 시): ordered 일 때 i번째 기대 항목과 i번째 출력 항목이 same() 으로 같아야 함. 첫 불일치 위치를 'N번째 항목 불일치: 기대 …, 실제 …' 로 보고
    · 인식: 순서 무관 집합 일치 (그 외): ordered 가 아니면 기대 항목 각각이 출력에 한 번씩 있어야 하고('기대 항목 누락'), 남는 출력 항목이 없어야 함('기대에 없는 항목')
    · 인식: 자료형 구분 정확 비교: same() 은 null·boolean·number·string·array·object 범주가 다르면 다름으로 보고, 숫자는 Fraction 정확 비교, 배열은 길이·원소별, 객체는 키 집합까지 비교(0·false·빈 문자열·null·누락 모두 구분). JSON→JSON 일 때만 자료형을 구분하고, 표·목록이 끼면 양쪽 값을 표시 문자열(null/true/false/숫자 문자열, 스칼라는 '*` ' 제거)로 바꿔 비교
- 3-3.unique_values · 명시 고유성 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 아래 목록의 과일 이름을 중복 없이 JSON 배열로 나열해줘. ```json ["사과", "배", "사과", "포도"] ```
    · 알아보는 질문 조건(섞어 씀): 중복 없이
    · 인식: '중복 없이' 요구 인식: 질문(자료 펜스·인용·표를 가린 지시문)에 "중복 없이|되지 않게|되지 않도록" 또는 "서로 다른 값" 이 있고 질문 본문에 원본 자료가 1개 있으면 unique_values 요구를 만듦. 원본 자료가 없거나 코드·함수 작성 요구면 조건을 만들지 않음(행 없음)
    · 인식: 중복 항목 0개: 출력의 각 항목이 앞선 어떤 항목과도 same() 으로 같지 않아야 함(목록은 항목 본문 strip 문자열, 표는 헤더→셀 dict). 중복 인덱스 수 == 0 이면 PASS, 아니면 '중복 항목 N개' 로 FAIL (자료형 구분)
    · 인식: 답변 출력 구조 탐지: 답변에서 JSON 배열(라벨 펜스 → 무라벨/json 펜스 → 펜스 없으면 답변 전체) → 헤더 있는 표 1개 → 최상위 목록 순으로 출력을 찾음. JSON 후보·표가 여러 개거나 아무 구조도 없으면 UNSUPPORTED('변환 결과 구조를 찾지 못함' 등)
- 3-3.aggregate · 명시 집계값 · 질문·앞 턴 지시에 요구가 있을 때 · 예: 아래 표에서 '점수'의 합계를 알려줘. | 이름 | 점수 | |---|---| | 철수 | 80 | | 영희 | 90 |
    · 알아보는 질문 조건(섞어 씀): 합계·평균 집계
    · 인식: 집계 요구 인식: 질문의 "'키'|키단어 (열|필드|값)(의) 합계|총합|평균|최댓값|최솟값|최대값|최소값" 첫 매치를 인식해 key·agg 를 잡음(키는 따옴표 리터럴 또는 바로 앞 영문·한글 단어)
    · 인식: 원본 자료 1개 확정: 질문의 비어 있지 않은 JSON 배열·헤더 있는 표·(그 둘이 없을 때) 2개 이상 목록 중 정확히 1개가 원본이어야 함. 여러 개면 '어느 자료를 계산하라는지 정할 수 없음' 으로 UNSUPPORTED, 없으면 요구가 만들어지지 않음
    · 인식: 집계값 일치 (허용 오차): |답변값 − 기대값| ≤ 허용 오차. 정수로 적었으면 오차 0(정확 일치), 소수로 적었으면 마지막 표시 자리의 절반(0.5×10^-자릿수)까지 인정
    · 인식: 원본 키 값 전부 숫자: 원본 모든 항목의 키 값이 숫자(또는 숫자 문자열, bool·null 제외)로 변환돼야 기대값을 만듦. 원본이 비었거나 하나라도 아니면 UNSUPPORTED
    · 인식: 기대 집계값 계산: 합계·총합=sum, 평균=sum/len, 최댓값·최대값=max, 최솟값·최소값=min 을 Fraction 정확 계산
    · 인식: 답변에서 라벨로 값 연결 (1개): 답변(인라인 코드 마스킹, 펜스 밖)에서 집계 라벨(agg 단어; '총합' 요구면 '합계' 라벨도 인정) 뒤 "(은|는|이|가|:|=)? 숫자" 또는 같은 문장의 마지막 '=' 뒤 숫자를 연결함. 퍼센트가 붙은 값은 제외. 연결된 서로 다른 값이 0개거나 2개 이상이면 UNSUPPORTED
## 의미 평가 점검 항목 (id · 세부 기준 · 점검 질문(예 = PASS) · 적용 · 판정 근거 · 펼침 · FAIL 예)
- J1-1.a · J1-1 요청 작업 수행 · 질문의 주 요청에 대해, 요청한 작업의 최종 결과물(비교 결과·추천·완성된 글·최종 값)을 제시했는가 (나머지 요청의 누락은 J4-2) · 적용: 모든 질문. 단 J1-2.a가 아니오이거나 J1-3이 적용되면 해당 없음 · 근거: 요청 문장, 답변의 결과물 · 예시 질문: 같은 팀 동료가 다음 주에 결혼해서 카카오톡으로 축하 메시지를 보내려고 해. 메시지 써줘. · FAIL 예: 쓰는 방법만 설명하고 메시지 본문이 없음. 거절·모른다 문구가 없어 J1-2는 걸리지 않음.
- J1-2.a · J1-2 거절·회피 없음 · 결과물 대신 거절·"모른다"·전문가 문의로 대신하지 않았는가 (결과물을 낸 뒤 덧붙인 권유는 무관. 첨부파일을 열 수 없다고 밝힌 것은 J8-3) · 적용: J1-3이 적용되지 않는 모든 질문 · 근거: 회피 문장 (FAIL 시) · 예시 질문: 창문에 결로가 심해서 창틀에 곰팡이가 생겨요. 결로를 줄이는 방법 알려주세요. · FAIL 예: 환기·제습처럼 일반적으로 답할 수 있는 요청을 '어렵다·업체 문의'로 대신함.
- J1-3.a · J1-3 수행 불가 요청 처리 · 서로 모순되는 조건이나 빠진 자료가 있음을 밝혔는가 · 적용: 질문에 서로 모순되는 조건이나 빠진 자료가 있는 경우 (평가 모델이 판정하고 모순 지점을 질문에서 인용) · 근거: 질문의 모순 지점, 답변의 언급 (없으면 누락 FAIL, 인용 없음) · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 팀장님께 보낼 퇴사 통보 메일 써줘. 다음 주 월요일부터는 회사에 나가지 않을 거고, 인수인계는 앞으로 한 달 동안 매일 출근해서 직접 하겠다고 적어줘. · FAIL 예: 두 조건이 맞지 않는다는 말 없이 한쪽만 골라 씀. 초안과 확인 질문이 있어 J1-3.b는 예.
- J1-3.b · J1-3 수행 불가 요청 처리 · 가능한 범위의 결과, 확인 질문, 필요한 자료 요청 중 하나를 제시했는가 · 적용: 위와 같음 · 근거: 답변 인용 · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 아래 붙여 넣은 고객 불만 메일에 보낼 답장을 써줘. [질문에 메일 본문이 붙어 있지 않음] · FAIL 예: 빠진 자료는 밝혔으나(J1-3.a 예) 기본 틀·확인 질문·자료 요청 없이 끝남.
- J1-4.a · J1-4 불필요한 내용 없음 · 질문에 답하는 데 쓰이지 않는 단락이 없는가 (같은 내용의 반복은 J1-4.b에서만 봄) · 적용: 모든 질문 · 근거: 해당 단락 (FAIL 시) · 예시 질문: 베란다 화분에 심은 바질 잎이 아래쪽부터 노랗게 변해요. 왜 그런 건가요? · FAIL 예: 원인 설명은 다 했지만 요리 활용법은 잎이 노래지는 이유와 무관함.
- J1-4.b · J1-4 불필요한 내용 없음 · 본문에서 같은 내용이 새 정보 없이 별도 항목·단락으로 두 번 나오지 않았는가 (마무리 요약 한 번은 제외) · 적용: 모든 질문 · 근거: 반복된 두 구간 · 예시 질문: 재택근무를 시작했는데 집에서는 집중이 잘 안 돼요. 집중하는 데 도움이 되는 방법 알려주세요. · FAIL 예: 첫 번째 방법(일하는 자리 정하기)을 새 정보 없이 다른 말로 다시 씀.
- J2-1.a · J2-1 대상 수준 · 지정한 대상·받는 사람이 모를 용어를 설명 없이 쓰지 않았는가 · 적용: 대상·받는 사람 표현 · 근거: 대상, 해당 용어 (FAIL 시) · 예시 질문: 70대 어머니가 스마트폰에서 와이파이랑 데이터가 뭐가 다른지 자꾸 물어보셔. 어머니가 이해하실 수 있게 설명해 줘. · FAIL 예: 설명 깊이와 말투는 PASS와 같지만 'LTE·5G 셀룰러 망'을 풀어 주지 않고 써서 J2-1.a만 아니오.
- J2-1.b · J2-1 대상 수준 · 지정 대상이 이미 아는 수준의 설명만 있거나(너무 얕음), 대상이 모를 전제 지식을 요구하지(너무 깊음) 않는가 (용어 문제는 J2-1.a) · 적용: 위와 같음 · 근거: 대상 표현 인용, 가장 얕거나 깊은 문장 1개 · 예시 질문: 사내 세미나에서 10년 차 이상 시니어 백엔드 개발자들에게 '인덱스를 언제 추가해야 하는지' 발표하려고 해. 발표에서 설명할 내용을 정리해 줘. · FAIL 예: 모르는 용어는 없지만(J2-1.a 예) 입문자용 깊이라 10년 차 시니어 청중에게 맞지 않아 J2-1.b만 아니오.
- J2-2.a · J2-2 말투·어조 · 지정한 말투·존대를 처음부터 끝까지 지켰는가. 추상적 어조 지시(따뜻하게 등)는 명백히 반대되는 문장이 없는가 · 적용: 현재 질문의 말투·어조 지정 · 근거: 지정 문장, 어긋난 문장 · 펼침: 지시별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 우리 독서 모임 단톡방에 이번 달 모임 장소가 바뀌었다고 알리는 글을 써 줘. 모임원들끼리는 다 반말 쓰니까 편한 반말로 써 줘. · FAIL 예: 앞부분은 반말이지만 마지막 두 문장이 존댓말로 바뀌어 끝까지 지키지 못해 J2-2.a만 아니오.
- J2-3.a · J2-3 조건·제약 준수 · 질문이 직접 말한 조건·제약("~는 빼고", "~이내", "~만", "~안 돼")을 어긴 문장이 없는가 (조건 아래서 계획이 성립하지 않는 것은 J3-5.a) · 적용: 질문의 조건 문장 (개수·형식은 코드 평가, 모순 조건 쌍은 J1-3, 인원·시간·장소 같은 자원 조건은 J3-5) · 근거: 조건 문장, 위반 문장 · 펼침: 조건별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 팀 전체에 보낼 퇴사 인사 메일을 써 줘. 이직하는 회사 이름이랑 퇴사 이유는 절대 쓰지 말고, 그동안 고마웠다는 내용 위주로 써 줘. · FAIL 예: 감사 내용은 갖췄고 퇴사 이유도 없지만, 쓰지 말라고 한 이직 회사 이름을 써서 '회사 이름' 조건에서 J2-3.a만 아니오.
- J2-4.a · J2-4 설명 방식 · 지정한 방식(비유·예시·관점·상황)으로 설명했는가 · 적용: 설명 방식 지정 · 근거: 지정 문장, 해당 설명 · 예시 질문: 컴퓨터에서 '캐시'가 뭔지 비유를 들어서 설명해 줘. · FAIL 예: 설명 내용은 맞지만 비유 없이 직접 설명만 해 지정한 방식을 따르지 않아 J2-4.a만 아니오 (비유가 없으므로 J2-4.b는 해당 없음이어야 함).
- J2-4.b · J2-4 설명 방식 · 비유·예시가 설명 대상의 핵심 특징과 맞물리는가 (개념을 틀리게 전달하면 J5-1) · 적용: 설명 방식이 지정되고 답변에 비유·예시가 실제로 있을 때 (J2-4.a가 아니오면 해당 없음) · 근거: 비유·예시 문장 · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 회사의 '이익'과 '현금흐름'이 왜 다른지 비유를 들어 설명해 줘. · FAIL 예: 비유는 들었고(J2-4.a 예) 직접 설명도 맞지만(J5-1 통과), '짧은 기간 대 긴 기간 평균'이라는 날씨·기후의 차이가 외상·선투자의 시점 차이라는 이익·현금흐름의 차이와 대응하지 않아 J2-4.b만 아니오.
- J2-5.a · J2-5 추천·글의 목적 적합성 · 추천이 현재 질문에 서술된 배경·상황(J2-3 목록에 없는 것)에 맞는가 (이전 턴에만 있는 상황은 J6-2.b) · 적용: 추천·제안 요청 · 근거: 상황 문장, 추천 문장 · 예시 질문: 다음 달에 결혼하는 대학 동기한테 결혼 선물을 하려고 해. 신혼집은 원룸이고 둘 다 요리는 거의 안 하고 주로 배달시켜 먹는대. 뭐가 좋을까? · FAIL 예: 질문에 금지·예산 같은 명시 조건은 없어 J2-3에는 걸리지 않지만, 원룸에 요리를 안 하는 부부라는 서술된 상황과 맞지 않는 부피 큰 주방용품을 추천해 J2-5.a만 아니오.
- J2-5.b · J2-5 추천·글의 목적 적합성 · 글이 질문이 정한 목적(사과·거절·홍보·안내 등)을 실제로 수행하는가 (예: 사과문이 변명 위주가 아닌가) · 적용: 글 작성 요청 · 근거: 목적 표현 인용, 목적에 어긋난 문장 · 예시 질문: 주문한 케이크가 약속한 날보다 하루 늦게 배송된 고객에게 보낼 사과문을 써 줘. · FAIL 예: 사과 대신 주문량·택배사 사정을 늘어놓아 변명 위주라 사과문이라는 목적을 수행하지 못함.
- J3-1.a · J3-1 내부 모순 없음 · 같은 대상·조건에 대해 서로 다른 값·결론·평가가 없는가 · 적용: 모든 답변 · 근거: 모순되는 두 위치 (FAIL 시) · 예시 질문: 원룸으로 이사하는데 라텍스 매트리스와 메모리폼 매트리스 중 뭐가 나을까요? 여름에 더위를 많이 타는 편이에요. · FAIL 예: 같은 라텍스의 통기성을 두고 "열이 잘 빠진다"와 "열이 잘 빠지지 않는다"를 함께 말하고, 추천도 라텍스→메모리폼으로 갈림. 근거는 각각 있어 J3-2는 통과.
- J3-2.a · J3-2 근거와 결론 · 주 결론(질문이 요구한 선택·추천·판단)에 결론을 바꿔 말한 것이 아닌 근거 문장이 하나 이상 있는가 · 적용: 추천·선택·판단이 있는 답변 ("왜·원리" 설명은 J3-3). 답변당 1개 · 근거: 결론 문장, 근거 문장 · 예시 질문: 사무실에 둘 공기청정기를 하나 추천해 주세요. 직원 6명이 쓰는 20평 정도 사무실이고 창문이 하나뿐이에요. · FAIL 예: 추천 결과물은 있으나(J1-1 통과) 왜 그 제품인지 설명하는 근거 문장이 없음. "가장 알맞다"는 결론을 다시 말한 것이지 근거가 아님. 질문이 이유를 요구하지 않아 J4-2도 해당 없음.
- J3-2.b · J3-2 근거와 결론 · 제시한 근거로 결론이 성립하는가 · 적용: 위와 같음 · 근거: 위와 같음 · 예시 질문: 재택근무를 시작해서 화상회의를 하루 서너 번 합니다. 집 인터넷을 하늘넷 기본형과 하늘넷 프리미엄 중 어느 것으로 할지 골라 주세요. · FAIL 예: 근거(가입 사은품)는 있어 J3-2.a는 통과하지만, 그 근거로는 "화상회의가 안정적"이라는 결론이 나오지 않음.
- J3-3.a · J3-3 인과·원리 · 원인과 결과를 잇는 방향이 질문이 준 선후·조건과 맞는가 (각 사실의 진위는 J5-1) · 적용: 질문에 선후·조건이 적힌 이유·원리 요청. 없으면 해당 없음 · 근거: 질문의 선후·조건, 답변의 인과 문장 · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 집에서 키우는 몬스테라 잎 끝이 갈색으로 마릅니다. 겨울 들어 난방을 켠 뒤부터 그래요. 왜 그런 건가요? · FAIL 예: 건조한 공기→잎 마름이라는 원리 자체는 현상을 설명하므로 J3-3.b는 통과하지만, 난방과 건조 사이의 원인·결과를 뒤집어 난방을 결과로 놓음. 질문이 말한 선후(난방 뒤 잎 마름)와도 맞지 않음.
- J3-3.b · J3-3 인과·원리 · 설명한 원리가 대상 현상을 실제로 설명하는가 (비유·예시 문장은 빼고 직접 설명만. 비유는 J2-4.b) · 적용: 이유·원리 요청 · 근거: 원리 설명 부분 · 예시 질문: 식빵을 냉장고에 넣어 두면 실온에 둘 때보다 더 빨리 딱딱해지던데, 왜 그런가요? · FAIL 예: 저온에서 미생물 번식이 느리다는 설명은 방향도 맞고 사실이지만, 그것이 왜 빵을 더 빨리 굳게 하는지는 전혀 설명하지 못함(원리와 현상이 연결되지 않음).
- J3-4.a · J3-4 풀이 연결 · 풀이 단계가 끊김 없이 이어지는가 (계산값은 코드 3-1, 입력 값은 J5-2) · 적용: 풀이 요청 · 근거: 끊긴 단계 (FAIL 시) · 예시 질문: 자전거로 집에서 회사까지 평균 시속 15km로 가면 1시간 20분이 걸립니다. 평균 시속 20km로 가면 얼마나 걸리는지 풀이 과정과 함께 알려 주세요. · FAIL 예: 거리를 구하는 단계가 없어 "빨라지면 줄어든다"에서 1시간으로 건너뜀. 최종 값은 맞고 입력 값도 그대로라 코드 3-1·J5-2는 통과.
- J3-5.a · J3-5 실행 가능성 · 답변 안에 적힌 시간·인원·순서끼리 맞는가 (같은 사람 동시 배정, 결과가 전제보다 먼저, 적힌 소요 시간 합이 구간을 넘음 등. 외부 지식이 필요한 불가는 J5-1) · 적용: 계획·일정·절차 요청 · 근거: 맞지 않는 두 지점 · 예시 질문: 주말에 동네 플리마켓에 혼자 부스를 내려고 합니다. 오후 1시부터 5시까지 운영하고, 물건은 차에 실어 둘 건데 주차장은 부스에서 걸어서 15분 거리예요. 당일 운영 계획을 짜 주세요. · FAIL 예: 혼자인데 1시에 부스 판매와 주차장 왕복을 동시에 배정해 한 사람이 실행할 수 없음. 질문의 명시 조건(혼자·1~5시·15분 거리)은 바꾸지 않아 J2-3·J5-2는 통과.
- J3-5.b · J3-5 실행 가능성 · 값은 같은데 상한·예상·실제 같은 역할을 바꿔 쓰지 않았는가 (값 자체가 다르면 J5-2.a) · 적용: 예산·수치에 역할이 있는 질문 · 근거: 값과 역할 표현 · 예시 질문: 이번 달 식비 예산 상한을 40만원으로 잡았습니다. 지금까지 실제로 쓴 돈은 28만원이고, 남은 2주 동안 예상 지출은 15만원입니다. 예산 안에서 끝낼 수 있을까요? · FAIL 예: 15만원(예상)과 28만원(실제)의 역할을 서로 바꿔 씀. 값 자체와 계산(40-15=25, 28-25=3)과 최종 차액은 그대로라 코드 3-1·J5-2·J3-1은 통과.
- J4-1.a · J4-1 비교 완결 · 비교 대상을 모두 다뤘는가 · 적용: 비교 요청 (비교 문장이 어떤 형태로든 있을 때. 비교 자체가 없으면 J1-1) · 근거: 예: 대상마다 답변 인용 / 아니오: 질문 인용 + 가장 가까운 답변 구절 · 펼침: 대상별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 출퇴근용으로 전기자전거, 전동킥보드, 일반 자전거 중 뭐가 나을지 비교해 줘. 편도 6km 정도고 언덕이 좀 있어. · FAIL 예: 일반 자전거를 한 번도 다루지 않고 두 대상만 비교해 결론을 냄. 결론 자체는 있으므로 J1-1 아님, 질문에 비교 기준 지정이 없어 J4-1.b는 해당 없음.
- J4-1.b · J4-1 비교 완결 · 질문이 정한 비교 기준(장단점 포함)을 모두 다뤘는가 · 적용: 비교 기준이 명시된 경우 · 근거: 예: 기준마다 답변 인용 / 아니오: 질문 인용 + 가장 가까운 답변 구절 · 펼침: 기준별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 이사 업체에 포장이사와 반포장이사 중 뭘 맡길지 고민이야. 비용과 이사 당일 내가 해야 할 일 기준으로 비교해 줘. · FAIL 예: 두 대상은 모두 다뤘고(J4-1.a 예) 근거 있는 결론도 있으나(J1-1·J3-2 예), 질문이 정한 기준 '이사 당일 내가 해야 할 일'이 어디에도 없어 비용 기준만으로 결론을 냄.
- J4-2.a · J4-2 함께 요구한 항목 · 주 요청 외에 종류가 다른 요구(추가 요청·이유·예시·각각)가 모두 있는가 (비교의 기준·장단점은 J4-1.b, "N개" 같은 개수 요구는 코드 2-1) · 적용: 요청·요구가 2개 이상 · 근거: 예: 요구마다 답변 인용 / 아니오: 질문 인용 · 펼침: 요구별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 신입사원 온보딩에 멘토 제도를 도입하려고 해. 좋은 점과 주의할 점을 알려주고, 멘토에게 줄 만한 보상 예시도 들어 줘. · FAIL 예: 좋은 점·주의할 점은 있으나 '보상 예시'는 없고 보상이 필요하다는 언급만 있음. 주 요청의 결과물은 있으므로 J1-1 아님, 비교 질문이 아니라 J4-1 해당 없음.
- J4-3.a · J4-3 핵심 단계·구성 요소 · 목적에 필요한 핵심 단계·필수 구성 요소를 먼저 나열하고 그중 빠진 것이 없는가 (풀이 단계는 J3-4, 빠져서 실행 불가면 J3-5.a) · 적용: 방법·절차(how-to) 요청과 글 작성 요청. 풀이 요청은 제외 · 근거: 예: 단계·요소마다 답변 인용 / 아니오: 질문 인용 · 펼침: 단계·요소별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 아파트 입주민에게 보낼 소방 대피 훈련 안내문을 써 줘. 10월 24일 금요일 오후 2시에 101동 앞 광장에서 하고, 훈련 중에는 승강기가 멈추니까 계단으로 대피해야 해. 문의는 관리사무소로. · FAIL 예: 장소·행동 요령·문의처는 있으나 안내문의 필수 요소인 일시(10월 24일 오후 2시)가 통째로 빠짐. 글은 완성되어 있어 J1-1 아님, 질문 값을 바꾼 것이 아니라 뺀 것이므로 J5-2 아님.
- J4-4.a · J4-4 요약 핵심 · 원문의 핵심 정보(독자가 판단·행동하는 데 필요한 날짜·기간·장소·대상·조건·할 일)를 먼저 나열하고 그중 빠진 것이 없는가. 해당 주제의 문장이 있으면 내용이 틀려도 있음(틀린 내용은 J5-2.b). "자세한 건 원문 참고"는 없음 · 적용: 요약 요청 · 근거: 예: 원문 인용, 요약 인용 / 아니오: 원문 인용 · 펼침: 핵심 정보별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 아래 사내 공지를 팀 채팅방에 올릴 수 있게 요약해 줘. 「총무팀 공지: 11월 3일(월)부터 본사 주차장 2층 방수 공사를 시작합니다. 공사 기간은 약 3주이며, 이 기간 동안 2층은 전면 폐쇄됩니다. 1층과 3층은 평소대로 이용 가능하나 자리가 부족할 수 있어, 인근 한빛 공영주차장 · FAIL 예: 시작일·기간·폐쇄·대체 주차 지원은 있으나 지원을 받기 위해 독자가 해야 할 '영수증을 매월 말 총무팀에 제출'이 빠짐. 없는 내용을 더하거나 뜻을 바꾸지는 않았으므로 J5-2.b 아님.
- J5-1.a · J5-1 사실 정확성 · 답변의 외부 사실 주장(수치·날짜·명칭·통계·개념 정의)이 사실과 맞는가. 시점이 있는 사실은 답변 수집 날짜 기준 · 적용: 코드 규칙이 사실 정보를 묻는 질문으로 판정한 질문 (J3-1 모순 쌍, J3-3 인과 연결 문장, 이전 턴 AI 답변에서 비롯한 값은 제외) · 근거: 주장 인용과 검색 기록. 거짓이면 올바른 사실과 반박 출처 원문 · 펼침: 주장별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 저녁에 커피 마시면 잠을 잘 못 자는 이유가 뭐야? 카페인이 몸에 얼마나 오래 남아? · FAIL 예: 아데노신 설명과 인과 구조는 맞지만 반감기 수치가 거짓(실제 평균 약 5시간). 사실 오류 하나로 해당 주장만 거짓, J3-3은 걸리지 않음.
- J5-2.a · J5-2 입력 자료 충실성 · 질문에서 준 개별 값·이름·날짜를 썼다면 다른 값으로 적지 않았는가 (쓰지 않은 값은 해당 없음. 상황 문장·선후 관계는 값이 아님) · 적용: 현재 질문의 값을 쓰는 답변 · 근거: 질문 원문, 답변 인용 · 펼침: 값별(질문에 이 요소를 2개 이상 넣음) · 예시 질문: 한빛물산 박지훈 과장님께 보낼 납품 일정 확인 메일을 써 줘. 납품 예정일은 5월 12일(월) 오전이고, 납품 장소는 평택 제2물류센터야. 당일 입고 담당자 연락처를 미리 알려 달라는 요청도 넣어 줘. · FAIL 예: 질문이 준 장소 '제2물류센터'를 '제1물류센터'로 바꿔 썼음. 메일 구성 요소와 요청 사항은 다 있어 J1·J4는 통과하고 이 값 하나만 아니오.
- J5-2.b · J5-2 입력 자료 충실성 · 질문이 준 자료를 정리·요약할 때 원문에 없는 문장을 더하거나 문장 단위 의미를 바꾸지(취소→연기 등) 않았는가 (개별 값 오기는 J5-2.a) · 적용: 자료 정리·요약 요청 · 근거: 자료 원문, 답변 인용 · 예시 질문: 어린이집 알림장인데 남편한테 보내게 핵심만 정리해 줘. 원문: '다음 주 수요일(5월 14일) 봄 소풍은 서현수목원으로 갑니다. 도시락은 원에서 준비하니 개인 물통과 모자만 챙겨 주세요. 비가 올 경우 소풍은 취소되고 평소처럼 원에서 보육합니다. 당일 등원은 평소와 같이 9시까지입니다. · FAIL 예: 원문은 '취소되고 평소처럼 보육'인데 '다음 주로 연기'로 의미를 바꿈. 핵심 정보는 다 들어 있어 J4-4(누락)는 통과하고 이 항목만 아니오.
- J5-3.a · J5-3 확인 과정 꾸밈 없음 · 하지 않은 조회·확인·실행을 한 것처럼 쓰거나, 존재하지 않는 출처·문헌·조문·제품을 들지 않았는가 (그 문장 안의 사실 값은 J5-1에서 따로 봄) · 적용: 확인·조회·출처를 언급한 답변. 조회·실행 부분은 도구 사용 여부를 알 수 없는 답변(AIONA)에서 해당 없음 · 근거: 해당 문장. 출처는 서버 존재 확인 · 예시 질문: 이번 달 카드값이 같은 날 두 번 빠져나간 것 같아. 어떻게 해야 해? · FAIL 예: 접근할 수 없는 사용자 결제 내역을 조회한 것처럼 쓰고 취소 요청을 실행한 것처럼 꾸밈. 외부 사실 주장은 없어 J5-1은 적용되지 않고 이 항목만 아니오.
- J6-1.a · J6-1 지시 유지 · 이전 턴의 유효한 지시와 제약(역할·말투·금지 사항·예산·범위 등)을 지켰는가 (결과물 편집 요청은 J6-3.b) · 적용: 이전 턴에 지시·제약이 있음 · 근거: 지시가 나온 턴과 인용, 현재 답변 인용 · 펼침: 지시·제약별(질문에 이 요소를 2개 이상 넣음) · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: PT 처음 받는데 몇 회로 시작하는 게 좋아요? · FAIL 예: 내용은 같지만 1턴의 존댓말 지시를 어기고 반말로 답함. 현재 질문에는 말투 지정이 없어 J2-2는 해당 없음.
- J6-2.a · J6-2 정보 기억 · 이전 턴에서 준 정보(이름·수치·선호) 중 대화 중 바뀐 적 없는 것을 정확히 썼는가 · 적용: 이전 정보를 쓰는 답변 · 근거: 정보가 나온 턴과 인용, 답변 인용 · 펼침: 정보별(질문에 이 요소를 2개 이상 넣음) · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 업체에 보낼 견적 요청 문자도 써 줘. · FAIL 예: 1턴에서 11월 7일이라 했는데 17일로 틀리게 씀. 나머지 정보는 맞고 빠진 것도 없어 J6-2.b는 통과.
- J6-2.b · J6-2 정보 기억 · 현재 답변에 필요한 이전 정보를 빠뜨리지 않았는가 (이로 인한 부적합·요소 누락은 J2-5·J4에서 보지 않음) · 적용: 현재 요청이 이전 정보를 필요로 함 · 근거: 필요한 정보의 턴 인용, 그 정보를 썼어야 할 답변 문장 인용 · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 산책 코스 좀 골라 줘. 집 앞에 하천 산책로 3km짜리랑 아파트 단지 안을 도는 500m 코스가 있어. · FAIL 예: 열 살에 관절이 안 좋다는 1턴 정보를 전혀 고려하지 않고 긴 코스를 고름. 틀리게 쓴 정보는 없어 J6-2.a는 해당 없음.
- J6-2.c · J6-2 정보 기억 · "그거", "아까 두 번째" 같은 말이 가리키는 이전 내용을 맞게 찾았는가 (오해로 다른 대상에 답하면 여기서만 FAIL, J1-1은 보지 않음) · 적용: 지시어가 있는 질문 · 근거: 지시어, 가리키는 이전 턴 · 예시 질문: 아까 두 번째 거 진행 방식 좀 자세히 알려줘. · FAIL 예: "두 번째"는 성대모사 퀴즈인데 첫 번째 항목인 립싱크 배틀을 설명함. 설명 자체는 충실해 다른 항목은 걸리지 않음.
- J6-3.a · J6-3 변경 반영 · 바뀌거나 취소된 조건·전제(장소·날짜·대상·예산)를 최신 상태로 반영했는가 (옛 값 사용은 여기서만 FAIL) · 적용: 대화 중 조건 변경·취소 · 근거: 변경 턴과 인용, 답변 인용 · 펼침: 변경별(질문에 이 요소를 2개 이상 넣음) · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 엘리베이터에 붙일 짧은 공지문도 하나 써 줘. · FAIL 예: 2턴에서 장소가 1층 경로당으로 바뀌었는데 취소된 옛 장소를 그대로 씀. 시간·안건은 맞음.
- J6-3.b · J6-3 변경 반영 · 같은 결과물을 여러 번 고칠 때 앞선 편집(문장·표현 수정)이 되돌아가지 않았는가 · 적용: 같은 결과물을 2회 이상 수정 · 근거: 편집 요청 턴 인용, 되돌아간 자리의 결과물 문장 인용 (사라진 경우 빈 인용 허용) · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 마지막 문장을 '두 사람의 앞날을 진심으로 축하합니다'로 바꿔 줘. · FAIL 예: 요청한 마지막 문장은 바꿨지만 2턴에서 뺐던 '영원히'가 1턴 문장 그대로 되살아남.
- J6-4.a · J6-4 자기 일관성 · 이전 자기 답변(결정·계산·추천)과 지시·정보·변경으로 설명되지 않는 모순이 없는가 · 적용: 이전 턴에 결정·계산이 있고 현재 턴에 반박이 없음 · 근거: 이전 답변과 현재 답변 인용 · 적용 여부는 평가 모델이 정함(그 상황이 분명히 생기게 설계) · 예시 질문: 진행자가 발표자를 차례로 소개하는 멘트 써 줘. · FAIL 예: 1턴에서 현우를 먼저 세우기로 정했는데 아무 설명 없이 반대 순서로 씀. 이름·책 종류는 맞아 J6-2.a는 통과.
