# 4단계 외부 AI 답변 수집 통합 (2026-10-13)

API·웹·에이전트·외부 플랫폼에서 받은 답변을 공통 형식으로 바꿔 기존 CODE·J1~J6 평가기에 연결한 결과다. 이전 단계: [3단계 통합 안정화](3단계_통합안정화_2026-10-13.md).

- 작업 브랜치 `feature/external-evaluation-ingestion` (기준 `integrate/main-eval-reliability` `cab014f`).
- **평가 판정 정책은 바꾸지 않았다.** PASS/FAIL/INCOMPLETE 규칙·J1~J6 질문·Routing·집계·Judge 설정(Claude Opus 5.5)은 그대로다. 추가한 것은 입력 경로와 기록·표시다.
- 유료 호출 0회. 수집 모델과 평가 Judge 는 모두 대역(mock)으로 검증했다. 실제 외부 플랫폼 연결과 실호출 판정 품질은 확인하지 않았다(9장·10장).

## 1. 기존 수집·평가 구조 조사 (STEP 1)

| 항목 | 기존 구현 | 4단계에서 |
|---|---|---|
| 모델 연결 | `ComparisonService.configure`·`load_environment` — `.env` 의 `GOOGLE/ANTHROPIC/OPENAI_API_KEY`+`*_MODEL`, 키는 서버 메모리에만 | 그대로 재사용 |
| 지원 제공자 | Gemini·Claude·GPT 3개 (`PROVIDERS`) | 외부 수집의 API 함께 수집에 그대로 사용 |
| API 호출 | `request_answer` — OpenAI Responses·Anthropic Messages·Gemini generateContent. 도구·시스템 프롬프트 없음, 자동 재시도 없음 | 중복 클라이언트 없이 그대로 호출. 원본 응답에서 사용량·출처·도구 정보만 추가로 읽음 |
| 질문 전송 | `_collect` — 독립 질문은 병렬, 같은 대화의 턴은 각 모델 자기 답변을 이력으로 순차 | 그대로 사용 |
| 답변 저장 | `run.datasets[provider][index]` + `collection`(상태·오류·원본 응답·지연) | 같은 구조에 공통 필드(수집 방식·시각·환경·사용량·출처·품질) 추가 |
| JSON 업로드 | `dataset_import.import_text` (Q/A·id/turns·회차 JSON·MD/TXT) | 기존 형식 변환기에서 그대로 사용 |
| 대화 ID·턴 | `conversation_id`+`turn`. 수집용 업로드는 1부터 연속을 강제, 평가 엔진은 누락을 J6 미확인으로 처리 | 외부 수집은 **빠진 턴을 기록한 채 허용**(평가 엔진의 누락 처리로 연결) |
| 결과 비교 | 실행(run) 단위, AIONA+3모델 고정 화면 | 임의 시스템 키를 표시하도록 일반화(기존 실행 표시는 동일) |
| 평가 입력 | `evaluate_case` (question·answer·displayed_text·reference·conversation_id·turn·system_id·source) | `answer_sources` 를 **있을 때만** 추가 |
| Routing | 모든 질문 같은 CODE 경로 + `jev_applicability` | 변경 없음 |
| 이력 | `data/comparison_runs/{run_id}.json` + 작업 이력 sqlite + 버전 레지스트리 | 그대로 저장. 외부 실행은 AIONA 버전이 없음 |
| 출처 | J5 가 답변 본문 링크만 추출(`answer_citations`) → 서버가 원문 대조 | 수집 단계의 구조화 출처를 먼저 쓰도록 연결(4장) |

```text
파일·직접 입력·API 수집
  └─ 어댑터 (webapp/ingestion/*_adapter.py)  ─ 형식 판별 · 원본 보존 · HTML→Markdown · 출처 URL 구분
       └─ 공통 묶음 modelgrade-collection/v1 ─ 검증(schema.py) · 여러 파일 병합 · 중복 판별
            └─ 실행 구조(runs.py)            ─ 시스템별 같은 질문 순서의 행, 실행 환경 비교
                 └─ ComparisonService.evaluate (기존) ─ CODE → J1~J6 → PASS/FAIL/INCOMPLETE
                      └─ data/comparison_runs/*.json · 작업 이력 · 결과 비교 화면
```

## 2. 공통 데이터 구조 (STEP 2)

`webapp/ingestion/schema.py` — **`modelgrade-collection/v1`**. 질문·시스템·답변을 나눈다. 같은 질문에 대한 여러 시스템의 답변은 같은 `case_id` 를 가리키므로 서로 다른 질문으로 잡히지 않는다.

| 묶음 | 필수 | 선택 (모르면 null) |
|---|---|---|
| `questions[]` | `case_id`, `question` | `question_type`, `scenario`, `dataset_version`, `conversation_id`+`turn`(함께), `reference` |
| `systems[]` (수집 대상) | `system_key`, `provider`, `platform`, `model`(모르면 `"unknown"` 명시), `access_mode`(api·web·agent·platform) | `label`, `model_version`, `settings`(확인된 값만), `environment.web_search_available`·`tools_available`·`system_instruction{known,text?,note?}` |
| `responses[]` | `case_id`, `system_key`, `collection_method`, `answer`(SUCCESS 일 때) | `status`(SUCCESS·INCOMPLETE·ERROR·NOT_COLLECTED), `error`, `collected_at`, `answer_format`, `original{format,content}`, `environment.web_search_used`·`tools_used`, `sources[]`, `usage`, `agent`, `raw`, `platform_ref`, `collection_quality[]` |

- **수집 대상 모델과 평가 Judge 분리**: 묶음에는 Judge 설정이 없다. 평가는 서버의 기존 의미 평가 설정(현재 Claude Opus 5.5)을 그대로 쓰고, 수집 모델 비용(`usage`)과 Judge 사용량(평가 기록의 `usage`)은 따로 남는다.
- **모름 처리**: 웹검색 허용 여부·도구·시스템 지시처럼 확인할 수 없는 값은 `null`. 제공자·모델이 빠지면 오류이고, 모르면 `"unknown"` 을 직접 적게 한다.
- **원본 보존**: 평가용 `answer` 가 원본과 다르면(HTML 변환, 인용 표시 정리) `original` 에 원본을 둔다. 변환 규칙은 `normalization` 에 남긴다.
- **비용**: 기존 정책(README: 비용을 계산·저장하지 않음)을 따라 토큰 수만 기록하고, 금액은 **제공자가 응답에 직접 밝힌 경우만**(`usage.reported_cost`, 예: Perplexity) 기록한다.
- **식별자**: `question_key`(질문 원문 + 같은 대화의 앞 사용자 질문 순서 + 참조 자료, 플랫폼 대화 ID 는 제외) · `response_key`(질문·시스템·상태·답변) · `import_fingerprint`(시스템 정의 + 답변 열쇠). 같은 질문은 파일이 달라도 하나로 묶고(다른 `case_id` 는 `aliases`), 같은 `case_id` 에 다른 질문이면 오류, 일부만 같은 대화는 다른 대화로 분리한다.
- **검증 오류**: 경로와 이유를 모두 돌려준다 (`BundleError.errors`, API 응답 400 의 `errors`). 예: 제공자·모델 누락, 예약 키(`aiona·gemini·claude·gpt`), 빈 답변(실제 빈 응답이면 `empty_answer_confirmed`), 수집 방식 누락, 없는 질문 참조, 같은 턴 중복, 같은 시스템·질문의 서로 다른 두 답변(재실행은 별도 Import).
- 예제: [`examples/external/`](../examples/external) — 공통 형식·대화 기록·API 응답·에이전트 기록 정상 예제와 오류 예제(`invalid.sample.json`).

보조 형식: `modelgrade-transcript/v1`(역할별 메시지 대화), `modelgrade-api-responses/v1`(질문 + 원본 API 응답 + 선택적 요청 본문), `modelgrade-agent-run/v1`(에이전트 실행).

## 3. 수집 경로별 구현 (STEP 3~6)

### 3-1. API

| 경로 | 구현 | 확인되는 환경 |
|---|---|---|
| 이 서버에서 실시간 수집 | 외부 수집 화면에서 "같은 질문을 API로도 수집" 선택 → 기존 `request_answer`·`_collect` 그대로 호출 → `_finalize_external_collection` 이 원본 응답에서 사용량·출처(url_citation 등)·완료 사유를 공통 형식으로 변환. 질문마다 실제 수집 시각 기록 | 웹검색 허용 **없음**·도구 **없음**·시스템 지시 **없음**(요청 본문을 서버가 만들므로 확정값) |
| API 응답 파일 가져오기 | OpenAI Responses(xAI·Perplexity Agent API 같은 모양), Chat Completions(Perplexity Sonar `citations`·`search_results` 포함), Anthropic Messages(web_search 인용), Gemini(groundingMetadata) | 응답의 도구 호출로 실제 웹검색 사용 확인. 요청 본문을 함께 넣으면 허용 도구·시스템 지시 확인, 없으면 모름 |

- API 오류·시간 초과·잘린 응답은 수집 상태(ERROR·INCOMPLETE)로 남고 평가에서 제외된다(품질 FAIL 아님, 기존 정책과 같음).
- API 키는 환경 변수·서버 메모리만 쓰며 결과 파일에 남지 않는다(테스트로 확인).

### 3-2. 웹 (공식 내보내기·사용자 파일·직접 입력)

| 입력 | 처리 |
|---|---|
| ChatGPT 공식 내보내기 `conversations.json`·`chat.html` | `mapping` 트리에서 `current_node` 까지의 화면 분기만 사용, 편집·재생성 분기 수 기록. 도구 호출(`recipient`·tool 메시지)로 웹검색 사용 판단. `content_references`·`citations` 의 인용 표시는 화면 표시 글자(alt)로 바꾸거나 지우고 원본 보존, 출처 URL 과 붙은 문장 연결. 사용자 맞춤 지침은 "있음"만 기록(내용은 개인정보라 보관하지 않음). 첫 질문 전 AI 메시지·첨부는 제외하고 기록 |
| Claude.ai 내보내기 | `chat_messages` 순서, text 블록 인용·도구 사용 기록 |
| 대화 기록 JSON | system·developer·tool 메시지를 질문에 섞지 않음, `missing_turns_before`·`turn` 으로 빠진 턴 표시, 시각·턴 역순·AI 먼저·한 질문에 답 여러 개는 오류 |
| HTML | 메시지 역할 표시(`data-message-author-role`)가 있으면 질문·답변 분리. 없으면 질문 원문을 따로 받아야 함(경계를 추측하지 않음) |
| 직접 복사 | 질문·답변(Markdown·텍스트·HTML) 한 쌍 |

**HTML → Markdown** (`html_markdown.py`, 표준 라이브러리만): 제목·문단·줄바꿈·목록(중첩·시작 번호·체크박스)·표(정렬·`|` 이스케이프·`<br>`)·코드 블록(언어 표시, 백틱 포함 코드는 더 긴 울타리, 복사 버튼 등 머리글 제외)·인용문·링크·각주(`[^n]`)·KaTeX 수식(`$…$`)을 옮긴다. 병합 셀·칸 안의 블록·짝이 맞지 않는 태그·알 수 없는 요소·빈 변환은 `collection_quality` 에 남기고, 빈 변환은 INCOMPLETE 로 평가에서 뺀다. 변환된 표·코드 블록이 CODE 에서 FAIL 하지 않음을 실제 엔진으로 확인했다. `displayed_text` 는 설정하지 않는다(기존 Markdown 답변과 같은 검사 경로 유지).

**API·웹 비교**: 같은 모델명이라도 실행 방식·웹검색·도구·시스템 지시·수집 시점이 시스템 정보에 따로 남고, 다르면 순위를 매기지 않는다(6장).

### 3-3. 에이전트

`agent_adapter.py` — 일반 형식, OpenAI Agents SDK trace·span, LangSmith run, OpenTelemetry GenAI span. 최종 답변만 평가기에 넘기고, 단계별 도구·입출력(4,000자 미리보기)·오류·실패 단계·실행 시간·조회한 출처는 `collection.agent` 에 보존한다. 실행 실패로 답이 없으면 ERROR, 실패·중단인데 글자가 남으면 INCOMPLETE(완성 여부를 알 수 없어 평가 제외), 도구 일부 실패 후 완료면 평가하고 경고를 남긴다. **도구 사용 과정을 평가하는 기준은 추가하지 않았다**(11장 후보).

### 3-4. 외부 플랫폼 조사 (STEP 6, 2026-10-13 공식 문서 확인)

이전 미팅에서 언급한 플랫폼 목록은 저장소 문서에 없어(ChatGPT·Gemini·AIONA 만 확인), 문서에 나온 서비스와 주요 서비스를 공식 문서로 조사했다. **미팅 목록을 주시면 추가 확인한다.** "관찰"은 공식 스키마 문서 없이 실제 파일 구조에 근거한 항목이다.

## 4. 출처와 J5 (STEP 7)

### 4-1. 수집 단계

- URL 구분(`sources.py`): 표시·제공 URL(`display_url`)은 그대로 두고, 평가용 `url` 은 원래 URL 을 알 때 그 값을 쓴다. `utm_source` 가 AI 플랫폼 값일 때만 utm 을 걷는다(`tracking_removed`). `google.com/url?q=` 같은 중계는 쿼리의 원래 URL 을 쓴다(`relay_unwrapped`). Gemini grounding redirect·t.co 등 원래 주소를 모르는 중계는 지어내지 않고 `relay_unresolved` 로 두어 **J5 원문 대조에서 뺀다** — 중계 URL 을 대조하면 다른 호스트 이동으로 '원문 확인 실패' FAIL 이 되므로, 플랫폼 전달 방식 때문에 답변이 FAIL 하지 않게 한다(주장 자체는 평가자 검색으로 확인).
- 이동 주소 확인은 **명시적으로 켤 때만**(평가 시작 시 "중계 URL의 원래 주소 확인") 한 번 요청해 Location 만 읽는다. 공개 IP·표준 포트·URL 형식 검사와 TLS 검증은 J5 출처 수집기 함수를 그대로 쓴다(사설 주소·비표준 포트 거부 테스트). 가져오기당 40개 한도.
- 출처가 붙은 주장: 플랫폼이 준 위치(span)·인용 표시·구절(segment) 순으로 찾고, **답변 원문에 실제 있는 문장만** 쓴다. URL 없는 출처는 `no_url`, 잘못된 URL 은 기록만 한다.
- 시각 구분: 답변 수집 시각(`collected_at`) · 플랫폼이 밝힌 출처 조회·게시 시각(`platform_retrieved_at`·`published_at`) · J5 서버 원문 확인 시각(평가 기록 `checked_at`) 을 따로 둔다. 확인 가능한 스냅샷 참조 자리(`snapshot`)를 두었으나 J5 는 아직 쓰지 않는다.

### 4-2. J5 연결

평가 입력에 `answer_sources` 가 있으면 J5 출처 목록을 구조화 출처 먼저, 본문에서만 찾은 링크를 뒤에 붙여 만든다(`answer-citations-v3`). 같은 출처는 정규화 URL·표시 URL·중계 URL 중 하나라도 같으면 하나다. 원문 대조 한도(4 URL·주장 3개)와 서버 재수집·판정 확정 규칙은 그대로다. **구조화 출처가 없는 답변(기존 업로드·기존 비교)은 이전과 같은 목록·같은 정책 이름(v2)** 이다. 확인되지 않은 출처를 PASS 근거로 쓰는 경로는 없다(평가자 판정을 서버가 받은 원문으로만 확정하는 기존 규칙 유지).

### 4-3. 3단계 후속 이슈 분석

| 문제 | 현재 동작 | 이번 변경 | 판정을 바꾸는 제안 (승인 필요, 미구현) |
|---|---|---|---|
| 서버가 출처에 접근하지 못함 | 평가자 web_fetch 원문이 있으면 그것으로 대조(F5b), 없으면 SOURCE_ORIGINAL_UNAVAILABLE FAIL | 세부 사유 `access_failed` 기록 | 원문 미확보는 INCOMPLETE — 영향: D2-02 같은 질문이 FAIL → 미완료. 외부 답변은 출처가 많아 영향 큼 |
| Claude 원문과 서버 원문이 다름 | 서버가 받은 원문 우선, 인용 없으면 quote_not_found | 세부 사유 `quote_not_found` | 두 원문 중 하나에 인용이 있으면 '원문 변동'으로 따로 표시하고 INCOMPLETE |

## 5. 멀티턴·긴 대화 (STEP 8)

- 외부 대화는 사용자 발화만 질문이 되고, 시스템 지시·도구 결과·AI 답변을 섞지 않는다. 각 시스템은 원래 대화의 자기 답변을 이력으로 쓴다.
- 대화 ID 는 플랫폼 ID 를 보존하고, 플랫폼마다 ID 가 달라도 사용자 질문 순서가 같으면 같은 대화로 묶는다. 한 턴뿐인 대화는 단일 질문으로 둔다.
- 앞부분·중간이 빠진 대화는 빠진 턴을 만들지 않는다. 평가 엔진이 그 턴부터 지속 지시 승계를 하지 않고 J6 를 "앞 대화 이력 확인 불가"(미확인)로 둔다. 빠진 대화가 있으면 API 함께 수집은 막는다(같은 맥락을 재현할 수 없음).
- 확인: 단일·2턴·5턴(지시 변경·해제)·12턴(먼 지시 승계)·앞부분 누락·중간 누락·순서 오류. 대량 롱 컨텍스트 데이터셋은 만들지 않았다.

## 6. 평가 실행·비교 (STEP 9)

- 외부 수집 실행(`run_kind: external_import`)은 기존 `evaluate` 를 그대로 쓴다. 수집 실패·없는 답변은 분모에 남고 평가에서 제외된다.
- 화면: 새 비교 화면 아래 **외부 AI 답변 가져오기** 패널(파일 여러 개, 시스템 정보 직접 입력, API 함께 수집·예상 유료 호출 수, 중계 URL 확인, 재실행). 미리 확인은 모델·평가자를 호출하지 않는다. 결과 비교 화면은 그대로 쓰고 다음만 더했다: 수집 환경 비교(다른 항목·평가 엔진·의미 기준·Judge·J5 출처 정책 버전), 모델 카드의 실행 방식·수집 경로·웹검색 허용/사용·도구·수집 품질·수집 시각, 답변 상세의 수집 정보(출처의 원래/중계 URL·연결 구절·품질 기록·에이전트 요약·원본 HTML).

## 11. 후속 작업 (5단계 데이터셋·롱 컨텍스트 확대 전)

1. **수집 품질과 평가 품질 분리 지표**: 시스템별 수집 품질(변환 경고·중계 URL 미확인·수집 시각 미기록 비율)을 평가 결과와 따로 집계해, 데이터셋 확대 전에 수집 불량이 점수에 섞이지 않게 한다.
2. **실제 수집 가능한 플랫폼 수**: 지금 바로 = API 3개(기존 연결) + 응답 파일 형식 4종. 파일 기반 = ChatGPT·Claude.ai 공식 내보내기·Perplexity(MD→대화 기록). 보류 = Gemini 앱·Copilot·M365·Mistral 소비자·Liner·국내 서비스. 미팅의 대상 플랫폼 목록 확정이 필요하다.
3. **정책 결정**(4-3): 원문 미확보 INCOMPLETE, 원문 변동 처리, 라벨 분리.
4. **에이전트 기준 후보**: 도구 실패 후 답변의 근거 표시, 조회한 출처와 답변 출처의 일치, 실패 단계 고지 — 공식 기준으로 쓰려면 `criteria_registry` 에 계층·근거 요구를 먼저 정의하고 승인받는다.
5. **스냅샷**: 출처 페이지 변동(GEN-03 유형)에 대비해 수집 시점 원문 스냅샷 참조를 J5 대조에 쓰는 방안(저장·저작권 검토 포함).
6. **확대 시 비용**: 외부 답변은 출처가 많아 J5 원문 대조·검색 비용이 늘어난다. 문항당 판정 비용(3단계 추정 $0.17~0.22)과 처리량 한도를 표본으로 다시 측정한다.
7. UI 스모크 고정 데이터 준비(3단계부터 남은 과제) — 저장소만으로 23개가 돌도록.
