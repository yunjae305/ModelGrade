# 모델 비교 서비스 UI

`start.bat` 또는 `python run.py` 실행 후 [모델 비교 워크스페이스](http://localhost:8080/workspace.html)를 엽니다. 루트 주소도 이 화면으로 연결됩니다. 기존 [평가 상세 도구](http://localhost:8080/code-eval.html)는 유지됩니다.

## 사용 흐름

워크스페이스는 업로드·진행·결과 화면의 반복 설명과 내부 구현 안내를 줄였습니다. 점수 계산법과 결과별 평가자 정보는 펼쳐서 확인하며, 평가자 정보의 펼침 상태는 결과 갱신 중에도 유지합니다. 미완료 사유·오류·실제 처리 수·판정 완료 수·통과율의 분모 안내는 계속 표시합니다. 기존 디자인과 평가 동작은 동일하며 화면 변경은 **Ctrl+F5**로 반영합니다.

서버 터미널에서 **Ctrl+C**를 누르면 새 수집·평가 호출을 중단하고 실행 중인 CLI 및 자식 프로세스를 종료합니다. 완료한 원문과 판정은 유지하며 실행은 `CANCELLED`로 남습니다. 일반 종료 대기는 10초이며, 동기 외부 요청이 끝나지 않으면 저장된 결과를 유지하고 프로세스를 종료합니다. 아직 응답이 없는 요청의 원격 실행·청구 취소를 보장하지 않으며 해당 비용은 터미널에 미확인으로 안내합니다. 서버 재시작으로 중단된 실행을 자동 재호출하지 않습니다.

실행 조회의 연결 오류가 발생하면 화면은 연결 끊김과 마지막 확인 상태를 표시하고 경과 시간을 멈춥니다. GET 조회만 1→2→4→5초 간격으로 재시도하며 연결 복구 후 실제 상태로 갱신합니다. 수집·평가 POST를 자동 재전송하지 않습니다. **전체 평가 시작**은 저장된 답변 전체를 다시 평가하므로 추가 평가 호출이 발생합니다.

업로드하는 자료는 **AIONA 서비스를 이용해 이미 받은 질문과 답변의 Q/A 원문**입니다. 업로드한 AIONA 답변을 그대로 평가 대상으로 보관하며(외부 수집 답변으로 덮어쓰지 않음), 같은 질문만 연결된 AI에 보내 각 AI의 답변을 새로 수집합니다. 2026-10-13부터 새 비교는 **파일 1개 업로드 → 자동 수집 → 질문별 답변 비교 → 평가 시작** 순서입니다.

1. **평가 데이터**: 질문과 AIONA 답변이 함께 있는 JSON·JSONL·MD·TXT 파일을 올립니다. 업로더가 공통 `question`, `answer` 평가 JSON으로 변환하며 회차별 JSON 묶음과 구분 표시가 있는 대화 텍스트도 지원합니다. 파일명과 함께 독립 질문·대화 수(단일 질문 1개 + 2턴 이상 멀티턴 대화 1개), 단일 질문 수, 멀티턴 대화 수(턴 수), 평가 대상 턴 수, AIONA 답변 준비 상태(답변이 있는 턴 / 전체 턴)를 보여 줍니다. 질문 목록은 아래 **질문별 답변 비교**에서 검색하고 펼쳐 봅니다. 파일 변환은 모델을 호출하지 않습니다.
2. **연결·수집 설정(관리 설정)**: Gemini·Claude·GPT·FactChat의 API 키와 정확한 모델 ID를 등록합니다. `python run.py` 또는 `start.bat`으로 시작하면 환경변수와 프로젝트 루트 `.env`의 키·모델(FactChat 은 `FACTCHAT_API_KEY`·`FACTCHAT_MODEL`·`FACTCHAT_BASE_URL`)을 읽습니다. 화면에서 등록한 키는 서버 메모리에만 보관하고 `.env`에 쓰지 않으며, 키 값은 브라우저 저장소·결과 파일에서 제외합니다. 같은 화면의 **자동 수집 허용 · 한도**에서 제공자별 허용, 입력·출력 단가(USD / 100만 토큰), 작업당·일일 최대 호출 수와 비용 한도, 요청당 최대 출력 토큰을 정합니다(`data/auto_collection_policy.json`, 키 없음). 파일이 없으면 모든 제공자의 자동 수집이 꺼진 상태이며, 네 한도와 해당 제공자의 단가가 모두 있어야 자동 수집합니다. 우수AI 는 공개 API·공식 대화 내보내기를 확인하지 못해 "연동 준비 중"으로만 표시합니다(화면 자동화·우회 로그인 없음).
3. **업로드 직후 자동 수집**(`POST /api/comparison/auto-collection/jobs`): 모델 체크박스·수집 시작 버튼 없이, 연결·허용되고 한도 안에 드는 제공자에만 같은 질문을 보냅니다. 요청 1회의 비용 상한은 (질문·같은 대화 앞 턴의 UTF-8 바이트 수 + 앞 턴 답변마다 최대 출력 토큰 + 메시지당 8토큰) × 입력 단가 + 최대 출력 토큰 × 출력 단가입니다. 제공자 하나의 전체 계획이 작업당·일일 한도 안에 들 때만 그 제공자를 시작하고(일부 질문만 잘라 보내지 않음), 요청마다 승인 범위를 다시 확인하며 응답의 실제 사용량으로 정산합니다(사용량이 없으면 상한으로 계산). 같은 업로드(질문·대화 구성·AIONA 답변이 같음)와 새로고침은 기존 작업을 다시 열고 새 요청을 만들지 않습니다. 실패·미수집 답변만 **다시 수집**(`POST /api/comparison/runs/{id}/collect`), 나중에 연결한 제공자의 **수집 시작**, **수집 중단**, 새 실행으로 **새로 수집**은 명시적으로만 합니다(평가 시작 후에는 같은 실행에 답변을 더하지 않음). HTTP 401·403·404·429 는 같은 결과가 반복되므로 그 제공자의 남은 요청을 멈추고 다른 제공자는 계속합니다. 수집 방식은 기존과 같습니다 — 제공자별 작업자가 동시에 진행하고, 같은 대화 안에서는 해당 AI 자신의 앞선 답변을 받은 뒤 다음 턴을 요청하며, 다른 대화·다른 AI·AIONA 답변을 이력에 섞지 않습니다. `COMPARISON_COLLECTION_WORKERS`(1~4, 기본 3)는 제공자별 상한입니다. 원문·원본 응답 JSON을 보존하며 별도 시스템 프롬프트·JSON 출력 강제·자동 재시도는 없습니다. 한 대화의 앞 턴 수집이 실패하면 그 대화의 후속 턴만 건너뜁니다.
   - FactChat 은 모델이 아니라 여러 제공자 모델을 중계하는 OpenAI 호환 게이트웨이입니다. 실행에는 플랫폼(`FactChat API Gateway`)·연결한 모델 ID·모델 ID로 추정한 제공자·응답의 `model` 값·실행 방식(`api`)을 따로 기록합니다. 게이트웨이의 시스템 지시·도구·웹검색 조건을 확인할 수 없어, FactChat 답변이 포함된 실행은 순위를 매기지 않고 의미 평가 문맥의 도구 사용도 '알 수 없음'으로 둡니다.
4. **질문별 답변 비교**: 질문·대화를 접힌 목록으로 보여 주고(10개씩), ID·질문 검색과 "아직 수집되지 않은 답변·수집 오류·멀티턴 대화" 보기를 제공합니다. 펼치면 턴마다 AIONA 원문과 각 AI 답변 원문, 수집 대기·실패 상태를 나란히 보여 주며 **상세 보기**는 기존 원문 비교 창을 엽니다. 수집이 끝나면 **평가 시작**으로 아래 평가를 시작합니다.
5. **평가 시작 → 블라인드 처리 → 모델별 동시 평가**: 수집을 마친 뒤 **평가 시작**을 누르면 AIONA까지 무작위 A~D 별칭을 배정하고, 모델별 CODE·LLM 평가 작업자 4개를 함께 실행합니다. 기본적으로 모델당 LLM 호출 3개씩, 비교 실행당 최대 12개가 동시에 진행됩니다. 이미 수집된 앞선 답변 전체로 이력을 구성하므로 이전 턴의 평가 완료를 기다리지 않습니다. `COMPARISON_SEMANTIC_WORKERS`(4~16, 기본 12)를 모델 수로 균등 배분하고, 실행 시작 시 동시 호출 수를 고정해 `evaluation_execution`에 기록합니다. 같은 평가자 설정을 한 번 확정해 공유합니다. 평가자에게는 모델명·공급자 정보를 보내지 않습니다. Q165라면 총 660개 Q/A가 대상이며, 수집 오류·미완료는 평가 제외로 표시합니다. 화면을 닫거나 새로고침해도 작업은 이어집니다. 수집 중단 시에는 블라인드 배정·자동 평가를 시작하지 않으며, 기존 대기·중단·실패 기록은 “전체 평가 시작”으로 명시적으로 평가할 수 있습니다.

기존 4개 모델 비교 API `POST /api/comparison/runs`는 새 비교 화면에서 더 쓰지 않지만 그대로 남아 있으며(수집 직후 자동 평가) 다음 규칙을 강제합니다. `providers` 생략 시 세 제공자를 모두 사용하며, 빈 목록·일부 모델·중복 모델 요청이나 미등록 키가 있으면 실행 기록을 만들거나 외부 모델을 호출하기 전에 거부합니다. `blind`와 `auto_evaluate`는 항상 활성화합니다. 블라인드 배정은 평가 직전에 한 번 수행하고 재평가할 때도 유지합니다. 이전 UI의 단독 평가 요청을 자동으로 유료 3개 모델 호출로 바꾸지 않고 새로고침을 안내합니다. `GET /api/comparison/info`의 `required_providers`와 `blind_after_collection`으로 서버 버전을 확인하므로, 수정 적용 후 서버를 재시작해야 합니다.

화면은 `/api/comparison/info`의 `evaluation_policy_version: 2`도 확인합니다. 값이 없거나 다른 구버전 서버에서는 새 평가·재평가를 막고 서버 재시작을 안내합니다. 저장 결과 열람과 진행 중인 작업의 조회는 계속됩니다. 화면만 새로고침해 이전 평가 코드로 다시 실행하는 일을 방지합니다.

기존 1~3개 모델 실행 기록은 그대로 열람할 수 있으며 결과 상단에 비교 범위를 안내합니다. **이 원문으로 새 비교 준비**로 원본 Q/A를 새 비교 화면에 다시 불러오면 업로드와 같이 자동 수집 작업을 요청합니다(같은 내용의 작업이 있으면 그 작업을 다시 엽니다). 진행 중인 작업이 끝난 뒤 사용할 수 있습니다. 자동 수집 실행은 연결·허용된 제공자만 포함하므로 4개 미만이어도 이 안내를 표시하지 않습니다.

## JSON·MD·TXT 자동 변환

파일 변환은 로컬 파서로 수행하며 LLM에 재작성을 요청하지 않습니다. 파일 내용의 지시문도 변환 명령으로 실행하지 않습니다. 업로드만으로 답변 수집이나 평가를 시작하지 않습니다.

- 기존 JSON 객체·배열·`{"cases": [...]}`·JSONL: 질문·답변 문자열을 그대로 유지합니다.
- JSON의 `질문`/`답변`, `Q`/`A`, `prompt`/`response` 등의 필드는 공통 이름으로 매핑합니다. 값이 다른 중복 필드나 문자열이 아닌 답변은 임의로 선택하거나 문자열로 바꾸지 않습니다.
- `{"1회차": [...], "2회차": [...]}` 묶음: 각 회차에 별도 `conversation_id`를 부여하고 `turn`이 없으면 항목 순서대로 지정합니다. 기존 턴 번호는 유지하며 누락·중복을 검사합니다. `단일턴` 묶음은 독립 질문입니다.
- `[{"id": 1, "turns": [{"turn": 1, "question": "...", "answer": "..."}]}]` 묶음: 질문·답변 원문을 유지하며 문항별로 펼칩니다. 1턴 묶음은 단일턴, 2턴 이상은 묶음별 별도 대화로 연결합니다. 묶음 ID 중복과 1부터 순서대로 이어지지 않는 턴은 거부하며, 원래 ID와 턴은 변환 출처에도 보존합니다.
- MD·TXT: 줄 시작의 `질문:`/`답변:`, `Q:`/`A:`, `User:`/`Assistant:`, `Human:`/`AIONA:`를 구분 표시로 읽습니다. Markdown 제목·강조·번호 목록 형태의 표시도 지원합니다. 파일 전체가 JSON 또는 JSONL 코드 블록인 Markdown도 읽습니다.
- `# 1회차`, `# 2회차` 등 명시적인 회차 제목이 있으면 해당 회차 안에서 멀티턴으로 연결합니다. `# 단일턴` 제목 또는 회차 표시가 없는 텍스트는 단일턴으로 분류하고, 회차 표시가 없었다는 안내를 표시합니다.
- Q/A 표시와 한 칸의 구분 공백을 분리한 뒤 본문 구간의 공백·CRLF·빈 줄·Markdown·코드 블록을 보존합니다. 코드 블록 안의 Q/A·회차 표시는 구분자로 읽지 않습니다. 텍스트의 `import_span`에는 원문에서 추출한 문자 구간을 기록합니다.

예시:

```text
# 단일턴
Q: 독립 질문 원문
A: AIONA 답변 원문

# 1회차
질문: 첫 질문 원문
답변: 첫 답변 원문
질문: 이어지는 질문 원문
답변: 이어지는 답변 원문
```

업로드 직후 미리보기에는 **ID와 질문 목록만** 표시합니다(첫 4개). 질문을 누르거나 **전체 원문 보기**를 선택하면 질문·AIONA 답변 원문을 확인할 수 있습니다. 답변은 목록에서만 숨기며 평가 입력과 결과 JSON에는 전체를 유지합니다.

전체 Q/A·회차별 원문 확인은 선택 사항입니다. 원문 상세 창의 **업로드 원문 보기**에서 업로드한 파일 전체와 읽기 과정의 안내를 확인할 수 있습니다. 업로드 화면에는 변환 안내·평가 JSON 다운로드·필수 확인 체크를 표시하지 않습니다. 변환 후 실행한 결과의 전체 JSON에도 `input_document`로 업로드 원문을 보관합니다. 원문 문서 전체는 수집 모델이나 LLM 평가자에게 추가로 보내지 않습니다.

질문·답변의 경계가 없는 일반 글, 답변 누락·중복, 닫히지 않은 코드 블록, 서로 충돌하는 회차 정보는 변환을 중단하고 구체적인 안내를 표시합니다. 첫 질문 앞의 제목·설명은 Q/A에서 제외하되 원문에 보관하고 업로드 원문 창에서 제외 사실을 안내합니다. 표 형식 Markdown이나 임의의 복잡한 문서 구조는 지원하지 않으므로 Q/A 표시를 추가해야 합니다. UTF-8과 BOM이 있는 UTF-16 파일을 읽고, 해석할 수 없는 인코딩은 대체 문자로 손상시키지 않고 UTF-8 저장을 안내합니다.

`POST /api/comparison/dataset`은 기존 `cases`와 함께 `import` 메타데이터를 반환합니다. 지원하는 모든 형식은 사용자 확인 체크 없이 자동으로 읽습니다. 변환 검사: `tests/test_dataset_import.py`, 실제 브라우저 경로: `tests/workspace_import_ui_smoke.py`이며 외부 유료 호출은 하지 않습니다.

추가 자료 `data/code_eval/AIONA_winz_단일28_멀티10-30_질문30_id_turns.json`은 첨부 원본 그대로 보관했습니다. 30개 묶음 안에 단일턴 28개와 10턴·30턴 대화가 있어 총 68개 Q/A입니다. 워크스페이스에서 이 파일을 그대로 업로드할 수 있으며, 기본 Q165 자료나 AIONA 버전 지정은 변경하지 않습니다. 이 자료의 업로드·원문 탐색은 `tests/workspace_input_ui_smoke.py`에서도 확인합니다.

롱 컨텍스트(J6) 대화 세트 `examples/AIONA_winz_longctx_J6_v1.json`은 J6 세부 기준(J6-1 지시 유지·J6-2 정보 기억·J6-3 변경·반복 수정·J6-4 자기 일관성)마다 대화 6개씩 24개 대화·231턴으로, Q165·공개 예제와 같은 평탄 행 형식(`id`·`conversation_id`·`turn`·`question`·`answer`)이며 J6 대상(2턴 이상)은 207턴입니다. 턴마다 어떤 점검 항목이 적용되고 그 근거가 이전 어느 턴의 어느 문구인지는 같은 이름의 `examples/AIONA_winz_longctx_J6_v1.expect.json`에 두어 테스트와 사람 검토의 정답지로만 쓰고, 평가 입력·run 기록에는 섞이지 않습니다. AIONA 답변은 아직 수집 전이라 `answer`가 비어 있으므로 파일 업로드로 형식만 확인하고 수집 전에는 비교 평가를 돌리지 않습니다. 구성·수집 절차는 [롱 컨텍스트 세트 안내](LONGCTX_J6_DATASET.md)에 있으며, `py -3 -X utf8 -m pytest -q tests/test_longctx_j6_dataset.py`가 형식·턴 순서·ID 분리·업로드 호환·J6 라우팅·expect 인용 일치·항목별 기대 적용 30 이상을 모델 호출 없이 검사합니다.

## 의미 평가 처리 속도

- 의미평가 동시 호출의 기본값과 `.env.example` 설정은 네 모델 합계 12개(모델당 3개)입니다. `.env` 또는 실행 프로세스 환경에 설정하며, 설정을 생략해도 클래스 기본값 12개를 적용합니다. 제공자 동시 호출 제한이나 429 응답이 발생하면 `COMPARISON_SEMANTIC_WORKERS=8`로 낮춥니다. 4로 설정하면 모델당 1개입니다. 서버 시작 시 읽으며 진행 중인 실행의 설정을 바꾸지 않습니다. 동시성 변경은 전체 호출 수·평가 모델·원문·판정 기준을 바꾸지 않습니다.
- J5는 모든 사실 주장을 계속 검토합니다. 동일한 사실을 묶어 검색하고 이미 읽은 직접 근거를 재사용하며, 근거가 충분한 주장에 대한 중복 검색을 줄입니다. 상충·시점·적용 범위가 불명확하면 추가 검증하고, 근거 부족은 기존대로 `UNVERIFIED`입니다. 당시 평가자는 OpenAI API `gpt-6.1-sol · medium`이었고 현재 평가자는 [현재 설정](#현재-설정-2026-10-12-claude-api--claude-opus-55) 절을 따르며, 동시성 변경에서도 평가자 설정과 전체 대화 이력·원문 인용 검증은 유지합니다.
- `evidence-v3.4-task-input-content`부터 질문에 주어진 값은 요약·추출뿐 아니라 이메일·메시지 작성, 계산의 입력값, 가상 계획의 상태 유지·변경에서도 사용자 원문과 대조합니다. 현재 요청의 정확한 인용과 지정된 사용자 원문·턴의 인용을 함께 확인합니다. 현실의 진위를 묻는 요청이나 답변에 추가된 외부 사실은 이 경로로 통과시키지 않습니다.
- `history-quotes-v2-current-relevance`는 전체 대화를 검토하면서 현재 답변에 적용되는 최신 유효 조건을 인용합니다. 폐기되었거나 현재 과업과 무관한 과거 조건을 기계적으로 재기재하게 하지 않습니다. PASS에는 현재 답변의 정확한 인용이 필요하며 실제 필수 내용 누락은 FAIL로 평가합니다.
- 출처 본문은 성공적으로 읽은 공개 자료에 한해 메모리에 최대 5분 재사용합니다. 동시 요청의 같은 URL 다운로드를 합치고, 실패는 캐시하지 않습니다. 각 평가의 검색 기록에 포함된 URL인지 확인하고 해당 답변의 인용문은 매번 대조합니다. 모델별 판정 결과 자체는 공유하지 않습니다.
- 검색 정책은 `J5_without_reference_grouped_evidence_v3`, 근거 검증 정책은 `evidence-v3.3-input-source-content`로 기록하여 이전 정책과의 평가 조건 차이를 버전 비교에서 확인할 수 있습니다.
- OpenAI API는 첫 요청이 정상 종료했지만 J5 사실 주장이 보류로 남으면 `j5_targeted_evidence_v1` 정책으로 **미확인 근거를 한 번 추가 검증**합니다. 원본 질문·답변·이력과 최초 평가 시각을 유지하고 J5만 요청합니다. 기존 PASS/FAIL 주장과 다른 기준은 유지하며, 주장 삭제·변경·해당 없음으로 보류를 지우지 않습니다. 새 근거도 검색 기록과 실제 원문 인용을 확인한 뒤 반영합니다.
- 추가 검증은 참조 자료가 없는 웹검색 평가에만 적용합니다. 기본 설정은 `SEMANTIC_API_EVIDENCE_RECOVERY_ROUNDS=1`(0으로 비활성), 추가 API 제한 시간 `SEMANTIC_API_EVIDENCE_RECOVERY_TIMEOUT=120`초, 도구 호출 상한 `SEMANTIC_API_EVIDENCE_RECOVERY_MAX_TOOL_CALLS=6`입니다. 첫 요청의 제한 시간과 별도이며 각 단계의 출처 본문 대조는 기존 제한을 따릅니다. 따라서 보류 대상은 시간·사용량이 추가될 수 있습니다. HTTP 오류·거절·잘못된 최초 응답은 자동 재시도하지 않습니다.
- 추가 검증이 실패해도 최초 판정·근거를 보존하고 `verification.evidence_recovery`에 최초/추가 J5, 성공·미해결·오류 상태와 검증 기록을 남깁니다. 실제 요청별 사용량은 모두 합산하며 요청은 최대 2회입니다. 확인 가능한 오류 하나가 있으면 FAIL, 모든 주장이 검증되면 PASS, 끝내 확인하지 못하면 사유를 유지합니다. 변경된 검증 정책과 한도는 평가 조건에 포함되어 이전 정책의 결과와 구별됩니다.
- 최초 검색에서 실제로 관측한 출처는 추가 검증에 재사용할 수 있습니다. 모델이 임의로 적은 URL은 인정하지 않고, 재사용한 인용문도 본문과 다시 대조합니다. `tests/live_j5_recovery_check.py --live --run-id <단일 질문 실행 ID> --provider gpt`는 저장된 보류 판정에서 추가 검증만 한 번 실행하는 유료 점검 도구입니다. 원본은 변경하지 않으며, 별도 `results/j5-recovery-review/`에 최초·추가 판정과 원본 해시를 보관하고 비용은 터미널에만 출력합니다.
- 의미 평가의 소요 시간은 문항의 주장 수·검색·제공자 응답 시간에 따라 달라집니다. 동시성 확대가 실제 완료 시간을 정확히 절반으로 줄인다는 보장은 없습니다.
- 백엔드 개선은 서버를 다시 시작한 뒤 새로 시작하는 평가부터 적용합니다. 진행 중인 평가는 기존 설정으로 이어갑니다.

## 블라인드 평가와 네 모델 비교

새 화면에서 시작한 비교는 모델을 무작위 **모델 A·B·C·D**로 배정합니다. 배정과 평가 순서는 실행 기록의 `blind`에 저장되어 새로고침·재평가·기록 재열기 후에도 유지됩니다. 수집은 각 제공자에게 정상 모델 ID로 요청하고, LLM 평가자에게는 질문·답변·동일 모델의 이전 Q/A·참조 데이터만 제공합니다. 모델명·공급자·원본 응답의 모델 메타데이터·수집 API 키는 LLM 평가 요청에 넣지 않습니다. 한 비교의 모든 모델은 같은 평가자 연결·모델·추론 설정을 사용합니다. 현재 평가자 설정은 [현재 설정](#현재-설정-2026-10-12-claude-api--claude-opus-55) 절을 따릅니다(OpenAI API 는 대안 설정).

원문 보존이 우선이므로 질문·답변·참조 데이터 안의 이름은 지우지 않습니다. 블라인드는 평가 입력의 별도 모델 정보와 결과 화면의 이름 표시에 적용합니다. 전체 JSON·모델별 원문 JSON에는 재현을 위한 실제 제공자 정보와 원본 응답이 들어가므로 익명 공유용 파일이 아닙니다.

결과 화면은 **최종 요약 → 상세 평가 내역 → 모델별 카드 → 기준별 비교표 → 질문별 결과** 순서로 보여줍니다. 최종 요약에서 이번 질문 묶음의 최고점과 AIONA의 위치를 먼저 확인한 뒤 아래에서 판정 근거를 확인할 수 있습니다.

모델별 카드의 문항 상태는 FAIL·PASS·미완료·평가 중·평가 대기 중 하나로만 집계합니다. 확정 FAIL이 하나라도 있으면 문항은 FAIL이며 다른 기준의 미판정은 상세에 남깁니다. PASS는 적용된 모든 기준을 통과해야 합니다. 요청 처리 수와 문항 최종 판정 수를 구분합니다. **기준별로 나란히 비교** 표는 공통 CODE 1~3과 J1~J8을 표시하며, CODE는 조건 수, 의미 기준은 질문 수입니다. 미판정 또는 집계 대기가 남으면 통과율은 **미확정**입니다. 해당 없음은 PASS가 아닙니다. AIONA 특화 2항목은 **평가 대기·현재 미실시**이며 웹 평가에서 실행하지 않고 점수·완료율에서 제외합니다.

의미 기준의 **미판정**은 원인별로 **확인 필요**(평가가 응답했지만 근거가 부족함), **평가 오류**(호출·시간 초과·잘못된 평가 응답), **판정 누락**(정상 응답에 해당 기준의 확정 판정이 없음)으로 구분합니다. 이 세부 수는 미판정 총수의 구성이지 추가 건수가 아닙니다. 진행 중·제외는 기존대로 별도 표시합니다. 같은 답변의 호출 오류는 요청된 여러 기준에 나타날 수 있습니다. 예를 들어 GPT 답변 Q17_T1의 평가 응답 하나가 실패하면 J1·J3·J5에 각각 미판정 1건으로 집계됩니다.

표에서 PASS 7·FAIL 0·대상 34·미판정 27이면 비율은 **미확정**으로 표시합니다. 모든 적용 항목이 판정된 뒤 PASS ÷ (PASS + FAIL)을 표시합니다. 미완료 사유는 읽히는 문장(예: '질문에 준 값을 근거로 인정할지 서버가 판단하지 못함')과 건수로 묶고, 미완료는 답변 오류가 아니라 PASS·FAIL 근거를 확보하지 못한 상태라는 한 줄을 붙입니다. 전체 설명은 접힌 상세에 보존합니다. 답변 원문에서 위치를 가리킬 수 없는 FAIL 은 이유를 구분합니다: CODE 는 '요구: … · 실제: …', 누락형 의미 판정은 '빠진 내용', 평가 쪽 검증 실패(확인 불가)는 위반 구간으로 표시하지 않습니다. 평가 정책을 변경해도 기존 실행의 판정을 자동으로 덮어쓰지 않습니다.

### 최종 요약과 질문 통과점수 (2026-10-08)

최종 요약은 **한 문장 결론**, 점수순으로 정렬된 실제 모델명·모델 ID·순위·점수·PASS/FAIL 문항 수, 산식을 표시합니다. 점수는 `적용된 공통 CODE·LLM 기준을 모두 통과한 질문 수 ÷ 전체 질문 수 × 100`입니다. 질문 수는 단일 질문 1개 + 멀티턴 대화 1개(턴 수와 무관)로 세고, 대화는 모든 턴이 통과해야 통과입니다(한 턴이라도 FAIL 이면 FAIL, FAIL 없이 남은 턴이 있으면 미완료 — 2026-10-13 결정). 동일한 입력 문항 전체를 분모로 사용하며 문항마다 가중치가 같습니다. 질문별 결과 표와 '판정 완료 답변'은 턴(답변) 단위입니다. 아래 카드의 **공통 코드 조건 통과율**은 조건 단위 지표이므로 이 점수와 구분합니다.

- 모든 모델의 질문·대화 구성과 문항 수가 일치하고, 모든 문항이 PASS 또는 FAIL로 확정된 `COMPLETED` 실행에만 점수·순위를 확정합니다. FAIL이 확정된 문항에 남은 미판정 기준은 상세에서 계속 확인할 수 있습니다. 문항의 결과를 결정하지 못했으면 분모를 줄이지 않고 **최종 점수 미확정**과 남은 문항 수를 표시합니다. 진행 중에는 최종 요약을 표시하지 않습니다.
- 동점은 반올림 전 PASS 문항 수로 판단해 공동 순위로 표시합니다. 과거 단독 실행은 점수만 보여주고 다른 모델과 비교하는 순위를 붙이지 않습니다.
- **FAIL N문항 확인**을 누르면 아래 질문별 결과에 해당 모델·FAIL 필터를 적용합니다. 모든 문항을 통과했으면 통과한 문항으로 이동합니다.
- 점수는 이번 질문 묶음의 통과 결과입니다. 기준별 적용 수는 답변에 따라 다를 수 있으며 비적용 기준을 추가 PASS로 세지 않습니다. AIONA 내부 마커·금지 표현 등 특화 규칙은 제외합니다.

저장된 실제 Q165 비교 `a3b5d89bc041`에서는 GPT **98.2점(162/165)**, AIONA **96.4점(159/165)**, Claude **86.7점(143/165)**, Gemini **53.3점(88/165)**입니다. 네 모델 모두 165문항 평가 완료 상태입니다. 기존 CODE·LLM 판정으로 계산하며 새 평가나 모델 호출을 하지 않습니다. 저장 파일·원문·판정·평가자 입력은 그대로 유지합니다. 화면 변경은 **Ctrl+F5**로 적용합니다.

코드가 판정한 PASS/FAIL은 유지합니다. `UNSUPPORTED` 등으로 판정하지 못한 공통 조건만 기존 의미 평가 호출에 `C` 기준으로 추가하여 동일 평가자가 원문 전체로 판정합니다. 당시 연결은 OpenAI API `gpt-6.1-sol · medium`이었습니다(현재 평가자는 [현재 설정](#현재-설정-2026-10-12-claude-api--claude-opus-55) 절). 질문당 추가 호출은 만들지 않았으며, J1~J6 의미 기준과 보완 조건의 결과를 분리합니다. 내부 마커·금지 표현은 이 보완 대상에서 제외합니다.

부분 문장 수, 혼합 자료형 정렬, YAML 내부 목록, 단위·부정 문맥을 포함한 등식 등에 적용합니다. 조건 식별 정보와 기존 소분류의 기준을 제공하고, 확정된 코드 판정·측정값·공급자 메타데이터는 평가자에게 전달하지 않습니다. 질문·답변·이력·참조 데이터는 자르지 않습니다. 보완 응답에는 PASS/FAIL·확신도·구체적인 근거가 필요합니다.

원본 CODE `cases`·`summary`·`result_digest`는 보존하고, `jev_eval.records[].code_completion`에 보완 판정·근거·최종 표시용 결과를 저장합니다. 워크스페이스, 상세 화면, HTML 보고서와 종합 집계는 보완 결과를 반영합니다. JSON의 원본 CODE 미판정 값은 감사용 기록이며, 최종 판정은 함께 저장된 `code_completion`을 확인합니다.

적용된 공통 조건과 의미 기준을 모두 판정한 질문만 PASS로 집계합니다. 하나라도 FAIL이면 FAIL이며, 수집 실패·평가 시간 초과·잘못된 응답은 품질 FAIL로 바꾸지 않고 평가 미완료로 표시합니다. 단일턴 J6 등 적용 대상이 없는 기준은 ‘해당 없음’을 유지합니다. 이 동작은 **서버 재시작 후 새 평가부터** 적용되며, 기존 실행을 자동 재평가하거나 수집 실패 6건을 자동 복구하지 않습니다.

검증: 전체 pytest **381 passed**, 4개 모델 브라우저 흐름(48개 대역 판정), 보완 FAIL 3건 상세 화면의 데스크톱·모바일 표시를 확인했습니다. 기존 Q165 저장 데이터의 654개 정상 답변을 모의 평가자로 검증해 코드 미판정 29개(AIONA 4·Gemini 6·Claude 7·GPT 12)가 보완 경로에서 처리됨을 확인했습니다. 실제 품질을 다시 판정한 결과가 아니며 유료 호출 없이 원본 파일 해시를 유지했습니다.

평가 작업이 `COMPLETED`가 되면 카드·기준 비교표·질문별 결과·상세 탭·평가 기록에 **AIONA·Gemini·Claude·GPT의 실제 이름을 자동으로 표시**합니다. 카드에는 해당 실행에서 사용한 모델 ID도 표시합니다. 완료 전에는 모델 A·B·C·D를 유지하며, 화면에 공개한 뒤에도 저장된 별칭 배정과 LLM 평가 입력은 변경하지 않습니다. 새로고침·기록 재열기에서도 완료 결과는 실제 이름으로 열립니다. 검색·필터·다운로드·기록 조회는 모델을 다시 호출하지 않습니다. 예전 실행은 당시의 모델 ID와 결과를 그대로 표시합니다.

각 모델 카드 아래의 **답변 수집 시간**은 해당 제공자의 수집 작업 시작부터 종료까지 걸린 시간입니다. 요청·응답 대기와 수집 처리 시간을 포함하고, 다른 모델을 기다리는 시간이나 이후 평가 시간은 포함하지 않습니다. 수집 중에는 1초마다 `분:초`로 갱신하며 먼저 끝난 모델은 즉시 멈춥니다. 완료·취소·오류로 종료된 시간은 기록에 저장되어 새로고침 후에도 유지됩니다. AIONA는 이미 받은 답변을 업로드하므로 **업로드 원문 · 수집 없음**으로 표시합니다.

새 수집 결과의 `collection.latency_ms`는 개별 요청을 시작해 응답 처리가 끝날 때까지의 시간이며, 작업자 대기열과 결과 파일 저장 시간은 제외합니다. 병렬 요청의 개별 시간을 더한 값은 실제 전체 경과 시간과 다릅니다. 제공자 전체 수집 시간과 요청별 시간 분포를 함께 확인해야 합니다.

시간 기록이 없는 이전 실행은 **시간 기록 없음**, 서버 중단으로 정확한 종료 시간이 없는 실행은 **마지막 기록**으로 표시합니다. 과거 실행의 소요 시간을 임의로 추정하지 않습니다. 수집 시간 저장은 서버 재시작 후 새 실행부터 적용됩니다.

`POST /api/comparison/runs`에 `blind: true`, `auto_evaluate: true`를 보내는 것이 새 UI의 실행 경로입니다. 두 값을 생략한 기존 API 호출은 수동 흐름을 유지합니다. `GET /api/comparison/info`로 기능 버전을 확인하며, 이전 서버에는 새 UI의 실행 버튼을 활성화하지 않고 재시작을 안내합니다. 잘못된 평가 설정은 응답 수집 API를 호출하기 전에 거부합니다.

## 파일과 대화 원문 탐색

- 업로드 후 질문·AIONA 답변·멀티턴 대화 수를 표시합니다. 멀티턴 대화 카드를 누르면 해당 대화의 첫 턴부터 원문을 확인합니다.
- 원문 창의 **대화 선택**에서 전체 Q/A, 단건 질문 또는 개별 대화를 선택할 수 있습니다. 개별 대화의 이전·다음 이동은 파일 순서와 관계없이 턴 순서를 따릅니다. 모델 탭 선택은 질문을 이동해도 유지합니다.
- 현재 대화의 턴과 앞선 턴 수를 표시합니다. 질문과 답변 원문은 길이 제한 없이 표시하며, 복사도 원문 전체를 사용합니다. 질문 선택 목록의 짧은 미리보기는 입력 문자열을 변경하지 않습니다.
- 파일 확인 중에는 진행 안내를 표시하고 실행 버튼을 잠시 비활성화합니다. 잘못된 교체 파일을 올려도 기존 정상 파일은 유지합니다. 빠르게 여러 파일을 올리면 가장 최근 파일의 결과만 적용합니다.
- 실행 버튼 영역은 본문 뒤에 배치해 파일·설정 내용을 가리지 않습니다. 모바일에서는 실행 기록과 질문별 결과를 세로로 표시합니다.

## 원문과 비교 기준

- 질문과 응답의 공백·CRLF·줄바꿈·코드 펜스·리터럴 `\n`을 보존합니다. UI 미리보기의 말줄임이나 원문 보기의 화면 줄바꿈은 평가 입력을 바꾸지 않습니다.
- 공급자 응답의 텍스트 블록만 순서대로 연결해 `answer`에 보관하고, 받은 응답 JSON 전체는 `collection.raw`에 별도로 보관합니다. 추론·thinking 블록은 답변 텍스트에 섞지 않습니다.
- `conversation_id`와 `turn`이 있으면 1부터 연속된 고유 턴이어야 합니다. 원래 파일 순서는 유지하고 요청만 턴 순서로 진행합니다. 각 모델 자신의 앞선 답변을 사용하며 AIONA의 답변을 다른 모델의 이력으로 보내지 않습니다.
- 의미 평가에도 같은 대화의 이전 질문·답변 전문을 그대로 전달합니다. 이력 길이에 따른 축약·요약·턴 생략은 하지 않습니다. 제공자가 요청을 처리하지 못하면 호출 오류로 기록합니다. Q165의 구성과 J6 대상은 [Q165 데이터셋 안내](Q165_DATASET.md)에서 확인할 수 있습니다.
- 공통 CODE 조건 통과율은 `PASS / (PASS + FAIL)`입니다. 질문별 결과 건수와 코드·의미 평가 완료 수를 먼저 표시하고, 조건 통과율은 보조 지표로 표시합니다. AIONA 특화 판정은 공통 비교 지표에 더하지 않고 기존 상세 화면에서 확인합니다.
- 네트워크 오류, 제공자가 차단한 응답, 출력 한도로 끊긴 응답, 중단으로 아직 수집하지 못한 질문은 평가에서 제외합니다. 빈 답변의 품질 FAIL로 바꾸지 않습니다. 부분 답변과 오류 사유는 보관합니다.
- 모델별 다운로드는 같은 `question`·`answer` 입력 JSON 형식이며, 원래 질문 수와 순서를 유지합니다. 수집 미완료 항목에는 평가 제외 표시를 넣어 기존 CLI·상세 도구에 다시 입력해도 `INPUT_ERROR`로 구분합니다.

## 결과를 읽는 방법

### 문항 × 기준 실시간 진행 (2026-10-08)

기존 진행 카드 안에 **평가 롤링 줄과 접고 펴는 평가 기록**을 추가했습니다. `모델 B · Q009 · 2-1 분량·표현 조건 기준 평가 중…`처럼 실제 별칭·문항 ID·기준명을 보여줍니다. 이름은 현재 CODE 1-1~3-3 및 의미 기준 J1~J6에서 가져옵니다. 기존 코드·LLM·공통 조건 보완 평가를 그대로 호출하며 이벤트만 추가합니다. 여러 의미 기준을 같은 LLM 요청에 넣으면 **의미 평가 응답 대기 · 여러 기준 함께 평가**로 표시합니다. 특정 기준명이나 검색 단계를 실제 CLI 진행 상황처럼 표시하지 않습니다. 완료 응답이 돌아와야 처리 수가 증가합니다.

- 수신 방식: `GET /api/comparison/runs/{run_id}/events`의 SSE. 연결 시 누적 `snapshot`을 받고, `run_start`, `q_start`, `criterion_start`, `criterion_end`, `criterion_result`, `q_done`, `q_skip`, `run_done` 또는 `run_error`를 받습니다. 문항 식별은 별칭과 입력 인덱스를 사용하므로 중복 Q번호도 별개로 집계합니다.
- 카운터·진행 바·기록은 실제 수신 이벤트로 즉시 갱신합니다. 모델별 문항 수를 합산하므로 Q165의 4개 모델 비교는 660개입니다. 제외·오류도 처리 수에 포함되며, 품질 PASS와는 다릅니다. PASS/FAIL/미판정 합계는 공통 CODE·보완·LLM 기준의 조건 수입니다. 특화 내부 마커·금지 표현은 여기에 더하지 않습니다.
- 한 롤링 줄은 최소 350ms, 진입·퇴장 동작은 320ms입니다. 큐가 10개를 넘으면 기준 시작 줄을 생략하고 문항 완료·제외를 우선합니다. 50개를 넘으면 롤링을 생략하고 최신 집계를 보여줍니다. 종료 이벤트를 받으면 큐를 비우고 즉시 최종 상태로 고정합니다. 평가 작업에 인위적인 지연은 없습니다.
- 평가 기록은 최대 높이 320px의 내부 스크롤로 표시합니다. 문항을 펼치면 기준·판정·근거가 보입니다. 사용자가 위로 스크롤하면 자동으로 아래로 이동하지 않습니다. 완료 카드 클릭·키보드 Enter로 기록을 열 수 있으며, 모션 감소 설정에서는 텍스트만 교체합니다. 다크모드도 지원합니다.
- 보완 판정은 같은 조건 키를 갱신합니다. 처음의 UNJUDGED와 최종 PASS/FAIL을 이중 집계하지 않습니다. 수집·평가 오류는 실제 제외·미판정 사유로 기록합니다.
- 이벤트 재전송 버퍼는 최근 512개로 제한합니다. `Last-Event-ID`로 재연결하고, 버퍼 범위를 벗어나면 전체 문항 스냅샷으로 복구합니다. 누적 기록은 실행 JSON의 `evaluation_log`에 함께 저장하며 단순 상태 폴링에서는 제외합니다. SSE 접속을 끊어도 평가 작업은 취소되지 않습니다. 과거 실행에 없는 이벤트를 지어내지 않습니다.

**데모**: 서버 실행 후 [평가 진행 데모](http://localhost:8080/evaluation-demo.html). 10문항·문항당 0~5개 무작위 기준, 일부 제외, 느린 표시와 실제 속도 토글을 제공합니다. 정적 HTML·JS·CSS만 사용하므로 평가 백엔드나 모델 API 없이도 정적 서버로 확인할 수 있습니다.

전체 비교 흐름은 `python -X utf8 tests/workspace_blind_ui_smoke.py`, 데모·350ms 표시·1,500문항·스크롤 유지·다크모드·모션 감소는 `python -X utf8 tests/evaluation_stream_ui_smoke.py`로 검증했습니다. 전체 pytest는 **386 passed**입니다. 모두 대역을 사용했으며 실제 유료 호출은 없습니다.

평가 중에는 **실시간 진행** 영역을 1초마다 확인합니다. 코드 검사 처리 수, 의미 평가 처리 수, 판정 완료·호출 오류·제외 수, 평가 경과 시간과 현재 처리 중인 질문 ID를 표시합니다. 질문의 의미 결과가 도착하면 전체 모델의 평가 종료를 기다리지 않고 카드·질문별 결과·원문 창의 판정에 반영합니다. 검색·필터·키보드 포커스는 갱신 중에도 유지합니다.

처리 수에는 근거 보류·오류·제외도 포함됩니다. **판정 완료**는 적용된 의미 기준을 모두 확정했다는 뜻이며 답변의 품질 PASS만 세는 수가 아닙니다. 전체 질문의 코드·의미 판정을 모두 끝냈는지는 **평가 완료 수**로 따로 표시합니다. 평가 중인 질문은 보라색 **평가 중**, 아직 요청하지 않은 질문은 **평가 대기**, 실패한 호출은 **평가 미완료**로 구분합니다. 이미 확인된 위반이 있으면 처리 중이어도 **문제 발견**을 우선 표시합니다.

상단 진행 막대는 평가 시작부터 종료까지 **코드+의미 검사 단계 처리 수**를 유지합니다. 코드·의미 처리 카드도 종료 후 숨기지 않고 마지막 처리 수와 판정 완료·확인 필요·오류·제외 내역을 유지합니다. 모델 카드의 큰 숫자는 평가가 시작된 뒤 계속 **의미 평가 처리 수**입니다. 코드 단계에서 의미 단계로 넘어갈 때나 전체 작업 종료 시 다른 단위로 바꾸지 않습니다. 예를 들어 272개 답변을 모두 처리했지만 109개가 보류·오류이면 의미 처리 수는 **272/272**, 별도의 판정 완료는 **163개**입니다. 이 경우 전체 처리 막대가 끝까지 찼어도 최종 점수·순위는 미확정입니다. 종료한 실행의 경과 시간은 마지막 저장된 처리 시각으로 고정하며 시간 기록이 없는 과거 실행은 임의로 생성하지 않습니다.

진행 중 새로고침하거나 실행 기록에서 다시 열어도 같은 작업의 진행을 이어서 조회합니다. 이 조회는 평가나 모델 호출을 다시 시작하지 않습니다. 부분 결과에는 `live: true`를 표시하며, 완료된 질문을 포함한 진행 스냅샷은 약 1초 간격과 종료 시에 저장합니다. 진행 중인 부분 평가 보고서는 최종 보고서로 다운로드할 수 없습니다. 전체 원문 JSON은 계속 다운로드할 수 있습니다. 서버가 중단되면 보관된 결과를 유지하고 남은 요청은 중단으로 표시합니다.

진행 기능은 백엔드 변경이므로 서버 재시작 후 새로 시작한 평가부터 적용됩니다. 이전 코드로 이미 시작한 평가는 종료한 뒤 서버를 재시작해야 하며, 실행 중인 평가를 자동 중단·재평가하지 않습니다.

질문별 결과와 평가 완료 여부는 별개입니다. 모델별 카드의 건수는 질문 수이며, 코드 조건 통과·문제·판정 불가 수는 검사 조건 수입니다.

| 결과·완료 표시 | 표시 조건 |
|---|---|
| FAIL · 문제 발견 | 공통 코드 검사 또는 의미 기준에서 하나 이상의 FAIL이 확인됨(옛 기록의 LLM 보완 FAIL 포함). 다른 평가가 남아 있어도 확인된 문제를 먼저 표시 |
| PASS · 확인된 문제 없음 | 적용된 공통 조건과 의미 기준을 모두 판정했고 FAIL이 없음. 공통 검사 범위의 결과이며 모든 내용의 정확성을 보장하는 표시는 아님 |
| 평가 미완료 수·필터 | 수집 실패·입력 오류·호출 실패·연결 없음·시간 초과·확인 필요·보완 판정 누락 등이 남아 있음. 확인된 FAIL이 있는 질문도 포함하며, 질문의 대표 결과는 FAIL을 우선 표시 |
| 평가 대기 | 아직 평가를 시작하지 않음 |

- 최종 비교 요약의 **평가 완료 수**는 코드 조건과 의미 기준을 모두 판정한 질문 수입니다. FAIL이 있는 질문도 모든 판정이 끝났으면 완료 수에 포함합니다. 모델 카드의 큰 처리 숫자와 별개로, 하단에는 **의미 평가 완료** 수를 표시합니다.
- **FAIL 수와 평가 미완료 수는 겹칠 수 있습니다.** 확인된 문제와 남은 판정을 별도로 세므로 두 수를 더해 전체 질문 수로 해석하지 않습니다. 미완료 필터에서도 이미 FAIL이 확인된 질문의 남은 평가를 확인할 수 있습니다.
- 작업이 끝났어도 완료하지 못한 질문이 있으면 **평가 미완료**로 표시합니다. 실행 기록의 **평가 작업 종료**는 처리 작업의 종료만 뜻합니다.
- 의미 평가 미완료는 호출 실패·사용 한도·연결 필요 등 사유와 건수를 보여줍니다. 코드 조건 판정 불가도 별도 건수로 표시합니다.
- 예를 들어 Q100에서 코드 문제가 2개 질문에 있고 의미 호출 100건이 모두 실패하면 **문제 발견 2개 / 확인된 문제 없음 0개 / 평가 미완료 100개**, 평가 완료 **0/100개**입니다. 미완료 100개에는 문제 발견 질문 2개도 포함됩니다. 두 질문의 대표 결과는 FAIL로 유지됩니다.
- 카드의 결과 건수를 누르면 해당 모델·결과의 질문만 표시합니다. 모델·결과 선택과 ID·질문 검색을 함께 사용할 수 있습니다. 전체 모델 필터에서는 한 질문에 문제 발견이 있으면 우선 분류하고, 그다음 판단 보류·평가 대기·확인된 문제 없음 순서로 분류합니다.
- 질문의 결과를 누르면 선택한 모델의 코드·의미 상태, 문제 조건·판정 불가 사유, 의미 FAIL 이유와 오류 원문을 답변 원문 위에 보여줍니다. 모바일은 질문 아래에 모델별 결과를 세로로 배치합니다.
- 표시 변경은 저장된 판정·질문·답변을 변경하지 않으며 모델을 다시 호출하지 않습니다.

## 실행 기록 및 범위

실행 기록은 `data/comparison_runs/{run_id}.json`에, 평가 결과는 기존 `data/code_eval_runs/`에 저장됩니다. 전체 JSON에는 모델별 데이터셋과 공급자 원본 응답, 평가 결과가 함께 들어갑니다. 서버를 다시 시작해도 기록은 열 수 있으며, 진행 도중 재시작한 기록은 실행 중단으로 표시합니다. 화면에서만 등록한 API 키는 재등록해야 하며, 환경변수 또는 `.env`에 키·모델이 있는 경우 서버 시작 시 자동 등록합니다.

이 구현은 기존 localhost 서비스 안의 작업 화면입니다. 의미 평가 연결은 `.env`의 선택 엔진 설정을 사용하며, 평가 모델 설정은 응답 수집 모델 설정과 구분합니다. 현재 OpenAI 평가는 `SEMANTIC_API_KEY`를 사용합니다. 2026-10-12 사용자의 GPT 평가자 전환 요청에 따라 이미 등록된 OpenAI 키를 이 평가용 변수에도 명시적으로 지정했습니다. 수집 키를 자동으로 대신 사용하는 fallback은 없습니다. 실제 공급자 호출과 의미 평가의 정상 작동은 사용 가능한 키·모델·평가 연결로 확인해야 합니다. 배포·다중 사용자 계정·화면에서 입력한 키의 영구 저장은 지원하지 않으며, 사용자가 직접 저장한 로컬 `.env` 설정을 읽습니다.

요청마다 독립된 임시 폴더에서 사용자 CLI 설정을 제외하고 읽기 전용 샌드박스를 사용합니다. AGENTS.md 로딩·셸·브라우저·컴퓨터 제어·플러그인·앱·하위 에이전트 등 평가에 불필요한 기능은 끕니다. 사용자 승인에 따라 **J5가 포함되고 참조 자료가 없으며 검색 설정이 `live`인 요청에만** `code_mode`와 `code_mode_host`를 허용하여 웹검색을 사용할 수 있게 합니다. 다른 요청에서는 두 기능도 끕니다. - 버전 관리의 세 요약 카드와 표에서 기본 버전, 등록 수, 기본 버전의 최근 평가, 버전별 실행 수를 확인합니다. 상세 창은 변경 설명·등록 시각·등록 사유·연결 실행·기본 평가 버전 변경 기록(시각·이전 버전·사유)을 보여주며 버전별 점수를 합산하지 않습니다.
- **이력 관리**는 평가가 끝난 결과 비교마다 쌓인 AIONA 결과 기록입니다(완료 시각·AIONA 버전·질문 세트·평가 조건·AIONA 질문 통과율·직전 기록 대비 변화). 실행명·ID, AIONA 버전, 질문 세트, 기간으로 필터링하고, 상세에서 직전 기록 대비 바뀐 요인(기준 변경·평가 모델 변경·AIONA 버전 변경·같은 버전의 AIONA 답변 변경)과 바뀐 항목·기준별 통과율 변화·기준 변경 이유·원문을 보고 저장된 결과를 다시 엽니다. 한 요인만 바뀌고 두 기록 모두 평가 조건이 완전하며 모든 질문이 판정됐을 때만 그 요인의 효과로 읽고, 그 밖에는 변화를 확정하지 않습니다.
- **결과 비교 → 버전별 결과 비교**는 **기준 모델 / 비교 모델** 두 목록에서 하나씩 선택합니다. 평가 기록이 하나인 모델은 이름만 표시하고 선택 즉시 해당 저장 결과를 비교합니다. 같은 모델 버전에 기록이 여러 개이면 같은 목록 안에서 모델별로 묶고 실행명·시각·문항 수·상태로 구분합니다. 임의로 최신 실행을 선택하지 않으며 별도의 실행 선택란은 표시하지 않습니다. 선택과 필터는 현재 브라우저 세션에서 유지합니다.
- 대상 버전에 실행이 없으면 동일 질문으로 평가를 추가하도록 안내합니다. **동일 질문 내려받기 → 새 버전 답변 등록·평가**는 기존 흐름을 재사용합니다. 내려받은 JSON은 문항 ID·질문·참조자료·대화 ID·턴을 유지하고 답변만 비워 둡니다. 기준이 한 문항이면 질문을 수정할 수 없는 직접 답변 입력란을 제공합니다. 새 실행을 생성하고 평가자를 호출한다는 안내를 표시합니다. 조회·필터·저장 결과 비교에는 모델 호출이 없습니다.
- 모델 버전은 먼저 등록된 다른 버전을 선택합니다. 서버가 ID·질문 원문·참조자료·대화 순서와 모든 답변 입력을 검사한 후 새 AIONA 답변만 평가합니다. 다른 비교 모델의 답변은 다시 수집하지 않습니다. 파일 배열 순서는 ID로 기준에 맞추지만 대화의 턴 순서는 변경할 수 없습니다.
- 새 실행에는 `baseline_run_id`를 저장합니다. 평가가 끝나면 해당 기준과 대상을 선택한 비교 화면으로 이어집니다. 저장 결과에서도 **기준 버전과 비교**로 돌아갈 수 있습니다. 같은 버전의 반복 실행·평가 조건 차이·평가 미완료는 버전 개선 점수로 확정하지 않습니다. 조건이 다른 경우 기준 답변을 현재 설정으로 새 평가하는 버튼을 제공합니다. 원래 평가 기록은 유지하며 재평가에는 평가자 호출이 발생합니다.
- 동일 질문 흐름의 API: `GET /api/comparison/runs/{id}/version-template`, `POST /api/comparison/version-check`(검증만), `POST /api/comparison/version-runs`의 `baseline_run_id`(검증 후 평가). 원문 재평가의 `source_run_id`와 동시에 사용할 수 없습니다.

- 서로 다른 실행의 질문 ID·원문·참조자료·대화 및 앞 질문 경로, 실제 저장된 평가기·평가 모델·설정이 같고 AIONA 판정이 모두 완료되어야 전체 점수 증감을 확정합니다. 단일 문항 배열의 순서가 달라도 ID로 연결하지만, 중복·변경된 ID를 유사도로 추정하지 않습니다. 답변 차이는 정상적인 비교 대상입니다.
- 공통 문항의 개선(FAIL→PASS), 악화(PASS→FAIL), PASS 유지, FAIL 유지, 미완료를 확인하고 이전·현재 답변과 판정 근거를 나란히 열 수 있습니다. 조건이 다르면 개선·악화로 확정하지 않습니다. 추가·삭제·변경 문항은 따로 표시합니다. 기준별 적용 대상이 다르면 통과율 증감도 확정하지 않습니다.
- 버전 비교 화면의 **이 원문을 현재 기준으로 새 평가**는 새로운 실행을 만들고 원본 실행 ID와 AIONA 버전을 유지합니다. 재평가는 새 의미 평가를 실행하므로 단순 조회와 구분합니다. 기존 결과는 덮어쓰지 않습니다.

관련 API는 `GET /api/comparison/version-history`, `POST /api/comparison/model-versions`(register/activate), `POST /api/comparison/version-runs`입니다. 모델 버전 등록·선택은 평가자를 호출하지 않습니다. 비교 실행은 선택적인 `input_mode`(file/manual)와 `expected_model_version`을 받습니다. 화면과 서버의 현재 버전이 다르면 유료 호출 전에 거부하여 새로고침으로 확인하게 합니다. 버전 이력 조회는 기존 최근 30개 목록과 별개로 전체 저장 실행을 제공합니다. 기존 실행·상태 API에는 `aiona_release`, `evaluation_profile`, 문항·원문 지문이 추가됩니다. 기존 요청의 버전 정보는 선택 사항이며 새 AIONA 단독 버전 평가에서는 필수입니다. 버전은 `10.10`도 보존되는 문자열입니다. 평가 조건은 현재 환경설정을 과거 기록에 소급하지 않고 당시 저장 결과에서 읽습니다.

`tests/test_aiona_versions.py`, `tests/version_comparison_test.js`, `tests/workspace_versions_ui_smoke.py`로 원본 보존·버전 입력·문항 대응·비교 제한·브라우저 흐름을 확인합니다. 브라우저 검사에서 만든 10.2 변화 자료는 임시 서비스의 명시적 테스트 데이터이며 실제 저장 실행에 추가하지 않습니다.

### 모델 버전과 이력 저장 계약

작업 이력(버전 등록·기본 버전 변경·실행 시작·종료 등을 남기던 시스템 로그)은 2026-10-13 에 제거했습니다. 회의(10-12)와 설계안 v1.1 에서 이력 관리는 '결과 비교 기록이 쌓인 것'이고 시스템 로그와는 다르다고 정했기 때문입니다. 기본 평가 버전 변경 사유는 버린 것이 아니라 그 버전 기록(`default_changes`: 시각·이전 버전·사유)에, 등록 사유는 `registered_reason` 에 남깁니다.

| API | 동작 |
|---|---|
| `POST /api/comparison/model-versions` | `action: register, set_current: false`는 등록만 수행. 옵션 생략은 기존 클라이언트의 등록+기본 선택 동작 유지 |
| 같은 API의 `action: activate` | `version`, `reason`, `expected_current_version`으로 변경. 마지막 값이 현재 기본 버전과 다르면 저장하지 않고 재확인 안내 |
| `GET /api/comparison/runs/{id}/code-recheck` | 평가가 끝난 실행의 CODE FAIL 을 현재 엔진으로 다시 검사한 차이(`cleared`·`added`). 읽기 전용, 모델 호출 없음, 엔진이 같으면 검사하지 않음 |
| `GET /api/comparison/aiona-history` | `{version, factor_labels, entries(최신순), series(질문 세트별 추이 점)}`. 평가가 끝난 실행만, AIONA 결과만. 모델 호출 없음 |
| 기존 실행·버전 이력 API | `evaluation_conditions_summary`, `evaluation_summary`를 추가. 조건 요약과 문항 판정 완료/미완료 수를 별도로 제공 |

모델 버전 목록은 `data/aiona_versions.sqlite3`의 `registry` 테이블에 저장합니다(`webapp/registry_store.py`). 버전 등록·기본 변경은 하나의 SQLite 트랜잭션으로 반영하거나 취소하고, 동시 요청은 DB 쓰기 잠금으로 직렬화합니다. 기존 버전 JSON을 수동 편집해도 가져온 뒤의 DB 상태는 바뀌지 않습니다. 예전 DB 에 남은 `activity` 테이블은 읽지도 쓰지도 않습니다. 외부 DB 설치, 환경변수, 로그인 설정은 추가하지 않습니다.

이력 관리의 완료 시각은 실행이 끝날 때 실행 JSON 의 `finished_at` 에 남깁니다. 예전 실행 파일의 내부 `_activity_*` 필드는 읽기만 하고 공개 응답에서 제외합니다. 최초 실행·평가 시작 저장에 실패하면 평가자나 수집 모델을 호출하지 않습니다. 서버 재시작으로 중단된 실행은 오류 상태로 저장합니다. 기존 실행 원문·판정은 조회나 버전 변경으로 수정하지 않으며 원문 재평가는 `source_run_id`로 연결한 새 실행을 만듭니다. 판정 정책 소급 도구(`tools/apply_source_failure_policy.py`)의 적용 기록은 실행 JSON 의 `evaluation_policy_updates`(update_id·사유)에 남습니다.

API 키·인증 토큰·환경변수 원문·비용 금액은 기록하지 않습니다. 기존 비용의 터미널 전용 표시 정책을 유지합니다.

검증은 `tests/test_version_registry_store.py`(버전 목록·사유·롤백·동시 등록), `tests/test_evaluation_summary.py`(질문 단위 판정 요약), `tests/test_version_comparison_server.py`(AIONA 이력: 한 요인·여러 요인·버전 변경·추이)에서 합니다. 브라우저 스모크 스크립트(`tests/workspace_management_ui_smoke.py` 등)는 작업 이력 화면 기준이라 다시 써야 합니다.

## 외부 AI 답변 가져오기 (2026-10-13)

새 비교 화면 아래 **고급 · 기타 응답 파일 가져오기**(2026-10-13 자동 수집 도입 후 접힌 고급 기능으로 이동)는 API·웹·에이전트·외부 플랫폼 답변을 공통 형식 `modelgrade-collection/v1` 로 바꿔 기존 CODE·J1~J6 평가기로 평가합니다. 상세 설계·플랫폼 조사·검증 범위는 [4단계 문서](4단계_외부수집통합_2026-10-13.md)에 있습니다.

- 입력: 공통 수집 형식, 대화 기록(`modelgrade-transcript/v1`), API 응답 파일(`modelgrade-api-responses/v1`), 에이전트 실행(`modelgrade-agent-run/v1`, OpenAI Agents SDK·LangSmith·OpenTelemetry GenAI), ChatGPT·Claude.ai 공식 내보내기, HTML, 기존 Q/A 파일·저장된 비교 실행. 파일에 모델 정보가 없으면 "시스템 정보 직접 입력"에 제공자·플랫폼·모델(모르면 `unknown`)·실행 방식을 적습니다.
- 미리 확인(`POST /api/comparison/external/preview`)은 모델·평가자·네트워크를 호출하지 않습니다. 같은 내용을 다시 가져오면 막고, "같은 내용 재실행"을 고르면 별도 실행으로 남깁니다.
- 평가 시작(`POST /api/comparison/external/runs`). 연결된 Gemini·Claude·GPT 를 고르면 같은 질문을 기존 수집 경로로 함께 수집하며 예상 유료 호출 수를 먼저 보여 줍니다. 앞 턴이 빠진 대화가 있으면 API 함께 수집은 막습니다.
- 결과 비교 화면에는 수집 환경 비교, 모델 카드의 실행 방식·수집 경로·웹검색·도구·수집 품질, 답변 상세의 수집 정보(원래/중계 URL·연결 구절·원본 HTML·에이전트 요약)가 추가됩니다. 환경이 다르거나 확인되지 않으면 순위를 매기지 않습니다.
- 외부 실행은 AIONA 버전이 없어 버전 관리에 나타나지 않습니다. 이력 관리 화면(AIONA 결과 이력)에도 나오지 않으며, 실행 목록 API `GET /api/comparison/history` 와 현재 세션의 최근 결과로 다시 열 수 있습니다.
- 형식 목록과 플랫폼별 지원 현황: `GET /api/comparison/external/formats`.

## 의미평가 API 설정과 검증 근거 (2026-10-11)

답변 수집 API와 의미평가 설정은 분리됩니다. 기존 코드 검사·J1~J6·화면 디자인을 유지하며, 의미평가에는 동일한 질문·답변·참조 자료·모델별 이전 대화 원문을 전달합니다.

### 현재 설정 (2026-10-12): Claude API · Claude Opus 5.5

현재 평가자는 `SEMANTIC_ENGINE=anthropic_api`, `SEMANTIC_ANTHROPIC_MODEL=claude-opus-5-5`, `SEMANTIC_ANTHROPIC_EFFORT=high`입니다. 키는 `.env`의 `ANTHROPIC_API_KEY`를 쓰고, 검색·원문 조회 한도와 이어가기 설정은 아래 Claude 설정 예시와 같습니다. 모델·effort 값을 비우면 코드 기본값(`claude-sonnet-5-5`·`medium`)이 쓰이므로 `.env`에 명시합니다. ### J5: 사실 확인과 적용 여부

**평가 대상 답변에 출처나 링크가 없다는 이유로 FAIL·보류하지 않습니다.** 평가자가 외부 사실 주장을 추출해 직접 검색하고 출처 원문과 대조합니다. 제공 자료의 요약·변환은 해당 자료와 대조하며, 외부 사실은 검색 근거로 맞으면 PASS, 틀리면 FAIL입니다. 확인을 시도했지만 근거를 확보하지 못한 경우에는 UNVERIFIED입니다. 결과의 출처는 답변 작성자가 남긴 링크에 한정하지 않고 평가자가 찾은 근거도 포함합니다.

웹 인용 대조에서는 곡선 작은따옴표·큰따옴표(`‘’“”`)와 일반 따옴표의 글꼴 표기 차이를 같은 문자로 취급합니다. 숫자·부정문·수학 기호 차이는 지우지 않으며 원문도 변경하지 않습니다. 평가 중단 요청이 있으면 다음 출처를 열지 않고 미완료 검증을 중단으로 남깁니다.

- 새 CLI/API 평가는 숫자 유무와 관계없이 모든 답변에서 사실 주장이 있는지 확인합니다. 인사·순수 창작·의견·순수 계산 결과·개수 확인·형식 변환만 있고 외부 사실이나 제공 자료에 대한 검증 주장이 없으면 `NOT_APPLICABLE`, `basis=none`, `claims=[]`와 제외 이유를 기록하고 J5 통과·실패·미판정 분모에서 제외합니다. 계산이 포함돼도 실제 가격·기관·날짜·과학 원리 같은 외부 사실은 제외하지 않습니다. 사실 주장이 있는데 근거를 못 찾았으면 그 주장을 남기고 `UNVERIFIED`로 기록합니다.
- 참조 자료가 있으면 해당 자료와 대조하고, 참조 인용이 실제 전달된 자료에 포함되는지 코드로 확인합니다. 이는 **제공된 자료와의 일치 평가**이며 자료 자체의 공신력이나 현실의 사실을 독립적으로 입증하지 않습니다. 자료가 다루지 않는 주장은 `UNVERIFIED`입니다.
- 질문에 제공된 문서·가상 설정의 **요약·추출·변환 일치**는 `scope=input_consistency`로 구분합니다. 각 주장에 현재 질문의 해당 요청 원문인 `scope_quote`를 남겨야 하며, 서버가 변환 요청 범위와 지정된 인용문을 확인합니다. 현재 사용자 질문은 `origin=question`, 이전 사용자 질문은 `origin=history_user`와 정확한 턴 번호를 사용합니다. 이전 assistant 답변은 독립 사실 근거로 인정하지 않고, 질문을 `reference`로 복제하지 않습니다. 이 경로의 PASS는 제공 자료와의 일치를 뜻하며, 자료 자체의 진위나 추가된 외부 사실을 입증하지 않습니다. 서버가 진위 확인 요청으로 식별했거나 허용 범위를 확인하지 못한 경우에는 자료 자체 인용만으로 통과를 확정하지 않습니다.
- 문서 소개와 변환 요청이 서로 다른 문장이어도 확인합니다. 현재 계획·이전 조건 등을 되짚어 정리하는 요청은 이전 사용자 질문의 자료 문맥을 확인할 수 있지만, 현재 요청의 정확한 변환 인용과 지정한 이전 사용자 턴의 원문 근거가 모두 필요합니다. 과거 assistant만 자료를 제시했거나 외부 진위를 묻는 경우에는 이 경로로 통과시키지 않습니다. 순수 계산·가상 계획의 이전 선택 재진술은 관련 CODE/J2/J3/J6 기준으로 평가하며, 별도 외부 사실·사용자 제공값 검증 주장이 없을 때만 J5 미적용입니다. 모델이 제출한 적용 여부를 프로그램이 문항 ID로 일괄 바꾸지는 않습니다.
- 입력 자료만 대조하면 `basis=input`, 입력 자료와 웹·명시 참조 등 여러 출처 유형을 함께 쓰면 `basis=mixed`입니다. 혼합 답변에서도 모든 사실 주장을 남기고 주장별 근거를 따로 검사합니다. 외부 사실은 `scope=external_fact`로 구분하고 웹 또는 명시 참조 자료의 근거를 요구합니다. 일부 입력 자료 주장이 확인돼도 외부 사실의 미확인이 사라지지 않습니다. 입력·참조 인용은 웹 URL 수집 한도를 사용하지 않습니다.
- 참조 자료가 없고 검색 설정이 `live`이면 검색을 지원하는 CLI/API 엔진에서 J5 웹검색을 사용할 수 있습니다. 현재 Claude API는 Messages의 웹검색·원문 조회를, OpenAI API는 Responses의 웹검색을 사용합니다. 기존 Codex CLI도 선택할 수 있습니다. 외부 사실 주장이 있는데 실제 검색이나 출처 근거가 없으면 `UNVERIFIED`입니다. 입력 자료 일치만 확인하거나 J5 미적용이면 불필요한 검색을 요구하지 않습니다.
- 완료된 검색 도구 이벤트와 제공자 인용 기록에서 출처 URL을 확보합니다. 모델이 응답 JSON에 적은 URL만으로 검색 완료를 인정하지 않습니다. **서버는 관측된 URL에 한해 공개 원문을 직접 받아 인용문을 대조**합니다. 검색결과 요약이나 모델의 기억을 원문 증거로 쓰지 않으며, 본문 수집 실패·인용 불일치만 있는 주장을 PASS/FAIL로 확정하지 않습니다.

- 인용문이 실제 본문에 있다는 사실은 서버가 공백·유니코드 정규화 후 확인합니다. **발행 주체의 공신력, 기준 시점의 적합성, 인용문이 주장을 지지하거나 반박하는지는 모델이 판단**합니다. 결과에는 일차·신뢰 가능한 이차·신뢰성 미확인 출처 구분과 공신력·시점 판단 이유를 남깁니다. 신뢰성 미확인 출처만 있거나 이 근거가 부족하면 확인 필요로 남습니다.
- 확인된 오류가 있으면 FAIL, 모든 확인 대상이 근거로 뒷받침되면 PASS, 근거 부족·검색 실패·해소하지 못한 상충 자료는 `UNVERIFIED`입니다. 주장·출처·인용·판정 이유·검증 시각·인용 대조 결과를 저장하며 수집한 페이지 전문은 저장하지 않습니다.
- CLI와 API는 같은 `evidence-v3.3-input-source-content` 검증 정책을 사용합니다. 주어진 정보의 JSON 배열·객체 작성과 제공 정보만 사용하는 소개 문구 작성도 자료 변환 요청으로 확인합니다. 단순 추천·계산·진위 확인을 일괄 포함하지 않습니다. 서버는 원문 인용 일치와 자료 변환 요청 범위 검증을 각각 `input_quote_verified`, `input_scope_verified`에 남기고 둘 다 확인될 때만 유효 근거로 인정합니다. 자료와 주장 사이의 의미 관계는 모델이 판단합니다. 자료 자체의 진위나 모델의 판단이 항상 맞음을 독립적으로 증명하는 검사는 아닙니다. 설정상 검색 허용과 실제 연결 성공은 별개이므로 사용할 엔진·모델·계정으로 검색과 원문 대조 동작을 확인해야 합니다.

원문 수집은 평가 응답 하나당 **URL 최대 8개, 총 30초**, URL 하나당 최대 8초로 제한합니다. 본문은 **전송 크기와 압축 해제 후 크기 모두 2MiB 이하**여야 합니다. gzip·deflate는 완전한 단일 스트림만 지원하며, 잘림·비정상 압축·스트림 뒤 남는 데이터·여러 gzip 멤버가 있거나 br 등 지원하지 않는 압축이면 확인 필요로 남깁니다. 공개 HTTP(80)·HTTPS(443)의 HTML·일반 텍스트만 지원하며 PDF·로그인 필요 자료 등은 원문 검증할 수 없습니다. 리다이렉트는 같은 호스트에서 최대 3회만 허용하고 다른 호스트로 이동하면 확인 필요로 남깁니다. 이 제한이나 출처 접근 실패로 인용을 확인하지 못한 경우 답변이 틀렸다고 단정하지 않습니다.

2026-10-09 실제 CLI 검증에서 정상 사실 PASS, 명백한 오답 FAIL, 공개 근거 없는 주장 UNVERIFIED, 오래된 버전을 최신으로 제시한 주장 FAIL을 확인했습니다. 공개 합성 1문항으로 **파일 업로드 → 실제 3개 모델 답변 수집 → 4개 모델 코드·웹검색 의미평가 → 결과 표시**도 약 225초에 완료했습니다. 모든 모델에서 출처 원문 인용이 확인됐고, 실제 생성 답변의 부가 설명 오류도 FAIL로 남겼습니다. 이 값은 연결 검사이며 AIONA의 실제 성능 점수가 아닙니다. 결과와 화면 재검증은 `results/live-demo-flow/20261009T063027Z-web/result.json`, `ui-recheck-summary.json`에 있습니다. `python -X utf8 tests/live_workspace_flow_check.py --replay results/live-demo-flow/20261009T063027Z-web`는 추가 모델 호출 없이 저장된 결과 화면만 재검증합니다.

### J6: 멀티턴 맥락 유지 (이전 대화 검증)

2026-10-13 에 이름을 'LONG CONTEXT'에서 '멀티턴 맥락 유지'로 바꿨습니다. 같은 날 적용 조건도 바꿨습니다 — **멀티턴 대화**(한 턴의 질문 + 답변이 10K 토큰 이상인 턴이 10개 이상)의 2번째 턴부터 묻습니다(`multi-turn-v1`, 예전에는 대화 2번째 턴부터). 멀티턴 여부는 모델마다 자기 대화(같은 질문 + 그 모델 답변)로 재므로 같은 대화도 모델마다 다를 수 있고, 멀티턴이 아닌 대화는 대화 유지율에서 '멀티턴 아님'으로 따로 셉니다.

각 모델의 이전 대화 원문 전체를 유지합니다. 처음 지시뿐 아니라 중간에 변경한 최신 유효 지시를 확인하며, 결과에는 이전 턴 번호·지시 원문·현재 답변 인용·판정을 저장합니다. 인용한 턴과 문장이 실제 원문에 있는지 검사합니다. 이전 턴 누락·중복·입력 오류, 검증 근거 부족은 확인 필요로 남기고 통과로 계산하지 않습니다. 과거의 실패와 현재 답변의 실패를 구분합니다.

`context_checks`의 이전 지시와 현재 답변 인용은 각각 해당 원문의 짧고 연속된 구절이어야 합니다. 중간을 `...`·`…`로 생략하거나 원문에 없는 강조·백틱을 붙이면 인용 일치를 인정하지 않습니다. 필요한 답변 내용이 누락된 경우에는 빈 답변 인용과 FAIL/확인 필요 사유를 사용할 수 있지만, 빈 인용으로 PASS를 확정할 수 없습니다. 모델이 PASS라고 답했어도 확인 가능한 인용이 없으면 해당 검사를 `UNVERIFIED`로 남깁니다. 다른 검사에서 근거가 확인된 FAIL은 유지합니다.

서버의 J5/J6 근거 검사로 최종 판정이나 이유가 바뀌면, 변경 전 모델의 `choice`·`reason`을 `model_original_assessment`로 함께 보관합니다. 상세 근거의 **서버 근거 검증 전 모델 판정**에서 원래 설명과 최종 사유를 구분해 볼 수 있습니다. 이 값은 서버가 원응답에서 보존하는 감사 정보이며, 점수·완료 집계에는 서버 검증 후 최종 판정만 사용합니다. 원래 평가 질문·답변·대화 이력은 수정하지 않습니다.


### J7: 롱컨텍스트 활용 (2026-10-13 추가)

입력(현재 질문 + 참조 자료, 이전 대화 턴 제외)이 **272,000토큰 이상**일 때만 묻습니다. 토큰 수는 모델과 상관없이 같은 값이 나오도록 고정 공개 토크나이저 `tiktoken o200k_base`로 셉니다(`long-context-v3.1-272k`). 토크나이저를 불러오지 못하면 길이를 추정하지 않고 J7 을 확인 필요(UNVERIFIED)로 집계합니다(해당 없음으로 빼지 않음). 사전 내려받기는 최대 20초 기다리고, 실패는 5분 동안 기억해 질문마다 다시 받지 않습니다. 경계는 250K~500K 를 RULER 방식으로 시험해 정하려 했지만 세 비교 모델 모두 500K 까지 정답률이 떨어지지 않아 성능으로는 가를 수 없었고, GPT(OpenAI)의 롱컨텍스트 요금 경계 272K 를 따릅니다(설계안 v1.5 '롱컨텍스트 판별'). 결과는 길이 구간으로 나누지 않고 입력 토큰 수만 남깁니다. 예전 경계는 8K(`long-context-v1`)·250K(테스트 기간, `long-context-v2`)였습니다.

- 무엇을 보나: 긴 입력에서 질문이 묻는 정보를 위치와 관계없이(질문과 표현이 달라도) 찾았는지(J7-1), 여러 곳에 흩어진 근거를 빠짐없이 연결했는지(J7-2). 근거: Lost in the Middle·RULER·NoLiMa(J7-1), LooGLE·RULER·BABILong(J7-2).
- 경계: 입력에 없는 내용을 만들거나 값을 다르게 옮긴 것은 J5, 요구 항목 누락은 J4, 이전 대화 턴은 J6 입니다.
- FAIL 근거: 이유에 입력 원문(질문·참조 자료)과 답변을 각각 따옴표로 인용해야 하고 둘 다 원문과 맞아야 하며, 근거가 없으면 1회 재평가 뒤에도 없으면 미완료입니다. items 방식에서는 J7-1.a·J7-2.a 가 NO 이면 현재 입력 원문 인용이 필수이고 서버가 대조합니다.
- 기록: J7 판정에 `long_context`(입력 토큰 수·근거 인용의 입력 내 위치 0~100)를 붙입니다. 위치는 입력 중간 정보를 놓치는 경향을 보려는 기록이며 판정에는 쓰지 않습니다.
- 현재 질문 세트(Q165 등)에는 272K 토큰 이상 입력이 없어 J7 은 모두 해당 없음입니다. 롱컨텍스트 질문은 별도로 만들어 넣어야 합니다.


### J8: 첨부파일 활용 (2026-10-13 추가)

질문에 첨부파일(이미지·TXT·DOCX·PDF 등)이 있을 때만 묻습니다. 입력의 `attachments` 는 파일마다 `name`(파일 이름)·`type`(image·txt·docx·pdf …)·`content`(파일에 실제로 든 글자·표 값·그림 속 글자)이고, 보낸 파일을 확인하는 `sha256`·`size`·`path` 를 함께 둘 수 있습니다. 평가 모델에는 파일 대신 `name`·`type`·`content` 만 보냅니다(경로·지문은 보내지 않음). 첨부파일은 질문 생성 단계가 직접 만든 파일이라 정답 내용을 정확히 압니다.

- 무엇을 보나: 첨부 내용을 근거로 답했는지(J8-1 첨부 내용 반영), 표의 행·열·그림 속 글자·페이지·목록 같은 형식별 구조를 맞게 읽었는지(J8-2 파일 형식 읽기), 파일을 열 수 없거나 일부만 읽었을 때 그 사실을 밝혔는지(J8-3 첨부 접근 처리).
- 경계: 맞는 칸을 보고도 값을 다르게 옮긴 것은 J5-2, 272K 토큰 이상 긴 입력에서 찾기·연결은 J7, 첨부 요약에서 빠뜨린 것은 J4. 파일을 열 수 없다고 밝힌 것은 거절(J1-2)이 아니라 J8-3 이 보고, 이때 J8-1·J8-2 는 해당 없음입니다.
- FAIL 근거: 이유에 답변의 문제 부분을 따옴표로 인용해야 하고(답변 원문과 맞아야 함), 첨부 `content` 의 해당 부분 인용도 근거로 셉니다(`j1-j4-j7-j8-fail-evidence-v3`). 근거가 없으면 1회 재평가 뒤에도 없으면 미완료입니다. items 방식에서는 첨부 내용 인용을 `question_quote` 로 받아 서버가 첨부 `content` 와 대조합니다.
- 현재 질문 세트에는 첨부파일 질문이 없어 J8 은 모두 해당 없음입니다. 질문 생성 버튼(구현 중)이 첨부파일도 함께 만듭니다.
