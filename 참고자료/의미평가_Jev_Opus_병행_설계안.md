## 3. 병행 설계

### 3-1. 기준별 담당

| 기준 | 1차 담당 | 이유 |
|---|---|---|
| J1 의도 충족 · J2 내용 적절 · J3 논리 · J4 충분성 | **Jev** | 질문·답변만 보면 되는 PASS/FAIL 판단. 규칙(PASS/FAIL 조건)을 글로 줄 수 있음 |
| J6 멀티턴 맥락 유지 | **Jev** (대화가 Jev 한도 안일 때) / **Opus** (넘을 때) | Jev 요청 한도는 64K 토큰이고, `state` 와 가장 긴 질문을 합쳐 32K 이하여야 함. 326 세트 대화 16개 중 7개가 이 한도를 넘음 |
| J8 첨부 활용 | **Jev** (텍스트 첨부: txt·docx·pdf 의 글) / **Opus** (이미지) | Jev 는 글만 받음 |
| J5 DATA 신뢰도 | **Opus** | 웹 검색·원문 열기 도구가 필요함 (Jev 는 도구 없음) |
| J7 롱컨텍스트 | **Opus** | 입력 27만 토큰 이상이라 Jev 한도 밖 |

### 3-2. Jev 판정을 쓰는 규칙

1. Jev 가 **PASS 이고 확신도 0.8 이상**이면 그 판정을 최종으로 쓴다. 화면 사유는 "Jev 판정 (확신도 0.93)"처럼 수치만 보인다(원문 인용 없음).
2. Jev 가 **FAIL** 이거나 **확신도 0.8 미만**이면 그 기준만 **Opus 가 다시 판정**한다(사유·원문 인용 포함). Opus 판정이 최종이다. → FAIL 에는 항상 Opus 의 구체적 사유가 붙는다(화면 요구·D-1 유지).
3. Jev 호출이 실패하면(오류·시간 초과·키 없음) 그 질문의 Jev 담당 기준을 모두 Opus 로 넘긴다.
4. Jev 한도를 넘는 입력(대화 이력·첨부 글이 길어 32K/64K 초과)은 처음부터 Opus 로 보낸다(잘라서 보내지 않는다 — 원문 전체 전송 원칙).

### 3-3. 호출 흐름 (질문 하나)

```
CODE 평가 → 적용 기준 결정(코드 규칙)
  ├─ Jev 담당 기준(J1~J4, 한도 안 J6, 텍스트 J8) → Jev 1회 (실시간, 질문당 약 1초)
  │     └─ FAIL 또는 확신도<0.8 인 기준 + Jev 실패 → "재판정 목록"
  └─ Opus 담당 기준(J5, J7, 한도 밖 J6, 이미지 J8) + 재판정 목록 → Opus 1회 (Message Batches, 캐시)
```

Opus 는 질문마다 최대 1번만 부른다(담당 기준 + 재판정 기준을 한 요청에 묶음). 둘 다 비면 Opus 를 부르지 않는다.

### 3-4. 기록

- 기준마다 `judge`: `jev` / `opus` / `jev→opus`(재판정), Jev 확신도·확률, Opus 사유를 남긴다.
- 실행 기록에 Jev 판정 중 그대로 쓴 수, Opus 로 넘긴 수(이유별: FAIL·저확신·한도·Jev 오류), 기준별 담당 비율을 남긴다.
- 결과 화면의 평가 방식 표시에 "Jev + Opus 병행 (확신도 기준 0.8)"을 보인다.
