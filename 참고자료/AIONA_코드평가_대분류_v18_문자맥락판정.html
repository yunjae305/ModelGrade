금지 표현 출현은 질문별 사전 금지 목록이 제공된 테스트에 연결합니다. 목록이 없으면 미검사입니다. 필수 표현의 의미 판단·관측 전용 지표·LLM 심판 집계는 답변별 코드 판정에 넣지 않습니다.

v18은 1-1 문자 맥락 판정과 기존 검사 번호 정리를 반영했습니다. 평가기 코드(code_eval)도 같은 규칙으로 바뀌었습니다.

LLM은 모든 답변이 거치는 단계가 아닙니다. CODE에서 FAIL이 나온 질문만, 그 질문에서 FAIL이 난 기준과 사유를 함께 LLM으로 보냅니다. LLM 검토 결과는 CODE 판정을 자동으로 바꾸지 않습니다. 미판정 항목은 PASS/FAIL로 바꾸지 않고 사유만 남깁니다.

단계별 역할

CODE가 먼저 판정하고, LLM은 FAIL 질문만 재검토합니다. 실행할 때마다 LLM에게 평가 방법을 고르게 하지 않습니다.

A · CODE (모든 질문)

규칙과 계산으로 확인

표 존재 여부, 요구한 불릿·문장 수, Python·JSON 구문, 필수 필드, 금지 표현, 내부 마커, 명시된 행·열 수, 계산값처럼 조건을 확정할 수 있는 검사입니다.

B · CODE FAIL → LLM 재검토

FAIL 질문만 다시 확인

CODE에서 FAIL이 나온 질문만 LLM이 재검토합니다. 질문·답변과 FAIL이 난 기준·사유만 전달하고, PASS 결과는 보내지 않습니다.

C · LLM 재검토 항목

의미와 FAIL 사유 확인

요청 수행 · 관련성 · 충분성 · 자료 해석(자료가 없으면 해당 없음) · 코드 FAIL 사유 적합성. LLM 결과는 CODE 판정을 바꾸지 않는 별도 의견입니다.

PASS

검사 조건·대상·범위를 확정하고 실제 검사를 완료했으며, 조건을 만족한 경우입니다.

FAIL

같은 전제를 충족한 뒤 실제 검사에서 명확한 위반을 확인한 경우입니다. FAIL이 나온 질문은 LLM 재검토로 넘어갑니다.

CODE로 판단하지 못함

입력 부족, 미지원 구조, 조건 추출 실패, 검사 범위 미확정 또는 의미 판단 필요 등 사유를 따로 기록합니다. 미검사는 PASS도 자동 FAIL도 아닙니다.

# AIONA 코드 평가 대분류 통합안 v3

작성일: 2026-09-28
범위: 공통 코드 평가의 분류·판정 범위·근거와 AIONA 전용 정책의 연결안
상태: 설계 문서. 평가기 소스 수정, 회귀 테스트, 새 버전 재평가를 완료했다는 뜻이 아니다.

## 1. 전체 분류 — Depth 1~2

공통 코드 평가는 다음 세 대분류, 여덟 소분류로 정리한다. 이 분류 이름과 묶음은 프로젝트의 관리용 설계이며 외부 논문이 정한 보편적 품질 분류가 아니다.

| Depth 1: 대분류 | Depth 2: 소분류 | 핵심 질문 |
|---|---|---|
| 1. 출력 무결성 | 1-1. 응답·문자 정상성 | 일반 응답이 존재하고, 적용한 문자 정책을 지켰는가? |
| 1. 출력 무결성 | 1-2. 문서·코드 구문 유효성 | 정상 결과물로 제시한 JSON·Python 코드의 구문이 유효한가? |
| 1. 출력 무결성 | 1-3. 참조 연결 유효성 | 실제 사용한 각주·문서 내부 링크가 필요한 정의·대상에 연결되는가? |
| 2. 요구 조건 준수 | 2-1. 분량·표현 조건 | 사용자가 명시한 개수·분량·문자열 조건을 지켰는가? |
| 2. 요구 조건 준수 | 2-2. 형식·구성 조건 | 사용자가 요구한 형식·필드·구성·순서를 지켰는가? |
| 3. 수치·데이터 정합성 | 3-1. 계산 결과 일치 | 확정된 계산 관계를 재계산하면 답변값과 일치하는가? |
| 3. 수치·데이터 정합성 | 3-2. 선언 개수 일치 | 답변이 말한 개수와 연결된 실제 구조의 항목 수가 같은가? |
| 3. 수치·데이터 정합성 | 3-3. 원본 보존·변환 일치 | 원본 보존·명시 고유성·데이터 변환 조건을 지켰는가? |

판정은 **적용 조건·검사 대상·범위·측정 규칙을 코드로 확정한 경우**에만 PASS/FAIL로 남긴다. 대분류·소분류의 개수가 실제 검사 함수 수나 질문마다 적용되는 조건 수를 뜻하지 않는다.

## 2. 소분류별 코드 판정과 근거

### 1. 출력 무결성

| 소분류 | 검사 대상 | 코드 판정 방법 | PASS / FAIL | 근거 |
|---|---|---|---|---|
| 1-1. 응답·문자 정상성 | 일반 응답의 비공백 내용, 등록된 금지 문자와 예외 | 비공백 문자 존재 확인, 코드 포인트 순회, 확정된 허용·금지 규칙 대조 | PASS: 적용한 존재·문자 규칙 충족. FAIL: 일반 응답이 비었거나 적용 금지 문자 검출 | 기존 B1·B2의 내부 운영 정책. 문자 규격은 문자 식별의 근거이지 보편적인 품질 합격선이 아니다. |
| 1-2. 문서·코드 구문 유효성 | 정상 JSON 결과물, 완성된 Python 소스로 확인된 블록 | 엄격한 JSON 파싱, Python 구문 분석·컴파일. 답변 코드는 실행하지 않음 | PASS: 대상 구문 검사 성공. FAIL: 적용 대상에서 실제 구문 오류 확인 | RFC 8259, Python 언어·컴파일 규칙. 기존 A2·A7의 대상·예외 정의. |
| 1-3. 참조 연결 유효성 | 지원하는 각주 사용·정의, 명시 ID와 문서 내부 링크 | 사용 ID·정의 ID·연결 목적지 추출, 필요한 정의의 존재·유일성·내용 대조 | PASS: 적용된 연결 조건 충족. FAIL: 요구된 정의 누락·중복 또는 잘못된 연결 | 질문의 참조 요구, 선언된 출력의 연결 규칙, 기존 A4·U4의 검사 계약. |

적용 경계:

- 명시적으로 빈 출력을 요구한 상황과 일반 응답을 요구한 상황을 구분한다. 답변 필드 자체의 누락 같은 수집·입력 오류는 빈 응답의 품질 판정과 구별한다.
- 질문에 금지 문자가 등장한다는 이유만으로 허용 요청이라고 보지 않는다. 허용·금지·설명 요청의 구분을 확정할 수 없으면 미지원으로 남긴다. 이는 기존 B2의 단순 언급 예외에 대한 **수정 제안**이며, 원본 구현을 이미 바꾼 것이 아니다.
- JSON의 NaN·Infinity를 거부한다. 객체의 중복 키를 발견했다는 이유만으로 일괄 JSON 구문 FAIL을 주지 않는다. 고유성 요구 또는 후속 데이터의 모호성은 별도로 다룬다.
- 오류 예시·입력 재현·부분 코드와 정상 결과물을 구분하지 못하면 자동 품질 FAIL로 합산하지 않는다.
- 현재 구문 판정 대상으로 설명하는 것은 JSON·Python이다. 전체 HTML·Markdown 적합성, 다른 언어의 문법, 코드 실행 결과·기능·보안까지 검사한다고 확대하지 않는다.
- 참조 검사는 외부 출처의 사실성·신뢰성이나 URL 접속 상태 검사가 아니다. 지원하지 않는 자동 제목 ID·각주 문법을 정의 누락으로 단정하지 않는다.

### 2. 요구 조건 준수

| 소분류 | 검사 대상 | 코드 판정 방법 | PASS / FAIL | 근거 |
|---|---|---|---|---|
| 2-1. 분량·표현 조건 | 요구 개수·길이·문장·문단·줄 수, 필수·금지 문자열, 시작·끝 표현, 허용 문자 | 질문의 지원 표현에서 값·비교 연산·대상·범위 추출 → 고정된 단위로 측정 또는 문자열 비교 | PASS: 실제로 검사한 명시 조건 충족. FAIL: 확정된 비교식·문자열 조건 위반 | IFEval의 검증 가능한 지시 준수 접근 + 질문 원문 + 프로젝트 측정 규칙. 기존 U1. |
| 2-2. 형식·구성 조건 | 요구한 표·목록·제목·코드블록, JSON 최상위 유형·필수 필드·자료형, 지정 순서 | 질문 조건 추출 → 지원 문법으로 출력 구조를 읽음 → 필수 구성·형식·순서 대조 | PASS: 요구 구조·구성 충족. FAIL: 실제 부재 또는 확인된 구조 조건 위반 | IFEval의 형식·구성 지시, JSON/RFC·JSON Schema 등 형식별 규격, 질문 원문. 기존 U2. |

적용 경계:

- 목록 세 항목이 있다는 사실로 내용상 서로 다른 해결책 세 가지를 제시했다고 판정하지 않는다.
- 글자·문장·문단 계산 단위와 원문/표시 텍스트 범위를 고정하고 결과에 남긴다. 기존 코드 포인트 측정을 사용자 지각 문자 수와 동일시하지 않는다.
- 요구가 없는 길이·반복·장식량은 관측값이다. 적정 길이나 반복 허용량을 임의로 만들어 실패시키지 않는다.
- 기존 자료의 ‘300자 정도 = 정확히 300자’는 운영 정책이다. **새 공통 기본안에서는** 허용 범위가 없는 ‘정도’·‘적당히’ 표현을 엄격한 수치 FAIL 대상으로 삼지 않는 것을 제안한다. 기존 정책 원문과 변경 이력은 보존한다.
- 파싱을 지원하지 못하는 구조를 ‘구조가 없다’로 바꾸지 않는다. JSON 구문 오류로 필드를 읽지 못했다면 필드 누락까지 추정해 중복 실패시키지 않는다.
- CommonMark의 문서 끝 코드블록 종료를 보편적 문법 오류로 처리하지 않는다. 명시 종료를 요구한 사용자 조건 또는 AIONA 정책이 있을 때 그 규칙의 준수 여부로 검사한다.
- IFEval과 형식 규격은 검사 접근·비교 규칙의 근거다. 임의 한국어 질문에서 모든 조건을 정확하게 추출한다는 증거는 아니다.

### 3. 수치·데이터 정합성

| 소분류 | 검사 대상 | 코드 판정 방법 | PASS / FAIL | 근거 |
|---|---|---|---|---|
| 3-1. 계산 결과 일치 | 질문이 요구한 계산값, 답변이 주장한 직접 산술 관계 | 지원 수식·역할·단위로 계산 관계 확정 → 재계산 → 연결된 출력값 비교 | PASS: 재계산값과 출력값 일치. FAIL: 확정 관계·단위·표시 조건의 불일치 | 수학적 연산, 질문의 명시 수치 관계, 확정된 표시 정책. 기존 U3·A6 및 A3의 질문 연결 근거. |
| 3-2. 선언 개수 일치 | ‘다음 세 가지’처럼 정확한 개수를 주장하는 문구와 이어지는 목록·소제목·표·배열 | 선언 수사 정규화 → 독립적으로 구조 경계 확정 → 항목 수 측정·대조 | PASS: 선언 수와 실제 수 일치. FAIL: 같은 범위의 확정된 개수 불일치 | 선언값과 관측값의 정확 비교라는 프로젝트 설계. 기존 A5. 독립적인 ‘좋은 글’ 연구 기준으로 부르지 않는다. |
| 3-3. 원본 보존·변환 일치 | 원본 값·자료형·ID·순서, 명시 중복 금지, 정렬·필터·매핑·집계·참조 목록 | 질문의 데이터·연산·보존 요구로 비교값 생성 → 출력 대상 대조; 고유성은 타입을 구분한 동일 값 검사 | PASS: 적용 보존·고유성·변환 조건 일치. FAIL: 확정된 값·자료형·순서·중복·건수·목록 오류 | 질문 원본과 연산 정의, 정확 비교. 기존 U5, U4의 목록·보존 부분, 과거 명시 고유성 검사. |

적용 경계:

- 질문 기반 검산과 답변 등식 검산은 같은 소분류에서도 구별한다. 식 자체가 맞는 것과 질문이 요구한 계산을 수행한 것은 다르다.
