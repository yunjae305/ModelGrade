# 할 일 — GPT-6 Luna 의미 평가 입력을 대화 순서대로 (앞 턴 이력 → 현재 턴), 캐시가 걸리게

상태: **해야 함 (다른 계정에서 진행 예정, 2026-10-19 사용자 결정)** · 판정 내용은 바꾸지 않고 입력 순서만 바꾸는 작업

## 왜

- 대화(멀티턴) 턴을 평가할 때 Luna 입력이 `[평가 규칙] → [현재 턴 질문·답변] → [1~(n-1)턴 이력]` 순서다. 현재 턴 질문·답변이 매번 달라 바로 거기서 앞 요청과 글이 어긋나므로, OpenAI 프롬프트 캐시가 **평가 규칙 부분에만** 걸리고 앞 턴 이력은 턴마다 처음부터 다시 읽는다.
- 실측(실행 `8c61f117e661`, 대화 턴 762건): 입력 토큰 중앙 **67,918** 중 캐시 **5,783**(규칙 부분)뿐.
- 사용자: "원래부터 1턴부터 시작해서 마지막 턴으로 평가를 진행했어야지" → `[평가 규칙] → [1턴] → … → [(n-1)턴] → [현재 턴 질문·답변]` 순서로. 그러면 n턴 요청의 앞부분(규칙 + 1~(n-2)턴)이 (n-1)턴 요청과 같아 캐시를 다시 쓴다 — 입력 비용이 크게 줄고 속도도 조금 빨라진다(판정 시간은 주로 추론 출력이 정함: 시간과의 순위 상관 출력 0.92·입력 0.85).
- 앞 턴을 줄여 넘기는 방식은 **쓰지 않는다** — J5 는 앞 턴 사용자 원문을 그대로 인용해 대조하고, J6 는 앞에서 정한 조건·앞 답변(예: Q11 "앞에서 고른 두 번째 안")을 봐야 해서 원문 전부가 필요하다.

## 지금 코드 (확인됨)

- `code_eval/semantic_api_client.py` — Luna 경로(`self.config.model == DEFAULT_MODEL`, gpt-6-luna)는 `semantic.build_prompt_parts(state, …)` 로 `static`(공통 지시문, `prompt_cache_breakpoint` 표시)과 `dynamic`(실행 기준 시각 줄 + `## 평가 대상 (데이터)` + `json.dumps(state)`) 을 만든다. `state` 는 question·answer 가 history 보다 앞.
- Anthropic 경로는 이미 `code_eval/semantic_cli_common.py` `build_prompt_blocks` 로 "지시문 → history 턴마다 한 블록 → 현재 질문·참조·첨부 → 실행 시각·answer" 순서를 쓴다(`DATA_LAYOUT` 설명 포함). 같은 배치를 Luna(Responses API) 입력 블록에 적용하면 된다.

## 할 일

1. Luna 입력을 `input_text` 블록 여러 개로 나눠 **지시문 → history 블록(1턴부터) → 현재 질문·reference·첨부 → 실행 시각·answer** 순으로 보낸다. 원문은 한 글자도 빼거나 줄이지 않는다. 캐시 표시(`prompt_cache_breakpoint`)를 history 마지막 블록 뒤에도 둘 수 있는지 확인(모르면 지시문 하나만 두고 순서만 바꿈).
2. 첨부 그림(pictures) 위치·J5 추가 검증(`evidence_prompt`) 덧붙임이 그대로 동작하게.
3. 프롬프트 배치가 바뀌므로 평가자 버전 표시(`to_manifest`·`version_registry` 의 프롬프트 정책 필드)를 올려 이전 실행과 구분.
4. 시험(`tests/test_semantic_api_client.py`): 같은 대화 2턴·3턴 요청의 입력 앞부분이 같은지(캐시 접두), 모든 원문이 그대로 들어가는지. `tests/test_semantic_*.py`·`tests/test_dual_judge.py` 전체 통과.
5. 유료 API 실제 평가 비교는 사용자 확인 뒤.

완료 기준: 시험 통과, 바꾼 순서와 버전을 그날 변경내역에 한 절로 기록.
