# 평가기준 통합 감사 — CODE·LLM 기준 현황, 교차분석, 판정 정책 검토 (2026-10-12)

대상 코드: 브랜치 `fix/evaluation-reliability`, 엔진 `aiona-code-eval-v16.2.6`, 의미 기준 `jev-criteria-v3`, 최종 판정 정책 `semantic-binary-outcome-v1`.
조사는 문서가 아니라 실행 코드(`code_eval/`, `webapp/`, `frontend/src/`), 프롬프트(`semantic_cli_common.py`), 결과 스키마, 테스트를 기준으로 했다. 숫자는 `python -m code_eval criteria`(통합 기준 목록)와 코드에서 계산했다.

이 문서에서 **"반영"** 은 코드에 적용하고 테스트로 확인한 것, **"승인 대기"** 는 공식 판정 의미가 바뀌어 적용하지 않은 제안이다.

### 1-2. 실제 실행 구조

```text
질문·답변(+reference·conversation_id·turn)
  │
  ├─ CODE 엔진 (engine.evaluate_case) — 질문 유형 분류 없음, 모든 문항이 8개 소분류 검사를 지남
  │    질문 조건 추출(extract) + 답변 구조 분석(analysis/textparse) → 각 검사가 적용 여부를 스스로 결정
  │    결과 행: check_id · status · verdict(PASS/FAIL/null) · required · measured · evidence · explain
  │
  ├─ 의미 평가 (jev_eval) — 문항당 호출 1회
  │    적용 기준: J1 전체, J2~J4 질문 요청 문장 규칙, J5 사실 주장 선별, J6 2번째 턴부터(앞 턴 원문 전체)
  │    + 같은 호출에 C 기준: 판정하지 못한 공통 CODE 조건
  │    → 서버 근거 검증(J5 출처·인용, J6 이전 턴·답변 인용) → 최종 정책(확인 필요 → 검증 기준 미충족 FAIL)
  │
  └─ 질문 최종 판정 (workspace-results.caseState · combined.combined_summary)
       CODE·의미 중 FAIL 하나라도 → FAIL / 적용 기준 모두 판정 → PASS / 그 외 → 미완료
       모델 점수 = PASS 질문 수 / 전체 질문 수, 기준별 통과율 = PASS / (PASS + FAIL)
```

### 2-1. 교차분석표

| 현재 기준 | 검사 방식 | 세부 조건 (검사 단위) | 중복 여부 | 권장 조치 |
|---|---|---|---|---|
| 1-1 응답·문자 정상성 | CODE | 응답 존재 · 깨진·제어 문자 · 설명 없는 외국 문자 | 없음 | 유지 |
| 1-2 문서·코드 유효성 | CODE | 코드블록 존재·개수·금지 · 언어 표지 · 구획 표시 2개 이상(MD 165) · 코드·수식 구획 짝(MD 170) · JSON·Python 구문 · 짝 없는 닫는 태그(MD 169) | 같은 원인 이중 FAIL: 코드블록이 없으면 `code_block` 과 `code_fence_min` 이 함께 FAIL | 역할 분리 유지 (MD 165는 공식 조건). 통합은 승인 대기 G-6 |

| 2-1 분량·표현 조건 | CODE | 불릿·항목·문장·문단·줄·어절 수 · 글자 수 · 필수·금지·시작·끝 문자열 · 허용 문자 · 명시 빈 출력 | 3-2와 같은 원인 이중 FAIL · J2 '제약'과 금지 문자열 겹침 · J4와 경계(개수) · **J6와 공백(이전 턴 형식 지시)** | 유지. J2 경계 명시는 승인 대기 G-5, J6 공백은 G-3 |
| 2-2 형식·구성 조건 | CODE | 표 존재·개수·열·헤더·행 수 · 목록 사용·금지 · 제목 · JSON 최상위·키·자료형 | J1과 경계 · J6와 공백 | 유지 |

| J5 DATA 신뢰도 | LLM + 서버 출처 검증 | 주장별 판정·출처·인용·공신력·시점 | 3-3과 겹침, 1-3과 공백 | 정책 검토 → D-2 |

### 2-2. 중복 판단 근거

이름이 아니라 **검사 대상·PASS/FAIL 조건·실패 유형·대체 가능성·충돌 가능성·이중 반영**을 비교했다.

- **질문 점수에는 이중 반영이 없다.** 질문 최종 판정은 FAIL이 하나라도 있으면 FAIL이므로, 같은 원인의 FAIL 두 개도 질문 점수에는 한 번만 반영된다. 이중 반영은 **조건·기준별 통과율**에서만 생긴다.
- `1-2.code_block` ↔ `1-2.code_fence_min`: 대상(코드블록)과 원인이 같고, 한쪽이 FAIL이면 다른 쪽도 FAIL. 다만 MD 165행이 별도 공식 조건이라 기준 계약을 바꿔야 통합할 수 있다.
- `2-1.count` ↔ `3-2.declared_count`: 같은 목록 누락이 두 조건을 FAIL시키지만 비교 기준(질문 요구 vs 답변 자기 선언)이 달라 서로 대체할 수 없다. 선언만 틀리고 요구는 맞는 경우가 있다.
- `2-1.literal` ↔ J2: 금지 문자열은 CODE가 정확히 판정한다. J2 '제약' 규칙(`쓰지 마`)도 같은 질문에 적용되고, CODE 범위 안내(`CODE_SCOPE_NOTE`) 예시에 문자열 조건이 없어 평가자가 같은 위반으로 J2를 FAIL할 수 있다. 판단 충돌(CODE PASS·J2 FAIL)은 표현이 비슷한 다른 문구를 쓴 경우에만 생긴다.
- `3-3` ↔ J5 input_consistency: 질문 원본 값을 답변이 옮겼는지 두 방식이 함께 본다. 3-3은 자료형까지 정확 비교, J5는 사용자 원문 인용 대조다.
- 중복이 이미 막혀 있는 곳: 표가 없을 때 행·열 조건은 `DEPENDENCY_FAILED`(FAIL 아님), JSON 구문 실패 시 필드 조건 `DEPENDENCY_FAILED`, 불릿 개수 요구가 있으면 2-2 목록 형식 조건을 만들지 않음, 같은 `dedupe_key` 결과는 `DUPLICATE`.

### 3-2. 기준 ID·스키마·저장 호환성

- 기준 ID(1-1 ~ 3-3, `check_id`, J1~J6, C1…)는 바꾸지 않았다. 통합 목록의 ID가 곧 기존 `check_id` 앞부분이라 저장된 결과도 그대로 연결된다.
- 결과 스키마·저장 형식·비교·이력은 바꾸지 않았다. 통합 목록은 런타임 판정에 쓰이지 않는다.
- 규칙이 바뀐 검사는 결과 행의 `check_version` 이 달라져, 같은 화면에서도 저장 당시 규칙을 구분할 수 있다.

### 3-3. Routing·집계 연결

- 질문 분석으로 기준을 고르는 단계: CODE는 질문 유형 분류 없이 모든 검사를 지나며, 검사마다 질문 조건(38종)이나 답변 구조가 있을 때만 결과 행을 만든다. 선택되지 않은 CODE 조건은 결과 행이 없다(분모에 들어가지 않음). 의미 평가는 J 적용 규칙으로 고르고, 적용되지 않은 J는 `not_applicable` 에 이유와 함께 남는다.
- 실행 시점: 문항마다 CODE → 의미 평가 1회(J + C 동시). C 보완 결과는 `code_completion` 에 따로 보존하고 CODE 원본·해시는 그대로다.
- 이중 집계 방지: C 보완은 판정 없는 행에만 적용된다. 질문 점수는 FAIL 개수와 무관하게 질문당 한 번이다.

### 3-4. 변경 영향 (향후 단계)

| 대상 | 통합 목록 도입 | 화면이 목록을 읽도록 확장 | 기준 통합·이동 (G 항목) |
|---|---|---|---|

## 4. 판정 정책 검토

### 4-1. 근거 없는 FAIL (J1~J4)

**현재 동작.** 지시문은 "FAIL이면 답변의 문제 부분을 작은따옴표로 인용"하라고 하지만 스키마는 빈 문자열도 받는다. `parse_decisions` 는 빈 이유를 버리고 판정만 저장하므로 근거 없는 FAIL이 `SUCCESS` 로 확정된다. 2026-10-12 1차 작업에서 화면에는 "평가자가 FAIL 근거를 남기지 않았습니다"로 표시한다. J5·J6은 서버가 인용을 원문과 대조해 근거가 없으면 확인 필요로 내리므로 이 문제가 없다. C 보완 판정은 이유가 하나라도 비면 그 묶음 전체를 `INVALID_RESPONSE` 로 거부한다.

**주의할 상호작용.** 최종 정책 `semantic-binary-outcome-v1` 은 확인 필요(UNVERIFIED)를 모두 "검증 기준 미충족 FAIL"로 바꾼다. 그래서 근거 없는 FAIL을 단순히 확인 필요로 내리면 다시 FAIL이 되어 A안과 같은 결과가 된다. B·C안은 이 정책에서 제외되는 별도 상태가 필요하다.

| 안 | 동작 | 장점 | 단점 | 기존 결과 영향 |
|---|---|---|---|---|
| A. 현재 유지 | FAIL 저장 + 근거 누락 표시 | 비용·지연 증가 없음, 결과 즉시 확정 | 근거 없는 판정이 통과율·순위에 그대로 반영. 재현·이의 제기 불가 | 없음 |
| B. 재평가 후 확정 (권장) | ① 서버가 J1~J4 FAIL의 이유가 비었는지, 따옴표 인용이 답변·질문 원문에 있는지 확인 (`combined._quoted_where`, J6 `_contained` 재사용) ② 실패 시 해당 기준만 1회 재질의 (검색 없음) ③ 그래도 없으면 `JUDGE_REASON_MISSING` 상태로 **미완료** (FAIL·PASS 아님) | 근거 있는 FAIL만 확정. C 보완 규칙과 일관. 평가 오류와 품질 FAIL 분리 | 재질의 비용(검색 없는 Opus 5.5 호출 1회 ≈ $0.02~0.04, 2026-10-12 시험의 문맥 판정 1건 $0.023 기준)과 지연(6~10초) 증가. 미완료 질문이 남으면 모델 점수 미확정 | 저장 결과는 재평가하지 않음. 새 실행부터 적용. 기준 버전 표기 필요 |
| C. 즉시 보류 | 근거 없는 FAIL을 받으면 그 기준을 미완료로 두고 수동 재평가 | 구현 단순, 추가 호출 없음 | 미완료가 늘어 점수 확정이 늦어짐. 재평가 동선 필요 | 위와 같음 |

영향: 질문 최종 판정은 근거 없는 FAIL 하나로 FAIL이던 질문이 B안의 ②에서 PASS가 되거나 ③에서 미완료가 된다. 기준 통과율은 확정 판정만 분모로 쓰므로 분모가 줄 수 있다. 평가 완료 상태는 ③이 남으면 미완료다. 저장 형식은 기준별 상태값 하나와 재질의 기록이 추가된다.

### 4-2. J5 데이터 신뢰도·검색 불가 상황

**현재 동작 (Claude 평가자).** 답변당 검색 4회·원문 열기 8회 한도. OpenAI 경로와 달리 J5 추가 검증 단계가 없다. 확인하지 못한 주장은 최종 정책으로 FAIL이 되며 사실 오류 확정과 `reason_code` 로만 구분된다.

| 상황 | 현재 내부 처리 | 최종 결과 | reason_code | 제안 분류 (분석용, 승인 전 미적용) |
|---|---|---|---|---|
| 출처가 명확히 반박 (실제 거짓) | 주장 FAIL + 서버 인용 확인 | FAIL | (없음) | 사실 오류 |
| 검색했으나 근거 부족·자료 상충·시점 불명 | 주장 UNVERIFIED | FAIL | EVALUATION_EVIDENCE_INSUFFICIENT | 검증 불충분 |
| 검색 한도(4회) 소진 | UNVERIFIED | FAIL | EVALUATION_EVIDENCE_INSUFFICIENT | 검증 불충분 (평가 예산) |
| 검색 기능 없음 (`SEMANTIC_WEB_SEARCH=disabled`, 검색 없는 CLI) | basis=none, UNVERIFIED | **외부 사실이 있는 모든 답변 FAIL** | EVALUATION_EVIDENCE_INSUFFICIENT | 검증 도구 사용 불가 |
| 출처 원문 접속·인용 대조 실패 (403·시간 초과 등) | 서버 검증 상태 기록 | FAIL | SOURCE_ORIGINAL_UNAVAILABLE | 검증 도구 실패 |
| 답변에 출처 없음 | 감점하지 않음 (2026-10-12 #20) | 사실 검증 결과대로 | — | 출처 미제공 (정보) |
| 답변이 든 출처가 주장을 뒷받침하지 않음 | 평가하지 않음 | — | — | 출처 불일치 (누락 후보) |
| 모든 주장 확인 | PASS | PASS | — | 검증 완료 |
| 호출 자체 오류 | API_ERROR 등 | 미완료 | — | 평가 오류 |

**권장안.**

1. **판정은 그대로 두고 분류를 추가(우선).** `decision_policy` 에 `evidence_gap`(검증 불충분·평가 예산·도구 사용 불가·도구 실패)을 추가 필드로 남기고, 기준별 표에서 "사실 오류 FAIL"과 "검증 기준 미충족 FAIL"을 나눠 센다. 기존 PASS/FAIL·점수는 바뀌지 않는다.
2. **검색 불가 환경은 FAIL이 아니라 미완료로 (승인 필요).** 같은 답변이 설정에 따라 FAIL이 되므로 모델 간·실행 간 비교가 깨진다. 웹 검색이 꺼진 상태에서는 외부 사실 J5를 평가 환경 미충족(미완료)으로 두거나 J5 실행을 막는다.
3. **Claude 경로 근거 보강 1회 (승인·유료 검증 필요).** OpenAI 경로의 `j5_targeted_evidence_v1` 과 같은 보강 1회를 Claude에도 두거나 검색 한도를 조정한다. 한도 소진에 따른 FAIL을 줄이는 목적이며, 실제 효과는 유료 호출로 측정해야 한다.
4. 출처 원문 접속 실패 FAIL(#20)과 근거 부족 FAIL(#21)은 사용자가 요청한 정책이라 유지하되, 1번 분류로 화면·통계에서 분리한다.

기존 결과 영향: 1번은 추가 필드라 저장 결과는 "분류 없음"으로 읽힌다. 2·3번은 새 실행부터 적용되고 저장 결과는 재평가하지 않는다.

### 4-3. CODE 보완 판정 미완료 (반영)

의미 평가는 끝났지만 C 보완 판정이 실패(`INVALID_RESPONSE` 등)하거나 기록이 없으면, 질문은 미완료인데 결과 카드의 "미완료 사유"는 의미 평가 미완료만 셌다. 이제 `caseState` 가 `code.pendingReason`(`코드 보완 판정 실패`·`코드 보완 판정 기록 없음`·`코드 보완 판정을 조건에 연결하지 못함`)과 원문 오류를 만들고, 결과 카드와 질문 상세 첫 줄에 표시한다. 판정·집계는 바뀌지 않는다.

## 5. CODE 세부 검사 검증 (Markdown·줄 수·문장 수·필수 문구)

합성 입력을 실제 엔진에 넣어 확인했다 (모델 호출 없음). "정의대로"는 현재 공식 측정 규칙(MEASUREMENT_v16)과 일치하는 동작이다.

| 입력 | 결과 | 판단 |
|---|---|---|
| 일반·중첩 목록, 3칸까지 같이 들여쓴 목록, `*`·`+` 혼용 | 최상위만 셈 | 정상 |
| 형제 항목 1칸 어긋남 (`- a` / ` - b`) | 하위로 세어 개수 FAIL | **파싱 오류 → 반영** |
| 목록 안 3칸 펜스 | 코드 인식 | 정상 |
| 목록 안 4칸 이상 펜스 (`10.` 항목, 중첩 목록 아래) | 코드블록 요구 FAIL, 코드 줄을 본문으로 셈 | **파싱 오류 → 반영** |
| 들여쓴 펜스의 Python | 발췌 코드로 보고 미판정 | **파싱 오류 → 반영** (펜스 들여쓰기 제거 후 구문 확인) |
| 목록 밖 4칸 들여쓴 백틱 줄 | 코드 아님 | 정상 (CommonMark) |
| Markdown 표, 2칸 들여쓴 표, 목록 안 표 | 표 인식 | 정상 |
| 코드블록 안 표 모양 텍스트 | 표 아님 | 정상 |
| 양끝 파이프 없는 표, 인용문 안 표 | 표 없음 FAIL | **파싱 오류 → 반영** |
| 파이프가 든 문장 + `---` | 표 아님 | 정상 (회귀 테스트 추가) |
| 인용문 안 목록 (`> - a`) | 불릿으로 세지 않음 | 남은 차이 (빈도 낮음, 후속) |
| 질문의 "JSON 배열" | '열'을 표 열로 읽어 열 조건 생성 | **추출 오류 → 반영** |
| 질문의 "3개 열로 된 표" | 항목 수(3개) 조건도 생성 | 남은 추출 오류 (후속) |
| 빈 줄·공백 줄·끝 줄바꿈·CRLF | 영향 없음 | 정상 (CRLF는 1차 작업에서 반영) |
| 줄 수: 제목 줄·출처 줄·`---` 구분선 | 줄로 셈 (3줄 요구에 4줄 FAIL) | 정의대로 ("코드 밖 비어 있지 않은 줄") → G-2 |
| 줄 수: 코드블록 줄·빈 줄 | 제외 | 정상 |
| 문장 수: 소수점·`Dr.`·`e.g.`·URL·말줄임표·물음표·따옴표 안 마침표 | 올바르게 분리 | 정상 |
| 문장 수: 마침표 없이 줄바꿈만 | 한 문장 | 정의대로 (마침표 뒤 공백·줄끝 기준) → G-2 |
| 문장 수: 목록 항목 | 항목마다 문장 | 정상 |
| 필수 문구: 강조 표시(`**안녕하세요**`), 앞뒤 공백 | PASS | 정상 (강조 제거 투영) |
| 필수 문구: 연속 공백·줄바꿈·NBSP·제로폭 공백·문구 사이 구두점·대소문자 차이·코드 안 문구 | FAIL | 정의대로 ("단순 출현") → G-1 |

## 6. 의미 평가 세부 기준 검증

| 항목 | 현재 지원 | 한계 |
|---|---|---|
| 판단 일관성 | 같은 기준 정의·지시문·스키마를 모든 모델·문항에 적용, 평가자 설정 고정 | 반복 실행 일관성은 유료 호출이 필요해 미검증 |
| 조건별 실패 근거 | J5 주장별, J6 지시별 근거와 인용 대조 | J1~J4는 한 문장. 여러 실패 원인이 한 문장에 합쳐질 수 있고 검증하지 않음 (D-1) |
| 다른 기준과의 중복 | 모든 J 지시문에 CODE 범위 안내 + 기준별 경계 문장 | J2와 금지 문자열, 3-3과 J5 겹침 (2장) |
| 문맥 유지 실패 검출 | J6: 처음부터 직전까지 전체 이력, 최신 유효 지시 우선, 이전 답변 오류를 현재 오류로 세지 않음, 인용 대조 | 이전 턴 형식·분량 지시는 제외 (G-3) |
| 근거 없는 주장 vs 사실 오류 | `factual_error_confirmed: false`, `reason_code` 로 구분, 화면 문구 분리 | 기준별 통과율에서는 같은 FAIL로 합산 (D-2 1번) |
| 적용 대상이 아닌 질문 | J2~J4 질문 요청 문장의 단어 규칙, J5 사실 없음은 해당 없음, J6 첫 턴 해당 없음 | 단어 규칙이라 과소·과다 선택 가능 (근거 문구를 결과에 남김) |

롱 컨텍스트 항목별:

| 항목 | 지원 |
|---|---|
| 이전 대화의 명시 조건 유지 | J6 (형식·분량 제외) |
| 여러 턴에 걸친 요구 반영 | J6 지시문: 첫 지시와 중간 변경 중 현재 적용되는 조건 모두 확인 |
| 장거리 참조 정확성 | J6 인용 대조, J5 input_consistency 의 이전 사용자 턴 근거 (`history_user`) |
| 대화 앞뒤 모순 | J6 "앞서 정한 이름·조건·결정과 모순" |
| 지시 우선순위 | 최신 유효 지시 우선 |
| 이전 답변의 오류 전파 | 이전 답변 오류를 현재 오류로 세지 않음. 현재 답변이 이전 오류를 반복하면 J5(사실)만 잡음 |
| 턴 구간별 유지율 | `conversations_summary` 의 1~10·11~20·21~30·31+ 구간 |
| 이력 길이 | 원문 전체 전송, 축약 없음 (Opus 5.5 1M 문맥). 비용은 턴 수에 비례해 증가 |

## 8. 다음 단계 준비 — 외부 플랫폼·API·웹·에이전트 수집 확장

이번 작업에서 외부 플랫폼을 연결하지 않았다. 확장 시 평가기에서 필요한 점:

1. **입력 계약.** 현재는 `question`·`answer`·`displayed_text`·`reference`·`conversation_id`·`turn`·`system_id`. 웹·에이전트 수집에는 실제 표시본(`displayed_text`), 답변이 든 출처 목록(구조화), 첨부, 수집 방식(`capture_method`) 메타데이터가 필요하다. 표시본이 있으면 AIONA-M·F와 1-2 닫는 태그 검사를 실제 화면 기준으로 돌릴 수 있다.
2. **HTML·렌더링 답변.** 웹에서 HTML로 받는 답변은 Markdown 파서 대상이 아니다. 표는 HTML 파서가 있으나 목록·제목·코드는 HTML→Markdown 변환 또는 HTML 구조 측정이 필요하다. 이번 CommonMark 보완은 Markdown 원문 답변에 해당한다.
3. **출처 검증.** 웹 채팅 답변은 대부분 출처를 단다. G-4(답변 출처의 주장 지지)가 없으면 출처 신뢰도 평가가 반쪽이다.
4. **에이전트 출력.** 도구 호출 과정·중간 결과를 평가하는 기준이 없다. 새 기준이 필요하면 통합 목록(`criteria_registry`)에 계층·근거 요구를 먼저 정의하고 승인받는다.
5. **멀티턴.** 플랫폼별 대화 ID·턴 번호를 현재 계약으로 맞추면 J6와 이력 전송이 그대로 동작한다. 긴 대화는 문항당 비용이 턴 수에 비례한다.
6. **블라인드·비용.** 모델명·메타데이터 제거는 이미 있다. 평가 비용은 문항당 의미 평가 1회 기준으로 추정한다.

### 9-1. 판정 상태와 지표의 의미

- 기준 상태가 하나 늘었다: **판정 미완료(`INCOMPLETE`)** — PASS·FAIL 이 아니며 최종 정책도 FAIL 로 바꾸지 않는다. 사유는 `reason_code` (`JUDGE_FAIL_EVIDENCE_MISSING`, `J5_SEARCH_UNAVAILABLE`, `J5_SEARCH_ERROR`).
- 질문 판정: 확정 FAIL 이 하나라도 있으면 FAIL, 모든 적용 기준이 PASS 면 PASS, 그 밖은 미완료 — 정의는 이전과 같다.
- 모델 점수(PASS 질문 수 / 전체 질문 수)와 기준 통과율(PASS / (PASS + FAIL))의 계산식은 바꾸지 않았다. 미완료는 통과율 분모에서 빠지고 '미확정'·'판정 미완료 N'으로 따로 표시된다.
- **이전 결과와 비교할 때 주의:** 이전 정책은 근거 없는 FAIL 과 검색 불가 J5 를 FAIL 로 확정했다. 같은 데이터라도 새 정책에서는 일부가 PASS·미완료가 되거나 출처 불일치 FAIL 이 생긴다. 모델 점수가 확정되던 실행이 미완료 질문 때문에 미확정이 될 수 있다. 결과의 `decision_policy`·`jev_eval.version`·`versions.engine` 으로 정책을 구분한다. 저장된 결과는 다시 계산하지 않는다.
