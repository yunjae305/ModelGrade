# 첨부(이미지·텍스트 문서) 최소 평가 설계 (2026-10-14, 설계 — 이미지 경로는 구현 전)

> **10-14 3차 갱신**: main `b9145d7` 에 J8 첨부파일 활용이 들어왔다 — 업로드 `attachments: [{name, type, content}]`, 평가 모델은 파일 대신 `content`(글자 파일은 원문, 이미지는 그림 속 글자·값)를 받는다. 아래 §1 의 '업로드에서 거부'는 그 뒤 브랜치에서 뺐고, §2 의 텍스트 문서 경로는 J8 의 `content` 로 대체된다. 아직 남은 것은 **답변 수집 때 API 모델(GPT·Claude·Gemini)에 첨부가 전달되지 않는 문제**다 ([3차 보고서](3차검증_2026-10-14.md)).
>
> **10-14 3차 구현**: 답변 수집 경로는 `webapp/attachment_delivery.py` 로 구현했다 (8ad4b9d·ddc499c). 글자 첨부는 질문 뒤에 `[첨부파일: 이름 (형식)]` 블록으로, 이미지는 허용 폴더(`data/attachments`·`data/question_sets`·`examples`)의 실제 파일만 각 제공자 이미지 블록으로 보내고(파일 이름만 있으면 sha256 이 맞을 때만), 못 보낸 첨부는 행의 `collection.request.attachment_delivery` 에 `not_sent` 와 사유로 남긴다. PDF·DOCX 글자는 `tools/attachment_text.py` 로 뽑아 `content` 에 넣는다 (30cb364). **평가자(Opus)에게 이미지 파일을 보내는 §3-4 는 아직 구현 전** — 평가자는 J8 의 `content`(글자)만 받는다. 실제 API 로 이미지를 보낸 호출은 0회(모의 테스트만).

| 단계 | 보내는 것 | 첨부 |

| 업로드 `normalize_dataset` | — | `attachments`·`images`·`files`·`image`·`pdf` 필드가 있으면 이유와 함께 거부 (1차 P1-F — 3차에서 J8 과 충돌해 브랜치에서 뺌, 지금 코드에는 없음) |

지난 커밋 전에는 첨부 필드가 조용히 버려지고 텍스트만으로 평가될 수 있었다. 지금은 업로드에서 막고, 사전 점검(`check_question_set`)이 첨부 질문과 "첨부를 가리키지만 첨부가 없는 질문"을 따로 보고한다.

## 2. 텍스트 기반 PDF·문서 — 지금 바로 쓸 수 있는 경로 (검증됨)

- 추출한 본문을 질문 텍스트에 넣어 올린다. 모델과 평가자가 같은 본문을 받으므로 첨부 전달 문제가 없다.
- 기존 규칙이 그대로 붙는다 (`tests/test_attachments.py::test_text_document_inlined_in_the_question_reuses_the_existing_checks`):
  - CODE: 질문이 준 형식·분량 조건(예: '세 줄로'). 이 시험에서 CODE 2 가 적용됐다.
  - J5-2: 문서가 준 값(날짜·금액)과 요약 요청 — 답변이 문서와 맞는지 본다.
  - J7: 본문 길이를 o200k 로 재서 하한(현재 272K) 이상이면 적용. 짧은 문서는 해당 없음. 하한만 낮추면 같은 경로로 J7 이 붙는다.
- 한계:
  - 표·그림이 많은 PDF 는 추출 품질이 결과를 좌우한다. 추출 도구와 버전을 질문 메타데이터에 남겨야 한다.
  - 스캔 PDF 의 OCR 텍스트는 '이미지 이해'가 아니라 '문서 이해' 평가로만 본다.

## 3. 이미지 — 최소 설계 (구현 전)

목표는 "이미지를 실제로 받은 답변"만 평가하는 것이다. 파일명·OCR 로 대신하지 않는다.

1. **입력 형식**: 질문 행의 `attachments: [{kind: "image", name, sha256, path}]`. 파일은 실행 폴더에 저장하고 원본 해시를 남긴다.
2. **수집**: 각 제공자 API 의 이미지 입력 블록으로 질문과 함께 보낸다. OpenAI·Anthropic·Gemini 모두 이미지 입력을 지원한다(형식·크기 제한은 공식 문서로 다시 확인할 것). 요청 구성 기록(`collection.request`, 698e96f)에 첨부 해시·개수를 더해 "실제로 보냈는지"를 행마다 남긴다. 보내지 못한 모델은 `NOT_COLLECTED` 로 두고, 텍스트만으로 묻지 않는다.
3. **CODE**: 텍스트 조건만 그대로 (답변 형식·분량·계산). 이미지 내용 검사는 하지 않는다.
4. **의미 평가**: 평가자(Opus)에게도 같은 이미지를 보낸다. 기준은 새로 만들지 않고 J1(요청 수행)·J2(대상·수준)·J4(빠짐)·J5(이미지에 있는 값과의 일치 — J5-2 '질문이 준 자료'로 봄)를 쓴다. 평가자 요청에 이미지가 빠지면 그 답변의 의미 평가는 `INCOMPLETE`(첨부 미전달)로 남긴다.
5. **결과 표시**: 첨부 질문 수, 첨부를 실제로 받은 모델·평가자 수, 미전달로 미완료된 수를 따로 센다.

### 재사용 / 새로 필요한 것

| 재사용 | 새로 필요 |
|---|---|
| CODE 엔진, J1·J2·J4·J5-2 판정·집계·화면, 업로드 검증, 요청 구성 기록, 비용 상한(예약금) | 첨부 저장·해시, 제공자별 이미지 요청 블록, 평가자 이미지 전달, '첨부 미전달' 미완료 사유, 업로드 형식 |

## 4. 비용·검증 계획

- 이미지 입력 토큰은 모델마다 계산법이 달라 실제 사용량으로만 확인한다. 소규모(이미지 질문 5개 × 3개 모델 + 평가)로 먼저 재고, 비용 상한은 승인 뒤 정한다.
- 검증 순서: 모의 제공자로 '첨부가 요청에 실렸는지' 시험 → 소규모 실호출 → 사람 검수 5~10건(이미지에 실제 있는 값과 맞는지).

## 5. 정할 것

1. 이미지 평가를 10-21 범위에 넣을지, 텍스트 문서 경로만 먼저 쓸지.
2. 텍스트 문서 추출 도구(그리고 표·그림 처리)를 무엇으로 고정할지.
3. 이미지 내용 일치를 J5-2 로 볼지, 별도 세부 기준으로 둘지 (새 기준이면 기준 버전을 올려야 함).
