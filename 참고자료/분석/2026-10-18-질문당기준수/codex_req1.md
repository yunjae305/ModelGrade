# 요청: 질문당 기준 수(k) 범위(boundary) 결정 방법 검토 + 개선안 (한국어로 답)

## 목표
질문생성 프롬프트에 "한 질문이 노리는 평가 기준 수"를 고정값이 아니라 **범위 [a, b] + 허용 오차(범위 밖 질문 비율 ±%)** 로 넣으려 한다. 임의로 정하지 않고 데이터로 근거를 만들어야 한다(1개부터 촘촘하게 바꿔 가며).

## 데이터
- 질문 세트 326개(단일 310 + 대화 16) — 질문 파일 `C:/Users/winz/Desktop/quality-test-integrated/참고자료/수집결과/2026-10-14-질문세트326-세부기준/questions.json`
- 이미 받은 답: AIONA·GPT(gpt-6-luna)·Gemini 각 425턴 (`answers.json` 같은 폴더)
- 평가: CODE 검사(코드) + 의미 평가 GPT-6 Luna(high, J1~J8) + Jev(J1~J4, 확신도). 결과: `eval326/luna-*.jsonl`, `eval326/jev-*.jsonl`, `eval326/*.json`
- 평가 기준 72개 = CODE 28 + 의미 44. 질문 내용으로 적용이 정해지는 64개 중 항상 적용 의미 항목 7개 제외 = k 를 세는 57개.

## 지금 분석 (`boundary326.py`, 결과 `boundary326.json`)
- k = 질문만 보고 코드 규칙(webapp.question_generation.check)이 정한 적용 기준 수 (대화는 턴별 k 평균)
- k 별: 세 모델 PASS 비율, 변별(세 모델 질문 판정이 갈린 비율), 전부 PASS·전부 FAIL, 기준 하나 통과율, Jev↔Luna J1~J4 일치
- 범위 [a,b] 스윕: 범위 안 단일 질문만으로 지표, 범위 밖 비율(=허용 오차 후보), 커버리지(범위 안 질문 분포로 326개를 채운다고 비례 환산했을 때 57개 기준이 각각 몇 번 적용되는지)
- 1차 결과: k 4~12 변별 0.34~0.60(비단조), 전부 FAIL 은 k≥10 에서 급증(0.43), 기준 통과율 0.90~0.94 평탄, Jev↔Luna 일치 0.97~1.00. 변별만으로 고르면 4~4 같은 좁은 범위(커버리지 6/57)가 뽑힘.

## 검토해 줄 것
1. 방법의 결함(관찰 데이터 교란: k 와 질문 유형·난이도·J5 적용 여부가 얽힘, 작은 n, 대화 처리, 비례 환산 커버리지의 타당성, 지표 정의 등)
2. 범위 [a,b] + 허용 오차를 고르는 **결정 규칙**(제약 + 목적 함수)을 구체적으로 제안 — 예: 커버리지 하한, 전부 FAIL/전부 PASS 상한, 변별 최대, 부트스트랩 신뢰구간, 허용 오차 t 를 0~30% 로 바꿔 가며
3. 코드 버그(파일 읽기만 — 수정하지 말 것): boundary326.py, eval326.py
4. 관찰 데이터로 부족하면 추가 실험 설계(필요 최소 질문 수, k 별 표본)
끝에 우선순위 목록으로 정리.
