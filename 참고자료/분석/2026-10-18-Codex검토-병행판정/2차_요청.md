# 2차 검토 요청 — 1차 지적 반영 + 질문 생성기 k 범위 단계 추가

1차 지적 반영 (diff 는 같은 폴더 `diff2.patch`, 새 파일 `code_eval/dual_judge.py` 는 저장소에서):
1. `semantic_evidence._in_answer` 느슨한 대조를 **공백 제거 + 따옴표 모양 통일만**으로 줄이고, 비교 대상도 raw 가 아니라 rendered(굵게 표시를 코드 밖에서만 벗긴 답변)로 바꿈 → 연산자·표 칸 구분(|)·코드 안 `**` 보존. 기존 시험 15개 통과 확인.
2. `dual_judge`: 중단(cancel_event)·재판정 SKIPPED 은 전체를 SKIPPED 로 전파(`_skipped`, answers 버리고 verification·사용량만). 
3. `dual_judge`: 사용량은 `accounting.usage`(재시도 누적) 우선(`_usage`), Jev 부분에 `unreported_attempts` 전달, 전체 accounting 에도 합산.
4. `frontend/src/workspace-results.js`: 보류(`held`·`source_unavailable`·`insufficient_evidence`·`search_limit_reached` 이면서 판정 없음)를 `j5Held` 로 구분해 '보류 — …' 문구·pending 스타일. 옛 FAIL 기록은 그대로.
5. `semantic_setup`: openai_api·dual 모두 `resolve_jev_client(…, "openai_api")` 로 같은 설정 생성·검증, dual 은 Jev 쪽도 `resolve_jev_client(…, "jev")` + 주소 검사(`_check_jev_base`).
6. `semantic_policy`: 출처 확인 실패 보류의 `changes` 항목을 `status: UNVERIFIED` 로.

새로 추가 — `webapp/question_generation.py` (question-gen-v2.0-kvar):
- 상수 `K_RANGE=(6,10)`, `K_OUT_RATIO=0.15`, `K_REPAIR_ROUNDS=2`, `K_REPAIR_BATCH=20`.
- `_K_RULE` 문구를 plan_prompt(기존 "조건 8개 이상/1~3개 섞기" 문장 대체)·extra_prompt·supplement_prompt 에 넣음.
- `k_var_units`(변동 기준 54개 — 항상 적용 CODE 3·의미 7·답변 전용 7·J5-3.a 제외), `k_var_by_group`(check 보고서의 cases 에서 턴별 적용 기준 집합 → 대화는 평균 반올림), `k_var_summary`(단일 질문의 분포·범위 밖 수·상한 floor(단일 × 0.15)), `k_repair_prompt`, `parse_k_repair`.
- `build()` 끝에 고치기 단계: 범위 밖 단일 질문 수 > 상한이면 범위에서 먼 것부터(긴 입력 질문 제외) 최대 20개씩 GPT 에 "조건만 고쳐 k 를 범위로" 요청 → 질문 본문·target_items 교체 → check 다시 → 최대 2회. 적용 수가 모자란 기준(≤ per_target 또는 10)은 빼지 말라고 protect 목록으로 보냄. 결과에 `k_var`·`k_rounds`, `_summary` 에 `k_var`.
- 실험 세트 300문항으로 k 분포 재현 확인(1~16 각 15~25개). 생성기 시험 22개 통과.

## 특히 봐 주었으면 하는 것
- 고치기 단계의 예산(`_ask` 호출 상한)·취소·경고 처리, `k_var_by_group` 의 case_id 파싱(`Q{id}_T{n}`), 질문 본문만 바꾸고 첨부·참조를 유지하는 것이 `flatten`/`check` 와 맞는지, 고친 뒤 커버리지가 떨어질 수 있는 문제.
- `k_var_summary` 가 긴 입력 단일 질문·대화를 다루는 방식(상한 계산에 긴 입력 포함, 고치기 대상에서는 제외).
- 1차 지적 반영이 충분한지. 남은 문제가 없으면 `VERDICT: APPROVED`, 있으면 `VERDICT: REVISE`. 한글로.
