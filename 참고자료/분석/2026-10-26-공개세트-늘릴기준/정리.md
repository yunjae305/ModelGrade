# 공개 세트로 늘릴 기준 찾기 (2026-10-26)

미팅 10-26 결정: 공개 데이터에서 우리 기준에 맞는 질문이 적다 → 기준을 깎지 말고 늘려서 더 많은 질문을 덮는다. 이 문서는 맞지 않는 질문을 보고 **어디를 늘릴지**만 정리한다. 코드 · 기준 문서 · 프롬프트는 고치지 않았고, 모델 · API 호출도 없다.

## 결론

- **가장 큰 구멍은 새 기준보다 인식이다.** LLM 항목 규칙(J2~J5)은 '요청 문장'(끝이 `줘 · 주세요 · 마 · 해 · ?`)에서만 낱말을 찾는다. 그래서 번역투(`하세요 · 하십시오 · 하라 · 해야 합니다`)로 쓴 공개 질문은 **IFEval 205/342 · KoMT 42/80 이 요청 문장 0개**라 항목이 붙지 않는다. 이 끝말만 넓혀도 IFEval '기준 1개 이상' 225 → 277.
- CODE 쪽은 이미 있는 2-1.literal · 2-1.count · 2-2.heading 이 알아보는 범위를 넓히면 IFEval 지시 9종(쉼표 금지 · 큰따옴표 감싸기 · 요청 반복 · 추신 · 끝 문구 · 따옴표 없는 금지어 등)이 덮인다. 새 기준은 아니다.
- 새 기준 후보는 13개다(CODE 8 · LLM 또는 정답 대조 5). 우선순위 '상'은 강조 구간 개수 · 낱말 빈도 · 자리표시자 개수 · 구분자로 나눈 답(IFEval) · 최종 답 정확(KoMT 수학 · 추론)이다.
- 모두 넣어도 **k 6~10 은 IFEval 3 → 27, KoMT 0 → 0**이다(어림). 공개 질문은 한 질문에 요구가 1~3개뿐이라 k 6 이상이 되기 어렵다. '기준 1개 이상'은 IFEval 225 → 342, KoMT 45 → 72 까지 늘어난다. 공개 질문을 쓰려면 기준을 늘리는 것과 별도로 **k 범위 규칙(6~10)과 v2 4절 '공개 세트는 쓰지 않는다'를 공개 질문에만 다르게 둘지** 결정해야 한다(참고: k 3 이상이면 IFEval 178 · KoMT 27).

## 방법 (숫자를 센 방법)

- 10-25 검토와 같다. 질문만 넣고(답은 빈칸) `tools/check_question_set.check_items(pipeline=items)`로 적용 CODE 검사 · LLM 항목을 센 뒤 `k_var_units()`(54개)와 겹치는 수를 k 로 했다. 같은 실행에서 `evaluate_batch`의 질문 조건 종류(`question_conditions`)도 모았다.
- 재현: `python -X utf8 참고자료/분석/2026-10-26-공개세트-늘릴기준/count_public.py` → `counts.json`(문항 번호 · 적용 기준만 담고 원문은 넣지 않음). 10-25 의 k 분포가 그대로 나온다(IFEval 0:117 · 1:123 … · 7:2, KoMT 0:35 · 1:27 · 2:11 · 3:7).
- '질문당 CODE 변동 검사'는 이번에 문항 단위로 셌다. 한 문항에 같은 지시가 두 번 있어도 1로 세서, 10-25 표와 0.01 정도 다를 수 있다.
- 어림(4절)은 스크립트 안에서만 가정을 더했다. 요청 문장 끝 규칙을 실행하는 동안에만 바꿨고, IFEval 은 원본 지시 목록을, KoMT 는 범주를 '완벽히 알아본다'고 보았다. 그래서 위쪽 어림이다.

모두 따로 세면 기준 수는 72 → 85 가 된다. 2-1 · 2-2 안의 조건 종류로 넣으면 기준 수는 72 그대로지만, 같은 검사로 묶여 1로 세어지므로 k 는 덜 오른다.

## 4. 다 넣으면 (어림)

| 단계 | IFEval 기준 1개 이상 | IFEval k 6~10 | KoMT 기준 1개 이상 | KoMT k 6~10 | 참고 k 3 이상 (IFEval · KoMT) | 평균 k (IFEval · KoMT) |
|---|---|---|---|---|---|---|
| 지금 | 225 | 3 | 45 | 0 | 40 · 7 | 1.16 · 0.88 |
| + R1 요청 문장 끝 | 277 | 8 | 54 | 0 | 98 · 14 | 1.88 · 1.26 |
| + R2~R5 기존 기준 인식 | 300 | 16 | 55 | 0 | 127 · 14 | 2.28 · 1.29 |
| + 새 CODE 8개(N1~N4 · N7 · N11~N13) | 342 | 24 | 55 | 0 | 160 · 14 | 2.76 · 1.29 |
| + 새 LLM · 정답 5개(N5 · N6 · N8~N10) | **342** | **27** | **72** | **0** | 178 · 27 | 2.96 · 1.94 |

가정:
- R1 은 실제 규칙을 실행하는 동안에만 바꿔서 다시 셌다.
- R2~R5 · 새 CODE 는 IFEval 원본 지시 목록(`instruction_id_list`)을 그대로 알아본다고 보았다. 실제 인식기는 이보다 덜 잡을 것이다.
- 새 LLM · 정답 기준은 KoMT 범주(math · reasoning → 최종 답, coding → 코드 동작, roleplay → 역할, extraction → 추출)와 낱말 규칙(장르: 장르 낱말과 쓰기 동사가 한 문장에 있을 때)으로 붙였다.
- 새 기준은 모두 변동 기준(k 에 셈)으로 넣었다.
- k 6~10 에는 10-25 에 지적한 '자료 없는 질문에 J5-2.a · J5-1.a 가 붙어 부풀려진 k'도 섞여 있다.
- KoMT 는 최대 k 가 5 다. 질문 하나에 요구가 1~2개라서, 기준을 늘려도 k 6~10 에는 들지 않는다.

## 5. 돌려 보기 — 하려면

이번에는 하지 않았다. 하려면 R2~R5 와 새 CODE 를 넣었을 때 k 3 이상이 되는 IFEval 20문항(N1~N4 · N7 · N11 을 3~4개씩)과 KoMT 10문항(math 3 · reasoning 2 · coding 2 · roleplay 2 · extraction 1), 모두 30문항을 네 모델에서 웹으로 받는다. 수집은 약 40분이다(78문항 1시간 반 기준 어림). 지금 기준으로 판정하면 약 20~30분이 더 걸린다. 새 기준은 구현한 뒤에야 판정할 수 있고, N5 에는 KoMT 참조 답이 필요하다.

## 확인하지 못한 것

- 실제 인식기를 만들었을 때 얼마나 잡히는지 모른다. S2 · S3 는 정답 지시 목록을 쓴 위쪽 어림이다.
- KoMT 참조 답을 확인하지 못했다. MT-Bench 계열은 math · reasoning · coding 참조 답이 있는 것으로 알지만, 로컬(`data/question_sets/public_sources/`)에는 질문만 있다.
- 새 기준이 모델을 가려내는지(변별력)와 LLM 후보의 판정 일치는 답을 받지 않아 모른다.
- '약 440문항' 가운데 IFEval 342 + KoMT 80 = 422개만 보았다. git 이력에 있는 LogicKor · Ko-Arena-Hard 등은 보지 않았다.
- KoMT 2턴은 앞 턴 없이 따로 세기만 했다(공식 k 아님). R6 낱말 규칙은 어림하지 않았다.
- 장르 · 역할 낱말 규칙(스크립트의 `GENRE` · `PERSONA`)은 어림용이다. 표본만 보았고(KoMT 오탐 4개를 쓰기 동사 조건으로 걸러냄) 전수 확인은 하지 않았다.
