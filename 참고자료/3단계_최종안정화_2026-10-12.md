## 1. 수정 내용

### F1 — 공급자가 직접 연 출처 원문 인정 (`87a8074`)

- 원인: `_provenance` 가 `web_search` 결과만 `search_performed` 로 세고, `verify_web_sources`·`_fact_check` 는 그 값이 있어야 웹 출처를 대조·인정했다. G4-01 에서 Claude 는 답변이 든 URL 을 `web_fetch` 로만 열어 확인했는데, 서버가 근거를 버려 근거 부족 FAIL 이 됐다.
- 수정: 공급자 `web_fetch_tool_result` 의 URL 을 `fetched_urls` 로 따로 기록한다. 검색 결과에 있거나 공급자가 직접 연 URL 만 서버가 다시 받아 인용문을 대조하고, 출처마다 `retrieval`(`web_search`/`web_fetch`)을 남긴다. `search_performed` 는 계속 검색만 센다.
- 유지: 모델이 적기만 한 URL, 공급자 열기가 실패한 URL, 다른 URL 을 연 기록은 계속 인정하지 않는다. 인용문 원문 대조·공신력·기준 시점 조건은 그대로다.

### F2 — 주장 수치에서 출처 표기 제외 (`79d9253`)

- 원인: 답변 출처 확인(G-4)에서 `claim` 전체(`… ([출처](https://docs.python.org/3/…))`)의 숫자를 읽어, URL 경로의 `3` 이 출처 원문에 있으니 '무관' 판단을 확정하지 않았다.
- 수정: 수치를 읽기 전에 괄호 안 출처 링크는 통째로, 본문 속 Markdown 링크는 주소만 빼고 표시 글자는 남긴다. 맨 URL·`<URL>`·`www.` 주소, `[1]`·`[1, 3]`·`[^1]` 인용 번호도 뺀다.
- 실제 데이터 확인: 저장된 G4-02 의 Claude 출처 판정(`unrelated`, 서버 수신 ok)에 적용하면 수치가 `['3']` → `[]` 가 되어 '무관'이 확정되고 J5 는 출처 불일치 FAIL(기대)이 된다. G4-01·G4-04 도 URL 숫자만 있던 경우였고, G4-03 은 본문 수치(2칸·PEP 8)가 그대로 남는다.

### F3 — 이전 턴 지시 해제 (`278d9a9`, 엔진 v16.3.2, 측정 규칙 [MEASUREMENT §19](MEASUREMENT_v16.md))

- 원인: `extract._CANCEL` 이 표·목록·분량 같은 대상 낱말 + 해제 표현만 인식해 `'이상입니다.'로 끝내지 않아도 돼` 같은 문구 해제를 몰랐다. 또 `'X'로 끝내지 마/않아도 돼` 를 그 문구로 끝내라는 요구로 추출했다(현재 턴에도 영향이 있던 기존 오류 — 해제 처리와 같은 경로라 함께 고침).
- 수정:
  - 따옴표 문구를 가리킨 해제(`끝내지 않아도 돼`·`빼줘`·`붙일 필요 없어`·`끝내지 마`·`없이`)는 그 문구 지시만 지우고 다른 문구 지시는 유지
  - `'X'는 이제 써도 돼` 는 그 문구의 금지만 해제
  - 끝맺음·끝인사·맺음말·시작 문구 낱말 인식, `표 형식은`·`글자 수 제한은` 처럼 대상 뒤 일반 낱말이 붙어도 그 대상만 해제(이전에는 전체 해제)
  - `취소`·`필요 없어`·`하지 마`·`예외` 추가. `무시하지 마` 처럼 해제 낱말을 다시 부정하면 해제가 아니고, `표현은…` 을 표 해제로 읽지 않음
  - 이전 턴의 `이번에는·이번 답변만` 해제·예외는 그 턴에만 적용, 현재 질문의 일시 해제는 현재 턴에 적용
  - 큰따옴표 인용과 띄어쓰기가 든 작은따옴표 인용(발언) 안의 지속·해제 표현은 지시가 아님
- 사용자 질문만 읽는 규칙(AI 답변 제외), 해제 시점 이전 턴의 결과, 현재 질문 우선, 작업 한정 지시는 그대로다.

### F4 — 요청에 바로 나열한 사용자 제공 값 (`9415bcf`)

- 원인: `_input_scope` 가 질문에 '다음·주어진·자료' 같은 표지어가 있어야 정리·요약 과업의 입력을 인정했다. `화요일 할 일도 정리해 줘: 빨래, 청소.` 를 Claude 는 입력 일치 PASS 로 봤지만 서버가 근거 부족 FAIL 로 바꿨다.
- 수정: `정리해 줘: A, B`, `할 일 목록: A, B`, `할 일은 A와 B야` 같은 나열을 제공 자료로 인식하고, 변환 과업에 분류·정렬·나열·순서대로를 더했다.
- 유지: 추천·비교 같은 판단 과업, 진위 확인 요청, 실제 시장 자료 요청, `external_fact` 주장은 계속 웹·참조 근거가 필요하다. 입력 일치는 그 값의 현실 진위를 인정하지 않는다(기존 안내 문구 그대로).
- 이 수정은 이전 문서에서 승인 대상(입력 일치 인정 범위 변경)으로 분류됐고, 이번 요청에서 F1~F4 수정 진행이 지시됐다.

### F5 — 출처 수집 (`6d08105`)

- `www.` 만 다른 리다이렉트(`www.afdc.energy.gov` → `afdc.energy.gov`)를 같은 발행처로 허용했다. 다른 하위 도메인·도메인 이동은 계속 `redirect_host_changed`. 단계마다 공개 DNS 주소·포트·인증서 검증·횟수(3)·시간(8초/30초)·크기(2 MiB) 제한은 그대로이고 403 우회는 하지 않는다.
- 접근 실패 원인을 `detail` 로 기록한다: `http_403`·`http_500` 등, `tls_certificate`. `status` 값과 판정 정책은 바꾸지 않았다.
- 기존 테스트 하나(apex → `www.` 이동도 거부)는 이 과잉 차단 규칙 자체였으므로 기대를 나눴다: `www.` 이동은 허용, 다른 호스트·`www.다른도메인`·다른 하위 도메인은 거부.

### F8 — 프롬프트 캐시 (`9ccfb79`)

- 사용자 메시지를 '고정 지시문 + 실행 시각·평가 데이터' 두 텍스트 블록으로 나누고 앞 블록에만 `cache_control: {type: "ephemeral"}`(5분)을 둔다. 캐시 지점까지 도구 정의·시스템·평가 규칙이 들어간다. 이어 붙인 문장은 기존 프롬프트와 글자까지 같다.
- 무료 `count_tokens` 확인: 새 요청 형식을 API 가 받았고 20문항 첫 요청 입력이 **273,728 토큰으로 변경 전과 같다**. 그중 캐시 가능한 고정 부분이 268,271 토큰(98%), 서로 다른 고정 부분은 8종(기준 조합별).
- 캐시를 쓰는 요청에서는 서버 도구(web_search/web_fetch) 결과 뒤에도 공급자가 자동으로 캐시를 쓴다 — 같은 요청 안의 검색 반복 입력이 캐시 읽기($0.20/M)로 바뀌는 것이 주 절감 원천이다.
- `SEMANTIC_ANTHROPIC_PROMPT_CACHE=on/off`(기본 on), 결과 manifest 에 `prompt_cache_policy` 기록. API 버전·모델·effort·도구 버전은 바꾸지 않았다.
- 재평가(D-1)는 이미 해당 기준만, 검색 없이 보내므로 더 줄일 부분이 없다.

### F5b. 서버가 받지 못한 출처의 처리

- 현재: 서버 수집 실패(403 봇 차단·인증서·500·다른 호스트)이고 다른 확인된 근거가 없으면 J5 FAIL `SOURCE_ORIGINAL_UNAVAILABLE`(사실 오류 아님, `source_unavailable`). 실사용 20문항 중 4건(D1-04·D2-02·G3-02·GEN-03).
- 문제: 실제 사실 오류(D2-02 에펠탑 1925년)가 '원문 확인 실패'로, 참인 주장도 출처가 막히면 FAIL 이 된다.
- **권장안 P1 — 공급자 원문 대조**: 같은 요청에서 공급자 `web_fetch` 가 그 URL 문서를 받았다면, 서버 수집이 접근 오류일 때만 그 문서 본문(메모리에서만, 저장하지 않음)으로 인용문을 대조한다. 기록은 `retrieval=provider_document`. 둘 다 못 받으면 지금처럼 FAIL. 정책 버전 `j5-source-original-failure-v2`.
  - 영향: D2-02·D1-04 는 Claude 가 해당 페이지를 web_fetch 로 열었다면 '사실 오류'로 정확히 분류된다(저장 기록에는 블록 원문이 없어 사전 확인 불가 — F1 로 `fetched_urls` 를 남기므로 다음 실행부터 측정 가능). 질문 판정이 바뀌는 쪽은 '출처 차단으로 FAIL 이던 참 주장' → PASS.
  - 위험: 공급자 문서는 변환된 텍스트일 수 있어 인용 대조 정규화가 필요하다.
- 대안 P2 — 접근 실패를 판정 미완료(INCOMPLETE): 권장하지 않음. D2-02 처럼 명백한 오류가 미완료가 된다.

### F6. J6 의 형식·분량 이중 판정

- 원인: J6 공식 경계(`jev_criteria.py` "분량·형식 지시는 코드 검사 영역", 통합 기준 목록 "J6는 의미 맥락만")가 기준 정의 쪽에만 있고, J6 절차 지시문은 "현재 적용되는 모든 관련 조건을 확인"하라고 해서 Claude 가 G3-02 의 '2문장 이내'를 context_checks 에 넣어 FAIL 했다.
- 영향: 질문 판정은 CODE FAIL 로 이미 FAIL 이라 바뀌지 않지만, 기준별 J6 FAIL 률과 모델 간 J6 비교가 부풀려진다.
- **최소 수정안**: `semantic_cli_common.py` J6 절차의 "후속 사용자 지시가 … 최신 유효 지시를 따릅니다." 뒤에 다음 문장을 넣고 `CONTEXT_CHECK_POLICY` 를 `history-quotes-v3-code-boundary` 로 올린다.
  > 문장·글자·줄·문단 수, 항목 수, 표·목록·JSON·코드블록·제목 형식, 시작·끝·필수·금지 문구처럼 코드 검사가 셀 수 있는 형식·분량 지시는 이전 턴 지시도 코드 검사가 이어받아 따로 판정합니다. 이런 지시는 context_checks에 넣지 말고 그 위반만으로 J6를 FAIL로 판단하지 마세요. 같은 이전 턴 문장에 말투·호칭·역할·금지 주제·기억할 정보 같은 의미 지시가 함께 있으면 그 의미 지시만 확인하세요.
- 서버 후처리(J6 FAIL 중 CODE 가 이어받은 지시만 인용한 것을 지우기)는 권장하지 않는다: 같은 문장에 의미 지시가 섞이면 의미 실패까지 지울 수 있다.

A는 2025년 점유율이 70%였습니다'에서 점유율만 claim입니다. 맞춤법·문장 교정·번역·문체 변경 답변의 교정·번역 결과 문장 자체는 claim이 아닙니다(J1·J2 영역). 답변이 근거로 든 어문 규정이나 사실 설명만 claim으로 확인하세요.
